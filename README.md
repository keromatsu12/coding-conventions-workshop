# coding-conventions-workshop

`docs/coding-conventions.md`（保守できるコードの原則 — 全5部20章）の**演習用リポジトリ**です。

> ## ⚠️ 警告
>
> **`src/` 以下のコードは、意図的に悪く書かれています。**
>
> 命名、関数分割、依存関係、状態管理、エラー処理、セキュリティ、パフォーマンス —
> 資料で「やってはいけない」とされていることを、わざと全部やっています。
> SQLインジェクションもXSSも**実際に成立します**。
>
> コピーして実務に持ち込まないでください。学習目的以外で使わないでください。
> コード中の APIキー・トークン・パスワードはすべてダミーの文字列です。

このリポジトリには **「悪いコード（Before）」しか入っていません。**
改善版（After）は、あなたが書くものです。

---

## 準備

```bash
npm install
```

必要なのは TypeScript と `@types/node` だけです。DB もメールサーバも要りません
（`src/fake-libs/` に偽物が入っています）。

## 動かす

```bash
npm start
```

注文アプリが起動し、リクエストを7本流します。ログイン・注文・検索・注文参照・
レポート送信が実行され、その結果が標準出力に出ます。

**まず出力を最後まで読んでください。** これから直すコードが「何をしてしまうのか」が、
コードを1行も読まないうちに分かります。

```bash
npm run typecheck   # 型チェック（今は通ります。それが問題です）
npm run test:bad    # 第11章の「悪いテスト」を実行（9本中1本落ちます。それも教材です）
```

`npm run test:bad` が失敗して終わるのは**想定どおり**です。
落ちた1本と、通ってしまった8本のうち「実は何も守っていない」ものを探してください。

`lint` と `format` のスクリプトは**わざと用意していません**。
第12章 12-8「既存プロジェクトへの導入手順」を読みながら、自分で入れてみてください。

資料の該当箇所と並べて読めます。**After は載せていません。**

## 進め方

### A. 章ごとに練習する（`src/chapters/`）

資料の章を読む → 対応する `ch*.bad.ts` を開く → After を自分で書く → 資料の After と見比べる。

1ファイルが独立しているので、どこから始めても構いません。
第2章（命名）と第3章（関数分割）は、他のどの章より効果が大きく、リスクが小さい入口です。

### B. まとめて立ち向かう（`src/legacy-app/`）

こちらが本番です。**いきなり書き直さないでください。**

資料の**第17章 17-1「テストなしにリファクタリングしてはいけない」**と、
**第20章 20-1〜20-8 のステップ順**が、そのまま手順書になります。

```
20-1 名前を直す        → まだ構造は変えない
20-2 ネストを浅くする   → ガード節
20-3 計算とI/Oを分離   → ここが最大の転換点
20-4 テストを書く      → ★ 構造を変える前に、振る舞いを固定する
20-5 エラー処理を正す
20-6 責務を分割する
20-7 依存を逆転させる
20-8 配置を整える
```

> 資料の第20章末尾にはこう書かれています。
> **「この全ステップを一度にやってはいけません。20-4（テスト）まで進めれば、既に大きな成果です。」**

### 進捗の測り方

`npm start` の出力が、最初と同じままであること。
リファクタリングは**振る舞いを変えない**作業です。出力が変わったら、それはバグです。

## 見つけた問題をどう扱うか

このリポジトリには「欠陥の一覧」を置いていません。**それを作るところまでが演習だからです。**

`docs/coding-conventions.md` の以下が、そのまま採点基準として使えます。

- 第17章 17-2「コードの臭い（Code Smells）カタログ」
- 第19章 19-4「日々のチェックリスト」
- 第20章 20-0 の欠陥一覧（1つのコードに対して、章ごとに問題を数え上げた例）

見つけた問題は、資料の第13章 13-5 の書き方（人ではなくコードに向ける）で書き出してみてください。
