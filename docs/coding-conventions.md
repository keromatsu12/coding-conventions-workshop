# 保守できるコードの原則 — 命名からアーキテクチャ、テスト、運用まで

エンジニア初心者向けの体系的な学習資料。全5部・20章＋巻末資料（演習問題・用語集）。

### はじめに

ソフトウェアの寿命の大半は「書いた後」にあります。そして**世の中の案件は、新規開発よりも保守・改修が圧倒的に多い。**
多くのエンジニアが実際に向き合うのは、白紙のエディタではなく、**誰かが書いた、事情の分からない既存のコード**です。

そこで必要になるのは、ゼロから理想を作る力より、

- 既存コードを**読み解く**力
- どこまで直し、どこは触らないかを**判断する**力
- 壊さずに**変えていく**手順

です。この資料は、そのための共通言語として原則を扱います。
原則を知らないと「なぜこうなっているのか」が読めず、良かれと思った変更が事故になります。

一貫して扱うのは、**「変更が来たとき、すぐ直せて、直しても壊れないコード」＝保守できるコード**をどう作り、どう保ち、どう受け継ぐかです。

> **「AIが書いてくれる時代に、こんな知識は要らないのでは?」**
> — もっともな疑問です。結論だけ先に言えば、AIによって価値が下がったのは「書く速さ」であって、
> **「良し悪しを判断する力」の価値はむしろ上がっています。**詳しくは第1章 1-4で述べます。

**「なぜ学ぶのか」→「どう書くか（コード規約）」→「どう分けるか（設計）」→「どう保証するか（品質担保）」→「どう直すか（実践）」**
という流れで、**小さな単位（名前・関数）から大きな単位（アーキテクチャ・運用）へ、同じ原則が拡大していく**構成になっています。

第1章から順に読むことを想定していますが、各章は独立しても読めます。

## 第1章 なぜ設計するのか

### 1-1. 設計の目的はただ一つ「変更しやすさ」

コードが満たすべき要件は2つあります。

1. **動くこと**（機能要件）
2. **変更しやすいこと**（非機能要件）

初心者は1だけを目指しがちですが、ソフトウェアの寿命の大半は「書いた後」です。
書く時間より、読む・直す時間の方が圧倒的に長い。だから**読みやすさ＝変更しやすさ＝設計の良さ**になります。

> 「良い設計とは、変更のコストを下げる設計である」

```
 変更コスト
    ▲
    │                          ／ 設計を怠ったコード
    │                        ／   （触るたびに壊れる）
    │                     ／
    │                  ／
    │              ／
    │      ＿＿／＿＿＿＿＿＿＿＿＿＿＿ 設計されたコード
    │  ／‾
    │／  ← 初期は設計する方が少し高い
    └──────────────┴──────────────────────▶ 時間
                 逆転する点
     ほとんどのプロジェクトは、この点を必ず通過する。
```


### 1-2. 人間の脳のワーキングメモリは小さい

人が同時に把握できる情報は**4〜7個程度**と言われます。
だから設計の技法はすべて、**一度に考えることを減らす**ためにあります。

- 関数を分ける → 一度に読む行数を減らす
- モジュールを分ける → 一度に把握する概念を減らす
- レイヤを分ける → 一度に考える関心事を減らす

```
❌ 1つのかたまりに全部入っている
┌──────────────────────────────┐
│ 200行の関数                    │  頭に載せる情報 = 20個
│ 変数15個・分岐8個・I/O 5箇所    │  → ワーキングメモリから溢れる
└──────────────────────────────┘        😵

✅ 名前をつけて分割する
┌──────────┐  ┌──────────┐  ┌──────────┐
│ 検証する   │  │ 計算する  │  │ 保存する   │  頭に載せる情報 = 3個
└──────────┘  └──────────┘  └──────────┘  → 中身は「今は」見なくていい
                                                 🙂
```

**設計の技法 = 認知負荷を下げる技法** と覚えてください。

### 1-3. 唯一の万能ルールはない

原則は「守るべき法律」ではなく「判断のための道具」です。
過剰な抽象化・過剰な分割は、逆に読みにくくします（YAGNI違反）。

- ✅ 「この原則を適用すると、変更が楽になるか?」
- ❌ 「この原則に反しているから直さないと」

### 1-4. AI時代に、なぜこれを学ぶのか

**「AIがコードを書いてくれるのに、こんな古典的な知識を学ぶ意味があるのか?」**
正当な問いなので、正面から答えます。

#### ① ボトルネックは「書く」から「読む・判断する」へ移った

```
 【AI以前】
  書く      ████████████████
  読む・直す ████████████

 【AI以後】
  書く      ███                     ← ここは劇的に速くなった
  読む・判断・統合・保守 ████████████████████████  ← むしろ増えた ★

  生成量が増えるほど、
  「これは採用していいのか」を判断する仕事が増える。
```

コードを書く速度が10倍になっても、**レビューする速度・理解する速度・障害を追う速度は10倍になりません。**
結果として、開発全体の律速段階は「書く」から**「判断する」**へ移りました。
本資料が扱っているのは、まさにその判断のための知識です。

#### ② AIの出力を評価できなければ、AIを使いこなせない

```
   AIの提案 ──▶ ┌──────────────────────────┐
                │ これは採用していいか?       │
                │ ・責務が混ざっていないか     │
                │ ・依存の向きは正しいか       │
                │ ・異常系が抜けていないか     │
                │ ・この抽象化は過剰ではないか  │
                └──────────────────────────┘
                        │
        判断できる人 ────┴──── 判断できない人
             │                      │
      提案を取捨選択し           全部そのまま採用し
      設計を保てる               破綻に気づくのは数ヶ月後
```

AIは「もっともらしいコード」を非常に高い精度で出します。
**もっともらしさと正しさは別物です。**その差を見抜けるかどうかが、原則を知っているかどうかで決まります。

#### ③ 良い指示を出すには、設計の語彙が要る

```
 ❌ 語彙がない指示            ✅ 語彙がある指示
 「いい感じにリファクタして」    「この関数は検証・計算・保存の3責務があるので、
                              計算部分を純粋関数として抽出して。
                              Repositoryはインターフェースに切り出して注入する形に」
      ↓                            ↓
 曖昧な出力。何度も往復        意図通りの出力が一発で出る
```

**プロンプトは、設計判断そのものです。**
「SRPで分割して」「DIPで依存を逆転させて」と言えることは、AI時代における実用スキルになりました。
本資料の用語集（巻末）は、そのまま**AIへの指示語彙**として使えます。

#### ④ AIが最も力を発揮するのは、整ったコードベース

```
   汚いコードベース                 整ったコードベース
   ┌────────────────────┐        ┌────────────────────┐
   │ 依存が絡み合っている  │        │ 責務が分離している   │
   │ 文脈が巨大で渡せない  │        │ 該当箇所だけ渡せる   │
   │ テストがない         │        │ テストが検証してくれる│
   └────────────────────┘        └────────────────────┘
     AIも読み違える                  AIの精度が最大化する
     修正が他を壊す                  壊れたら即座に分かる
     結局人間が全部確認               安心して任せられる
```

**設計が良いほど、AIの生産性も上がります。**
「AIがあるから設計は不要」ではなく、**「AIを活かすために設計が要る」**という関係です。

#### ⑤ テストの価値は、むしろ上がった

```
   AIが書いたコードが正しいと、どうやって確認するか?

   ・目視レビュー   … 量が増えると追いつかない
   ・実行して確認   … 手動では再現性がない
   ・テスト        … 唯一、量に耐えられる自動検証 ★
```

生成量が増えるほど、**「壊れたら即座に分かる仕組み」（第Ⅳ部）の重要性は上がります。**
テストのないコードベースでAIに大量の変更を任せるのは、ブレーキのない車を加速させるのと同じです。

#### ⑥ 責任はAIに移せない

```
   障害が起きたとき、セキュリティ事故が起きたとき、
   顧客に説明するのは人間です。

   「AIがそう書いたので」は、いかなる場面でも通用しません。
```

**採用した時点で、そのコードは自分の書いたコードです。**
説明できないコードを本番に出さない——この原則は技術が変わっても変わりません。

#### ⑦ そもそも「古い知識」ではなく「変化の遅い知識」

```
   陳腐化の速さ

   速い ◀────────────────────────────────────────▶ 遅い

   特定のライブラリのAPI     フレームワーク    言語     設計原則
   （1〜2年で変わる）       （3〜5年）      （10年）  （50年ほぼ不変）
        ↑                                            ↑
   AIに任せてよい領域                      人間が学ぶ費用対効果が最も高い領域
```

凝集度・結合度が提唱されたのは1970年代です。
半世紀を経てもなお有効なのは、これらが**特定の技術ではなく「人間が複雑さをどう扱えるか」の話**だからです。
そして人間の認知能力（第1章 1-2）は、この数十年で変わっていません。

#### 正直に認めるべきこと

一方で、**AIによって本当に価値が下がった知識もあります。**

```
 ┌────────────────────────────┬────────────────────────────┐
 │ 価値が下がったもの            │ 価値が上がったもの            │
 ├────────────────────────────┼────────────────────────────┤
 │ 構文の暗記                   │ 設計判断・トレードオフの理解    │
 │ ボイラープレートを速く書く力    │ 出力をレビューする力           │
 │ 定型的な実装スピード           │ 要件を正しく定義する力          │
 │ 書式・スタイルの議論           │ テストと自動検証の設計         │
 │ APIリファレンスの記憶          │ 既存コードを読み解く力 ★       │
 └────────────────────────────┴────────────────────────────┘
```

**この資料が扱っているのは、すべて右側です。**

> ### AIは「書く」を代替しました。
> ### しかし「決める」「見抜く」「責任を持つ」は代替していません。
> ### 本資料は、その3つのための知識です。

# 第Ⅱ部 コード規約編 — 読みやすさをつくる

> **この部で答える問い：「どう書けば、他人（と未来の自分）が読めるコードになるのか?」**
>
> 扱うのは**目の前の1画面**のスケールです。
> 名前・コメント・関数の書き方という、今日から使える最も効果の高い領域を扱います。
>
> ここだけで、日々のコードの読みやすさは大きく変わります。

## 第2章 命名とコメント — コード規約の基本

コード規約と聞くと「インデントは2つ」「セミコロンを付ける」といった書式の話を想像しがちですが、
**規約の本体は「名前」と「コメント」です。**書式は機械が直せますが、この2つは人間にしか決められません。

```
   コード規約の3層

   ┌──────────────────────────────────────┐
   │ ③ 意図の伝達  … コメント・ドキュメント   │ 人間が判断
   ├──────────────────────────────────────┤
   │ ② 名前        … 変数・関数・クラス名     │ 人間が判断 ★本章の主役
   ├──────────────────────────────────────┤
   │ ① 書式        … インデント・改行・順序   │ 機械に任せる（第12章）
   └──────────────────────────────────────┘

   ①で消耗しないために自動化し、②③に頭を使う。
```

### 2-1. なぜ命名が最重要なのか

**名前は、最も安価で最も効果の高いドキュメントです。**

```
   コードを読む人の思考

   良い名前            悪い名前
   ┌──────────────┐    ┌──────────────┐
   │ elapsedSecs  │    │ d            │
   └──────┬───────┘    └──────┬───────┘
          │                   │
     「経過秒数か」        「dって何だ?」
          │                   │
          ▼                   ▼
     次の行へ進む         定義元へジャンプ
     （0.1秒）           前後を読む
                         型を確認する
                         使用箇所を追う
                         （30秒〜数分）★
```

名前を1つ改善するコストは数秒。読む人が払うコストは、**読まれる回数だけ**発生します。
コードは書かれる回数より読まれる回数が圧倒的に多い、というのはこの意味です。

### 2-2. 良い名前の6条件

#### ① 明確な単語を選ぶ

汎用的すぎる語は、情報を持ちません。

| 曖昧 | より明確 |
|---|---|
| `get` | `fetch`（ネットワーク越し）、`load`（ディスク）、`compute`（計算） |
| `size` | `height`, `numNodes`, `memoryBytes` |
| `stop` | `kill`（強制終了）、`pause`（再開可能） |
| `make` | `create`, `build`, `generate` |

```
  ❌ tmp, data, info, retval, flag, manager, handler, util
     → 「何が入っているか」を一切伝えない
     （tmpは本当に一時的な入れ替え用途のときだけ許される）
```

#### ② 抽象的でなく具体的に

```
❌ ServerCanStart()     … 「起動できる」の何を確認している?
✅ CanListenOnPort()    … ポートを掴めるかを確認していると分かる
```

#### ③ 名前に情報を追加する

**単位と状態は、名前に埋め込むと事故が消えます。**

```
  ❌ delay          →  ✅ delaySecs
  ❌ size           →  ✅ sizeMb
  ❌ limit          →  ✅ maxItems
  ❌ password       →  ✅ plaintextPassword    ← 平文だと一目で分かる
  ❌ html           →  ✅ unescapedHtml        ← エスケープ前だと分かる
```

```
   単位を書かないと起きること

   setTimeout(delay)      delay は秒? ミリ秒?
        │                      │
        └──────────────────────┴──▶ 1000倍のバグ（実際に多い）
```

#### ④ スコープに応じて長さを変える

```
   名前の長さ
      ▲
   長 │                          ┌──────────────────┐
      │                          │ 公開API・グローバル │
      │              ┌───────────┤ 誤解ゼロが最優先    │
      │              │ クラスの   └──────────────────┘
      │  ┌───────────┤ フィールド │
   短 │  │ ループ変数 │            │
      │  │ i, x      │            │
      └──┴───────────┴────────────┴──────────▶ スコープの広さ
         狭い                              広い

   3行しか生きない変数に長い名前は不要。
   逆に、100ファイルから参照される名前をケチってはいけない。
```

#### ⑤ 誤解されない名前にする

**「他の意味に読めないか?」を自問します。**

```
  filter(list, "year <= 2011")
    → 「選び出す」? 「取り除く」?  ← どちらにも読める
    → select() / exclude() のように動作を明示する

  範囲を表すとき
    first / last   … 閉区間 [first, last]  （lastを含む）
    begin / end    … 半開区間 [begin, end) （endを含まない）

  限界値を表すとき
    max_ / min_ を前に付ける（maxItems, minLength）
    ※ limit だけだと「以上」か「より大きい」か分からない
```

**boolean は特に誤解が起きやすい要注意領域です。**

```
❌ disableSsl = false    … 二重否定。「SSLを使う」のか一瞬迷う
✅ useSsl = true         … 肯定形で書く

   接頭辞：is / has / can / should / needs
   ✅ isActive, hasPermission, canEdit, shouldRetry
```

#### ⑥ 一貫性を保つ

```
❌ 同じ概念に違う語を使う          ✅ 用語を統一する
   fetchUser()                     fetchUser()
   getOrder()          ──────▶     fetchOrder()
   retrieveProduct()               fetchProduct()

   読者は「違う名前＝違う意味」だと解釈する。
   同義語の乱立は、存在しない差異を読者に想像させる。
```

**チームでは「用語集（ユビキタス言語）」を持つのが理想です。**
業務用語とコード上の名前を一致させると、仕様書とコードの往復が劇的に楽になります。

```
   業務側の言葉      コード上の名前
   ─────────────────────────────
   「注文」      →   Order      （Purchase や Transaction と混ぜない）
   「取消」      →   cancel     （delete や remove と区別する）
   「確定」      →   confirm
```

### 2-3. よくある命名のアンチパターン

| 悪い例 | 問題点 | 改善例 |
|---|---|---|
| `d`, `n`, `s` | 何の略か不明 | `elapsedDays`, `nodeCount` |
| `data`, `info` | 意味を持たない | 中身を表す具体名 |
| `flag` | 何のフラグか不明 | `isEnabled`, `hasExpired` |
| `temp`, `result` | 使い回されがち | 処理内容を表す名前 |
| `list1`, `list2` | 区別がつかない | `activeUsers`, `bannedUsers` |
| `XxxManager`, `XxxProcessor` | 責務が曖昧（＝設計が曖昧） | 実際の役割を表す名前 |
| `getUserData()` | Data が冗長 | `getUser()` |
| ローマ字（`chumon`） | 英語と混在して検索性が落ちる | `order` に統一 |

> **`Manager` / `Util` / `Helper` という名前が出てきたら、命名の問題ではなく設計の問題です。**
> 「何をするクラスか説明できない」から曖昧な名前になっています。第4章の凝集度の話に直結します。

### 2-4. コメント — 「何」ではなく「なぜ」を書く

#### コメントの原則

```
   ┌──────────────────────────────────────────────┐
   │ ❌ 書くべきでないコメント                       │
   ├──────────────────────────────────────────────┤
   │ ・コードを読めば分かること（i++ // iに1を足す）  │
   │ ・ひどい名前の言い訳                            │
   │   → コメントを足すのではなく、名前を直す ★      │
   │ ・更新されずに嘘になったコメント                 │
   ├──────────────────────────────────────────────┤
   │ ✅ 書くべきコメント                             │
   ├──────────────────────────────────────────────┤
   │ ・なぜこの実装にしたか（背景・意思決定）          │
   │ ・なぜ自明な方法を採らなかったか                 │
   │ ・落とし穴・注意点（「この順序は変えられない」）   │
   │ ・全体像の要約（読者の地図になる）               │
   │ ・TODO / FIXME（既知の欠陥の明示）              │
   └──────────────────────────────────────────────┘
```

```javascript
// ❌ 何をしているかを説明している（コードを見れば分かる）
// ユーザーIDでソートする
users.sort((a, b) => a.id - b.id);

// ✅ なぜそうしているかを説明している
// 外部APIがID昇順を前提にページングするため、ここで必ず整列させる
users.sort((a, b) => a.id - b.id);
```

#### 判断のフロー

```
   コメントを書きたくなった
            │
            ▼
   ┌─────────────────────────────┐
   │ 名前を変えれば不要にならないか? │──── なる ──▶ 名前を直す（コメント不要）
   └────────────┬────────────────┘
                │ ならない
                ▼
   ┌─────────────────────────────┐
   │ 関数に切り出せば不要にならないか?│──── なる ──▶ 切り出す（関数名が説明になる）
   └────────────┬────────────────┘
                │ ならない
                ▼
        「なぜ」を書く ＝ 本当に価値のあるコメント
```

> **原則：コメントで補う前に、コードそのものを直せないかを先に考える。**
> コメントは「コードで表現しきれなかった情報」を書く最後の手段です。

#### 記法を揃える

```
  TODO:  後でやる（期限や担当が分かると尚よい）
  FIXME: 既知の不具合。動くが正しくない
  HACK:  応急処置。あるべき姿ではないと明示
  NOTE:  読者への補足
  WARN:  触ると壊れる箇所の警告
```

これらは**リンターで検出・集計できます**（第12章）。「TODOを放置しない仕組み」まで含めて規約です。

### 2-5. チームで規約を運用する

#### 規約の目的は「統一」であって「正しさ」ではない

```
   ❌ よくある不毛な議論
      「シングルクォート派 vs ダブルクォート派」
      「if文の波括弧は省略すべきか」
        → どちらでも品質は変わらない。決めれば済む話

   ✅ 規約の本当の価値
      ・どのファイルを開いても同じ形 ＝ 読む速度が上がる
      ・レビューで書式の指摘が消える ＝ 設計の議論に時間を使える
      ・新メンバーが迷わない
```

```
   規約なし                          規約あり
   ┌────────────────────┐          ┌────────────────────┐
   │ レビュー時間の内訳    │          │ レビュー時間の内訳    │
   │ ████████ 書式の指摘  │          │ █ 書式（自動化済み）  │
   │ ███ 命名の指摘       │  ──────▶ │ ███ 命名の指摘       │
   │ ██ 設計の議論 ←少ない │          │ ████████ 設計の議論   │
   └────────────────────┘          └────────────────────┘
```

#### 決め方の指針

1. **既存の有名なスタイルガイドを採用する**（Google, Airbnb, PEP 8, Effective Go 等）
   ゼロから作らない。議論のコストが最も安い
2. **迷ったら言語の標準・多数派に従う**（Goなら`gofmt`、Pythonなら PEP 8）
3. **書式は機械に強制させる**（第12章のフォーマッター・リンター）
4. **例外を認めるときは、理由をコードに残す**（`// eslint-disable-next-line` + 理由）

#### 規約は「守れる量」にする

```
   ❌ 100ページの規約ドキュメント
      → 誰も読まない → 守られない → 形骸化

   ✅ 「ツールで自動チェックされるルール」＋「A4一枚の判断指針」
      → 機械が守るので、人は忘れてよい
```

## 第3章 関数の分割基準

### 3-1. 大原則：関数は「1つのこと」だけをする

「1つのこと」の判定方法は3つあります。

#### 判定法① 説明に「そして(and)」が入るか

```
「ユーザーを検証して、DBに保存して、メールを送る」
                ↑and    ↑and
→ 3つの関数に分けるサイン
```

関数名が `validateAndSaveUser` のように `And` を含むなら、ほぼ確実に分割対象です。

#### 判定法② 抽象レベルが混在していないか

**同じ関数の中に、抽象度の違う処理が混ざっていないか。**

```javascript
// ❌ 悪い例：抽象度がバラバラ
function processOrder(order) {
  validateOrder(order);              // 高レベル（何をするか）
  const total = order.items          // 低レベル（どうやるか）
    .reduce((s, i) => s + i.price * i.qty, 0);
  const tax = Math.floor(total * 0.1);
  saveToDatabase(order, total + tax); // 高レベル
}

// ✅ 良い例：抽象度が揃っている
function processOrder(order) {
  validateOrder(order);
  const total = calculateTotalWithTax(order);
  saveToDatabase(order, total);
}

function calculateTotalWithTax(order) {
  const subtotal = calculateSubtotal(order);
  return subtotal + calculateTax(subtotal);
}
```

```
❌ 抽象レベルが混在（読者が上下に振り回される）
  高 │ validateOrder(order)          ← 「何を」
     │        ↓ ガクッと下がる
  低 │ order.items.reduce(...)       ← 「どうやって」
     │ Math.floor(total * 0.1)       ← 「どうやって」
     │        ↑ ガクッと上がる
  高 │ saveToDatabase(...)           ← 「何を」

✅ 抽象レベルが揃っている（同じ高さの言葉が並ぶ）
  高 │ validateOrder(order)
     │ calculateTotalWithTax(order)   ← 全部「何を」の粒度
     │ saveToDatabase(order, total)
     └──────────────────────────────
       ↓ 一段下がると、その中は「どうやって」で揃っている
  低 │ calculateSubtotal / calculateTax
```

これを**「抽象レベルを一段階だけ下げる原則」(SLAP)** と言います。
関数の中身を読んだとき、**同じ粒度の言葉が並んでいる**のが理想です。

#### 判定法③ 「無関係の下位問題」を抽出できるか

リーダブルコードの重要な考え方です。

```javascript
// ❌ 本題（近い店を探す）に、汎用処理（距離計算）が混ざっている
function findClosestLocation(lat, lng, locations) {
  let closest = null;
  let closestDist = Infinity;
  for (const loc of locations) {
    // ↓ここは「球面上の2点間距離」という汎用的な問題
    const latRad = toRadian(lat);
    const lngRad = toRadian(lng);
    const dist = Math.acos(
      Math.sin(latRad) * Math.sin(toRadian(loc.lat)) + ...
    );
    if (dist < closestDist) { closest = loc; closestDist = dist; }
  }
  return closest;
}

// ✅ 汎用処理を切り出す
function findClosestLocation(lat, lng, locations) {
  return locations.reduce((closest, loc) =>
    sphericalDistance(lat, lng, loc.lat, loc.lng) <
    sphericalDistance(lat, lng, closest.lat, closest.lng)
      ? loc : closest
  );
}

function sphericalDistance(lat1, lng1, lat2, lng2) { /* ... */ }
```

切り出した `sphericalDistance` は**単独でテストでき、再利用でき、名前がドキュメントになる**という3つの利得があります。

#### 分割のイメージ

```
【分割前】1つの箱に手順が直書き      【分割後】目次と中身に分かれる
┌────────────────────┐            ┌──────────────────┐
│ processOrder       │            │  processOrder    │ ← 目次（何をするか）
│  ・入力チェック      │            └───┬────┬─────┬───┘
│  ・小計を合計       │   ──────▶       │    │     │
│  ・消費税を計算      │            ┌────▼─┐┌─▼───┐┌▼──────┐
│  ・DBへINSERT      │            │ 検証 ││ 計算 ││ 保存   │ ← 中身（どうやるか）
└────────────────────┘            └──────┘└─────┘└───────┘
  全部読まないと分からない            名前を読むだけで流れが分かる
                                     各部品は単独でテストできる
```

### 3-2. 具体的な分割サイン（チェックリスト）

| サイン | 意味 | 対処 |
|---|---|---|
| 関数が画面に収まらない | 責任過多 | 処理のまとまりごとに抽出 |
| ネストが3段以上 | 制御フローが複雑 | 早期リターン、ループ内処理の関数化 |
| 引数が4個以上 | 責任過多、または引数のまとまりがある | オブジェクトにまとめる／分割 |
| boolean引数がある | 中で処理が2分岐している | 2つの関数に分ける |
| 「ここから〜の処理」というコメント | そのブロックが関数の候補 | コメント部分を関数に抽出、コメントを関数名に |
| 一部だけコメントアウトして試したくなる | 責任が分かれている | 分割 |

#### boolean引数を避ける例

```javascript
// ❌ 呼び出し側で意味が読めない
createUser(name, email, true);

// ✅ 意図が明確
createAdminUser(name, email);
createNormalUser(name, email);
```

### 3-3. ネストを浅くする技法

#### 早期リターン（ガード節）

```javascript
// ❌ ネストが深い
function getDiscount(user) {
  if (user != null) {
    if (user.isActive) {
      if (user.membershipYears >= 3) {
        return 0.2;
      } else {
        return 0.1;
      }
    } else {
      return 0;
    }
  } else {
    return 0;
  }
}

// ✅ 早期リターンで「例外的なケース」を先に片付ける
function getDiscount(user) {
  if (user == null) return 0;
  if (!user.isActive) return 0;
  if (user.membershipYears >= 3) return 0.2;
  return 0.1;
}
```

**ポイント**：正常系のロジックを、ネストの一番浅いところに置く。読者は「本筋」だけを追える。

```
❌ 矢印（三角形）コード              ✅ フラットな構造
if (…) {                           if (異常1) return 0;   ← 例外を先に片付ける
  if (…) {                         if (異常2) return 0;
    if (…) {                       if (異常3) return 0;
      ★本筋★     ← 一番深い所       ★本筋★               ← 一番浅い所
    } else { … }
  } else { … }                     読者は上から順に読むだけ
} else { … }
   └─ 本筋にたどり着くまでに
      3つの条件を頭に保持する必要
```


### 3-4. 副作用を分離する

```javascript
// ❌ 計算とI/Oが混在 → テストしづらい
function reportSalary(employeeId) {
  const emp = db.find(employeeId);        // I/O
  const salary = emp.base + emp.bonus;    // 計算
  console.log(`${emp.name}: ${salary}`);  // I/O
}

// ✅ 計算部分を純粋関数に
function calculateSalary(employee) {      // 純粋関数：テストが超簡単
  return employee.base + employee.bonus;
}

function reportSalary(employeeId) {       // I/Oはここに集約
  const emp = db.find(employeeId);
  console.log(`${emp.name}: ${calculateSalary(emp)}`);
}
```

```
❌ 計算とI/Oが絡み合っている        ✅ 外側にI/O、内側に計算
┌───────────────────────┐        ┌─────────────────────────┐
│ reportSalary          │        │ reportSalary（外殻）     │
│  ┌─────┐              │        │  ┌───────────────────┐  │
│  │ DB  │              │        │  │ calculateSalary   │  │
│  │ 計算 │ ← ここだけ    │        │  │  （純粋な計算）    │  │
│  │ 出力 │   テストしたい │        │  └───────────────────┘  │
│  └─────┘              │        │  DB / 出力はこの層だけ    │
└───────────────────────┘        └─────────────────────────┘
 テストにDBと標準出力が必要         計算部分は引数と戻り値だけでテスト可能
```

**原則：判断（計算）と実行（副作用）を分ける。**
これは後の第8章で「ドメイン層とインフラ層を分ける」という形で再登場します。

## 第4章 凝集度と結合度

第3章は「関数の中身」の話でした。ここからは**「関数・モジュール同士の関係」**の話です。

> **目標：凝集度は高く（High Cohesion）、結合度は低く（Low Coupling）**

これは設計における最重要の指針のひとつです。

### 4-1. 凝集度（Cohesion）＝ モジュール内部のまとまりの良さ

「このモジュールの中の要素は、どれくらい互いに関係しているか」

#### 凝集度のレベル（低い→高い）

| レベル | 名前 | 説明 | 例 |
|---|---|---|---|
| 1（最悪） | 偶発的凝集 | 関係ないものの寄せ集め | `Utils.js`, `Common.js`, `Helper.js` |
| 2 | 論理的凝集 | 種類が似てるだけ | 「全ての入力処理」を1クラスに |
| 3 | 時間的凝集 | 同じタイミングで実行されるだけ | `initialize()` に無関係な初期化を全部 |
| 4 | 手続き的凝集 | 決まった順序で実行される | |
| 5 | 通信的凝集 | 同じデータを扱う | |
| 6 | 逐次的凝集 | 前の出力が次の入力 | |
| **7（最良）** | **機能的凝集** | **すべてが単一の目的に貢献** | `PriceCalculator` |

#### 実例で見る

```javascript
// ❌ 偶発的凝集（レベル1）：何でも入る神クラス
class Utils {
  formatDate() {}
  calculateTax() {}
  sendEmail() {}
  validatePassword() {}
}
// → 「Utilsを直したら関係ないところが壊れた」が起きる

// ✅ 機能的凝集（レベル7）
class DateFormatter { format() {} }
class TaxCalculator { calculate() {} }
class EmailSender { send() {} }
```

```
❌ 偶発的凝集（Utils）              ✅ 機能的凝集
┌──────────────────────┐          ┌──────────┐ ┌──────────┐
│ Utils                │          │DateFormat│ │TaxCalc   │
│  ・日付整形           │          └──────────┘ └──────────┘
│  ・税計算            │  ──────▶ ┌──────────┐ ┌──────────┐
│  ・メール送信         │          │EmailSender│ │PwValidator│
│  ・パスワード検証      │          └──────────┘ └──────────┘
└──────────────────────┘
  中身に関連がない                  それぞれが名前で説明できる
  ＝ 全モジュールから依存される      ＝ 必要なものだけ依存すればいい
```

**判定のコツ**：「このモジュールを一言で説明できるか?」
説明に「〜と〜と〜」が必要なら凝集度が低い。

### 4-2. 結合度（Coupling）＝ モジュール同士の依存の強さ

「Aを変更したとき、Bも変更しなければならない度合い」

#### 結合度のレベル（強い＝悪い→弱い＝良い）

| レベル | 名前 | 説明 |
|---|---|---|
| 1（最悪） | 内容結合 | 他モジュールの内部を直接いじる |
| 2 | 共通結合 | グローバル変数を共有 |
| 3 | 外部結合 | 外部データ形式に依存 |
| 4 | 制御結合 | フラグ引数で相手の動作を制御 |
| 5 | スタンプ結合 | 必要以上に大きいデータを渡す |
| **6（最良）** | **データ結合** | **必要最小限のデータだけ渡す** |

```javascript
// ❌ スタンプ結合：巨大なuserオブジェクト全体を渡している
function canDrink(user) {
  return user.age >= 20;
}

// ✅ データ結合：必要なものだけ
function canDrink(age) {
  return age >= 20;
}
```

#### 結合を弱くする代表的な手段

1. **インターフェース（抽象）に依存する** → 第5章 DIP
2. **引数を最小限にする**
3. **グローバル変数・シングルトンを避ける**
4. **公開範囲を絞る**（private / エクスポートしない）
5. **イベント/メッセージで疎結合にする**

### 4-3. なぜこの2つが重要か

```
凝集度が低い → 1つの変更が複数箇所に散らばる（探すのが大変）
結合度が高い → 1つの変更が他に波及する（壊れる範囲が読めない）
```

#### 変更が来たときの違い

```
【低凝集・高結合】                  【高凝集・低結合】
   ●=修正が必要になった箇所

  ┌───┐   ┌───┐   ┌───┐          ┌───┐   ┌───┐   ┌───┐
  │ A●│──▶│ B●│──▶│ C●│          │ A●│   │ B │   │ C │
  └─┬─┘   └─┬─┘   └───┘          └───┘   └───┘   └───┘
    │       │                      修正は1箇所で完結
    └───────┴────▶ ┌───┐          影響範囲が読める
                   │ D●│          テストも1箇所で済む
                   └───┘
  1つの変更が芋づる式に波及
  「どこまで壊れたか分からない」
```

#### 2軸で見る4象限

```
              凝集度 高（まとまっている）
                       ▲
   ┌───────────────────┼───────────────────┐
   │ △ 分割しすぎ        │ ◎ 理想             │
結 │ 部品は綺麗だが      │ 変更が局所化し      │ 結
合 │ 連携が追えない      │ 影響範囲が読める    │ 合
度 ├───────────────────┼───────────────────┤ 度
高 │ × 最悪（泥団子）    │ △ 部品はいいが      │ 低
   │ Utils＋グローバル変数│ 繋ぎ方が雑          │
   └───────────────────┼───────────────────┘
                       ▼
              凝集度 低（バラバラ）
```

**「関係するものは近くに、関係しないものは遠くに」** — これが凝集度と結合度の本質です。

#### 例1：偶発的凝集（Utilsクラス）

## 第5章 SOLID原則

オブジェクト指向設計の5大原則。**第4章の「高凝集・低結合」を、具体的な手順に落とし込んだもの**と理解してください。

### 5-1. S — 単一責任の原則（SRP: Single Responsibility Principle）

> **クラスが変更される理由は、1つだけであるべき**

「1つのことをする」ではなく、**「1人のアクター（変更を要求する人）に対して責任を持つ」**が正確な定義です。

```javascript
// ❌ 3人の異なる関係者が変更を要求しうる
class Employee {
  calculatePay() {}    // 経理部門が仕様変更
  reportHours() {}     // 人事部門が仕様変更
  save() {}            // DB管理者が仕様変更
}
// → 経理の都合で直したら人事の機能が壊れる、が起きる

// ✅ 変更理由ごとに分離
class PayCalculator { calculate(employee) {} }
class HourReporter { report(employee) {} }
class EmployeeRepository { save(employee) {} }
```

```
❌ 1クラスに3人の「変更を要求する人」    ✅ 1対1に整理する

  経理部門 ──┐                          経理部門 ──▶ PayCalculator
            │                          
  人事部門 ──┼──▶ ┌──────────┐          人事部門 ──▶ HourReporter
            │    │ Employee │          
  DB管理者 ──┘    └──────────┘          DB管理者 ──▶ EmployeeRepository

  経理の都合で直す                       変更要求と変更箇所が1対1
   → 人事の機能が壊れる                  → 他部門に影響しない
```

**見分け方**：「この変更を要求してくるのは誰か?」を考える。相手が違えばクラスも分ける。

### 5-2. O — 開放閉鎖の原則（OCP: Open-Closed Principle）

> **拡張に対して開いていて、修正に対して閉じているべき**

**新機能を追加するとき、既存コードを触らずに済む設計にする。**

```javascript
// ❌ 決済手段が増えるたびに、この関数を修正する必要がある
function processPayment(type, amount) {
  if (type === 'credit') { /* ... */ }
  else if (type === 'paypal') { /* ... */ }
  else if (type === 'bank') { /* ... */ }
  // PayPay対応 → ここを修正 → 既存機能を壊すリスク
}

// ✅ 新しい決済手段は「追加」だけで済む
class CreditCardPayment { pay(amount) { /* ... */ } }
class PayPalPayment    { pay(amount) { /* ... */ } }
class PayPayPayment    { pay(amount) { /* ... */ } }  // 追加するだけ

function processPayment(paymentMethod, amount) {
  paymentMethod.pay(amount);  // ここは二度と修正しない
}
```

```
❌ 修正して対応（Closedでない）      ✅ 追加して対応（Open）
┌──────────────────────┐          ┌────────────────────┐
│ processPayment       │          │ processPayment     │ ← 二度と触らない
│   if credit  …       │          └─────────┬──────────┘
│   if paypal  …       │                    │ 抽象に依存
│   if bank    …       │          ┌─────────▼──────────┐
│   if paypay  … ←追記 │          │ PaymentMethod（抽象）│
└──────────────────────┘          └──▲───▲───▲───▲─────┘
  既存コードを毎回書き換える           │   │   │   │
  → 既存機能を壊すリスク            Credit PayPal Bank PayPay
                                                    ↑ 追加するだけ
```

**注意**：最初から全部OCPにしようとしないこと（YAGNI）。
**「2回目に同じ種類の変更が来たとき」に抽象化する**のが実践的です。

### 5-3. L — リスコフの置換原則（LSP: Liskov Substitution Principle）

> **親クラスを子クラスに置き換えても、正しく動作すべき**

```javascript
// ❌ LSP違反の古典例
class Rectangle {
  setWidth(w) { this.width = w; }
  setHeight(h) { this.height = h; }
  area() { return this.width * this.height; }
}

class Square extends Rectangle {
  setWidth(w)  { this.width = w; this.height = w; }  // 勝手に高さも変える
  setHeight(h) { this.width = h; this.height = h; }
}

// 利用側のコード
function test(rect) {
  rect.setWidth(5);
  rect.setHeight(4);
  assert(rect.area() === 20);  // Squareを渡すと16になり破綻
}
```

```
利用側は「親の型」だけを見て書かれている

        ┌────────────────┐
        │ 利用コード       │   「幅と高さは独立に設定できる」
        │ setWidth(5)     │    という前提でコードを書いている
        │ setHeight(4)    │
        │ area()===20 ?   │
        └────────┬───────┘
                 │ 使う
        ┌────────▼───────┐
        │  Rectangle     │
        └────────△───────┘
                 │ 継承
        ┌────────┴───────┐
        │  Square        │ ← 差し込むと前提が崩れる（area()が16）
        └────────────────┘

   ＝ 利用側に「もしSquareなら…」というif文が必要になる ＝ LSP違反
```

**実践的な指針**：
- 継承は「is-a関係」が成立するときだけ使う
- 子クラスで例外を投げたり、何もしないメソッドを作ったら黄信号
- **迷ったら継承より委譲（コンポジション）を使う**

### 5-4. I — インターフェース分離の原則（ISP: Interface Segregation Principle）

> **使わないメソッドへの依存を強制してはいけない**

```javascript
// ❌ 巨大インターフェース
interface Worker {
  work();
  eat();
  sleep();
}
class Robot implements Worker {
  work() { /* ... */ }
  eat()  { throw new Error("ロボットは食べない"); }  // 不要な実装を強制
  sleep(){ throw new Error("ロボットは寝ない"); }
}

// ✅ 小さく分割
interface Workable { work(); }
interface Eatable  { eat(); }

class Robot implements Workable { work() {} }
class Human implements Workable, Eatable { work() {} eat() {} }
```

```
❌ 巨大な1つのインターフェース        ✅ 小さく分割
                                    
Robot ──┐   ┌──────────────┐        Robot ──▶ ┌───────────┐
        ├──▶│ Worker       │                  │ Workable  │◀── Human
Human ──┘   │  work()      │                  └───────────┘      │
            │  eat()  ←不要 │                  ┌───────────┐      │
            │  sleep()←不要 │                  │ Eatable   │◀─────┘
            └──────────────┘                  └───────────┘

 Robotは使わないメソッドの                 それぞれ必要なものだけを
 実装を強制される（例外を投げる）           実装すればよい
```

**SRPの「インターフェース版」**と考えるとわかりやすいです。

### 5-5. D — 依存関係逆転の原則（DIP: Dependency Inversion Principle）

**5つの中で最重要。第7章のパッケージ設計と第8章のアーキテクチャは、全部これを実現するための形です。**

> **上位モジュールは下位モジュールに依存してはならない。両者とも抽象に依存すべき**

```javascript
// ❌ ビジネスロジックがMySQLに依存している
class OrderService {
  constructor() {
    this.db = new MySQLDatabase();  // 具体に直接依存
  }
  createOrder(order) {
    this.db.insert(order);
  }
}
// → DBをPostgreSQLに変えたら、ビジネスロジックを書き換える羽目に
// → テストのたびに本物のMySQLが必要

// ✅ 抽象（インターフェース）に依存させる
interface OrderRepository {
  save(order);
}

class OrderService {
  constructor(repository) {   // 外から注入される（DI）
    this.repository = repository;
  }
  createOrder(order) {
    this.repository.save(order);
  }
}

class MySQLOrderRepository implements OrderRepository { save(order) {} }
class InMemoryOrderRepository implements OrderRepository { save(order) {} } // テスト用
```

#### 「逆転」とは何が逆転しているのか

```
【従来】 業務ロジック ───依存──▶ DB実装
         （重要）              （詳細）
         重要なものが、詳細に振り回される

【DIP】  業務ロジック ──▶ 【Repositoryインターフェース】 ◀──実装── DB実装
         （重要）           （業務ロジック側が所有）        （詳細）
         依存の矢印が逆向きになった ＝「逆転」
```

**ポイント：インターフェースは「使う側（業務ロジック側）」が定義する。**
これを理解すると、第8章のアーキテクチャ図がすべて腑に落ちます。

### 5-6. SOLIDまとめ

| 原則 | 一言で | 効果 |
|---|---|---|
| SRP | 変更理由は1つ | 凝集度↑ |
| OCP | 追加で拡張、修正しない | 変更の波及↓ |
| LSP | 置き換えても壊れない | 継承の安全性 |
| ISP | 使わないものに依存しない | 結合度↓ |
| DIP | 具体でなく抽象に依存 | 結合度↓↓、テスト容易性↑ |

#### 5原則の関係

```
      SRP  ─────┐
   （責務で分ける）│
                 ├──▶ 分割の結果、境界＝インターフェースが生まれる
      ISP  ─────┘                    │
   （IFを分ける）                      ▼
                            ┌──────────────────┐
      OCP ─────────────────▶│  DIP             │
   （追加で拡張できる形に）     │ 抽象に依存する     │← 5つの結節点
                            └────────┬─────────┘
      LSP ───────────────────────────┘
   （差し替えても壊れないことを保証）

   SRP・ISP で「分け」、OCP で「差し替え可能にし」、
   LSP で「差し替えの安全を保証」し、DIP で「向きを正す」。
```

#### 例2：OCP — 判定の追加で既存コードを触らない

```javascript
// ❌ Before：通知手段が増えるたびにswitchを編集
function notify(user, type) {
  switch (type) {
    case 'email': sendEmail(user); break;
    case 'sms':   sendSms(user); break;
    case 'push':  sendPush(user); break;
    // LINE対応 → ここを修正 → 既存の3経路を壊すリスク
  }

// ✅ After：チャネルを部品として登録するだけ
const channels = [emailChannel, smsChannel, pushChannel, lineChannel];

      .filter(c => c.isEnabledFor(user))

#### 例3：LSP — 継承ではなく委譲にする

```javascript
// ❌ Before：Stackは配列ではないのに配列を継承
class Stack extends Array {
  push(v) { super.push(v); }
  pop()   { return super.pop(); }
}
const s = new Stack();
s[0] = 'x';          // 配列としての操作ができてしまい、不変条件が壊れる
s.splice(0, 1);      // Stackとして意味をなさない操作

// ✅ After：内部に持つ（委譲）
class Stack {
  #items = [];
  push(v) { this.#items.push(v); }
  pop()   { return this.#items.pop(); }
  get size() { return this.#items.length; }
}
```

#### 例4：ISP — 使わないメソッドを強制しない

```typescript
// ❌ Before
interface Storage {
  read(key: string): string;
  write(key: string, value: string): void;
  delete(key: string): void;
  listAll(): string[];
}
class ReadOnlyConfig implements Storage {
  read(k) { return this.data[k]; }
  write() { throw new Error('読み取り専用です'); }   // ★実装できない
  delete() { throw new Error('読み取り専用です'); }

}

// ✅ After：役割ごとに分割
interface Readable { read(key: string): string; }
interface Writable { write(key: string, value: string): void; }

class ReadOnlyConfig implements Readable { read(k) { return this.data[k]; } }
class FileStorage implements Readable, Writable { /* ... */ }
```

#### 例5：DIP — 具体クラスの new をやめる

```javascript

    client.post('#alerts', message);
  }
}

// ✅ After：抽象に依存し、外から注入する

new AlertService(new SlackNotifier(token));   // 本番
new AlertService(new InMemoryNotifier());     // テスト
```

#### 例6：4つの原則が同時に効く例

```javascript
// ❌ Before：料金計算が全部入りのif地獄
function calculatePrice(user, items, campaign) {
  let price = items.reduce((s, i) => s + i.price, 0);
  if (user.isMember) price *= 0.9;
  if (user.years >= 3) price *= 0.95;
  if (campaign === 'summer') price -= 500;
  if (campaign === 'newyear') price *= 0.8;
  if (price < 0) price = 0;
  return price;
}

// ✅ After：ルールを部品化（OCP）、判定は各部品の責務（SRP）、
//           共通の形を型で保証（LSP/ISP）
const rules = [
  new MemberDiscount(),
  new LoyaltyDiscount(),
  new CampaignDiscount(campaign),
];

function calculatePrice(user, items) {
  const subtotal = items.reduce((s, i) => s + i.price, 0);
  const total = rules.reduce((price, rule) => rule.apply(price, user), subtotal);
  return Math.max(0, total);
}
```

## 第6章 依存関係の考え方

SOLIDのDIPを、実装レベルで理解する章です。

### 6-1. 依存とは「知っている」ということ

`A が B に依存する` ＝ `A のコード内に B の名前が登場する`

依存があると：
- Bが変わればAも影響を受ける
- AをテストするにはBが必要
- AだけをコピーしてもBがないと動かない

### 6-2. 依存の向きの原則

> **依存の矢印は、変わりにくいものへ向ける**

```
変わりやすい ←─────────────────→ 変わりにくい
UI/フレームワーク   DB   ユースケース   ビジネスルール

依存の矢印はこの向き：
  UI ──▶ ユースケース ──▶ ビジネスルール
  DB ──▶ ユースケース（DIPで逆転させる）
```

```
❌ 重要なものが、変わりやすいものに依存している

  ┌──────────────┐  依存   ┌────────────────┐
  │ ビジネスルール │ ──────▶ │ フレームワーク   │
  │  （不変）     │         │ （年1回大改修）  │
  └──────────────┘         └────────────────┘
        ↑ 毎回巻き込まれて書き換えになる

✅ 依存の向きを正す

  ┌────────────────┐  依存   ┌──────────────┐
  │ フレームワーク   │ ──────▶ │ ビジネスルール │
  │ （変わりやすい） │         │  （安定）     │
  └────────────────┘         └──────────────┘
        フレームワークを乗り換えても、業務ロジックは無傷
```

**理由**：変わりやすいものに依存すると、頻繁に巻き込まれるからです。
ビジネスルール（「送料は5000円以上で無料」など）は、DBやフレームワークが何であっても不変です。

### 6-3. 依存性注入（DI: Dependency Injection）

DIPを実現する具体的な手段。**依存するオブジェクトを自分で作らず、外から受け取る。**

```javascript
// ❌ 自分で作る（依存を自分で決めてしまう）
class NotificationService {
  constructor() {
    this.sender = new EmailSender();  // Emailに固定される
  }
}

// ✅ 外から受け取る（Constructor Injection）
class NotificationService {
  constructor(sender) {
    this.sender = sender;
  }
}

// 使う側で組み立てる
const service = new NotificationService(new EmailSender());
const testService = new NotificationService(new MockSender()); // テストが楽
```

```
❌ 自分で依存を作る                ✅ 外から注入する（DI）

┌────────────────────┐          ┌──────────────┐
│ NotificationService│          │  main / DIコンテナ │ ← ここだけが
│  new EmailSender() │          └───────┬──────┘    「誰と誰を繋ぐか」
└────────────────────┘             生成 │ 注入        を知っている
  Email送信に固定される           ┌──────▼─────────────┐
  差し替え不可                    │ NotificationService │ ← 相手を知らない
  テストで本物のメールが飛ぶ        └──────────┬──────────┘
                                              │ 使うだけ
                                    ┌─────────▼─────────┐
                                    │  Sender（抽象）     │
                                    └───▲───────────▲───┘
                                        │           │
                                  EmailSender   MockSender
                                    （本番）      （テスト）
```

#### DIの恩恵

1. **テストが書ける**（本物のDBやAPIなしでテストできる）
2. **差し替えが効く**（Email→Slack通知に変更が容易）
3. **依存関係が明示される**（コンストラクタを見れば何に依存しているか一目瞭然）

## 第7章 パッケージ設計

第6章までは「1つのクラス・関数の中や、その周辺」の話でした。
本章はその**間**にあるステップです。ここを飛ばすと、第8章のアーキテクチャが「なぜ層に分けるのか」ではなく「そういう決まりだから」になってしまいます。

> **パッケージ = クラスをまとめた箱。ディレクトリ・モジュール・名前空間とほぼ同義。**

言語によって呼び方が違います。

| 言語 | 呼び方 |
|---|---|
| Java / Kotlin | パッケージ |
| Go | パッケージ |
| Python | パッケージ / モジュール |
| TypeScript / JavaScript | モジュール、ディレクトリ |
| C# | 名前空間 / アセンブリ |

本章では総称して「パッケージ」と呼びます。

### 7-1. パッケージは3つの単位である

パッケージを「ただのフォルダ」だと思っていると、分け方の基準が持てません。
パッケージは次の3つの単位です。

1. **理解の単位** — 「認証まわりを見たい」と思ったら `auth/` を開けば済む
2. **変更の単位** — 1つの仕様変更で触るファイルが、1つのパッケージに収まっているのが理想
3. **公開・隠蔽の単位** — 外に見せるものと、中だけで使うものを区別する

この3つ目が特に重要です。**パッケージの本質は「隠すこと」**にあります。

```
order/
├── index.ts          ← 外に公開するものだけを列挙（公開API）
├── OrderService.ts   ← 公開
├── Order.ts          ← 公開
├── PriceTable.ts     ← 内部専用（外から直接importさせない）
└── taxUtil.ts        ← 内部専用
```

```typescript
// order/index.ts — このパッケージの「窓口」
export { OrderService } from './OrderService';
export { Order } from './Order';
// PriceTable, taxUtil はexportしない = 外から見えない

// 使う側
import { OrderService } from '../order';        // ✅ 窓口経由
import { taxUtil } from '../order/taxUtil';     // ❌ 内部に手を突っ込んでいる
```

```
      パッケージ ＝ 「窓口だけを外に出した箱」

           外から見える範囲
        ┌─────────────────┐
        │  OrderService   │ ← 公開（index経由）
        │  Order          │ ← 公開
        └────────┬────────┘
   ─ ─ ─ ─ ─ ─ ─│─ ─ ─ ─ ─ ─ ─  パッケージ境界
        ┌────────▼────────┐
        │  PriceTable     │ ← 非公開（自由に変えられる）
        │  taxUtil        │ ← 非公開（自由に変えられる）
        └─────────────────┘

   公開したものは「約束」になる ＝ 気軽に変えられなくなる
   だから公開は最小限に。
```

**外に公開するものが少ないほど、そのパッケージは自由に作り替えられます。**
これが第4章の「結合度を下げる」を、パッケージのスケールでやるということです。

### 7-2. 分け方の2大方針：技術で分けるか、機能で分けるか

パッケージ分割の最初の分岐点にして、最も重要な選択です。

#### ① レイヤで分ける（Package by Layer）

```
src/
├── controllers/
│   ├── UserController.ts
│   ├── OrderController.ts
│   └── ProductController.ts
├── services/
│   ├── UserService.ts
│   ├── OrderService.ts
│   └── ProductService.ts
├── repositories/
│   ├── UserRepository.ts
│   ├── OrderRepository.ts
│   └── ProductRepository.ts
└── models/
    ├── User.ts
    ├── Order.ts
    └── Product.ts
```

**「役割が同じもの」をまとめる。**フレームワークのチュートリアルでよく見る形です。

| ✅ 利点 | ❌ 欠点 |
|---|---|
| 初心者が置き場所に迷わない | **1つの機能追加で全ディレクトリを触る** |
| 技術的な統一が図りやすい | 機能間の境界が見えない |
| 小規模なら十分機能する | 規模が大きくなると1ディレクトリが肥大化 |

**致命的な問題はこれです。**

```
「注文にクーポン機能を追加して」
→ controllers/ と services/ と repositories/ と models/ を全部開く
→ 4ディレクトリに変更が散らばる ＝ 凝集度が低い
```

#### ② 機能で分ける（Package by Feature）

```
src/
├── user/
│   ├── UserController.ts
│   ├── UserService.ts
│   ├── UserRepository.ts
│   ├── User.ts
│   └── index.ts
├── order/
│   ├── OrderController.ts
│   ├── OrderService.ts
│   ├── OrderRepository.ts
│   ├── Order.ts
│   └── index.ts
└── product/
    └── ...
```

**「一緒に変更されるもの」をまとめる。**

| ✅ 利点 | ❌ 欠点 |
|---|---|
| **変更が1ディレクトリに収まる** | 各パッケージ内の規律が必要 |
| ディレクトリを消せば機能ごと消える | 初心者には置き場所の判断が必要 |
| 担当分担しやすい（コンフリクトが減る） | パッケージ間の共通処理の置き場に悩む |
| 内部を隠蔽できる | |

#### どちらを選ぶか

#### 「クーポン機能を追加して」と言われたとき

```
【Package by Layer】変更が散らばる      【Package by Feature】1箇所に収まる
 src/                                   src/
 ├── controllers/  ●修正                ├── user/
 ├── services/     ●修正                ├── order/     ●●●● 修正はここだけ
 ├── repositories/ ●修正                └── product/
 └── models/       ●修正
     ↑ 4ディレクトリを行き来する            ↑ ディレクトリごと理解・移動・削除できる
```

> **原則：機能（Feature）で分けてから、その中でレイヤに分ける。**

```
src/
├── order/                      ← ①まず機能で分ける
│   ├── presentation/           ← ②その中でレイヤ
│   │   └── OrderController.ts
│   ├── application/
│   │   └── PlaceOrderUseCase.ts
│   ├── domain/
│   │   ├── Order.ts
│   │   └── OrderRepository.ts  ← インターフェース（第5章 DIP）
│   ├── infrastructure/
│   │   └── MySQLOrderRepository.ts
│   └── index.ts
├── user/
│   └── （同じ構造）
└── shared/                     ← 複数機能から使う共通部分
    └── ...
```

**理由**：ソフトウェアの変更依頼は、ほぼ常に「機能単位」で来るからです。
「Controllerを全部直して」という依頼は来ませんが、「注文機能を変えて」は毎日来ます。

**変更の単位とパッケージの単位を一致させる。**これがパッケージ分割の第一原則です。

### 7-3. パッケージの凝集度：3つの原則

第4章の凝集度を、パッケージのスケールに適用したものです。
「どのクラスを同じパッケージに入れるか」の基準になります。

#### ① REP — 再利用・リリース等価の原則

> **再利用の単位は、リリースの単位である**

一緒に再利用されるものだけを、同じパッケージにまとめる。
「このパッケージだけ使いたい」と思ったときに、無関係なものが付いてこないこと。

#### ② CCP — 閉鎖性共通の原則（Common Closure Principle）

> **同じ理由で、同じタイミングで変更されるクラスを、同じパッケージにまとめる**

**SRP（単一責任の原則）のパッケージ版**です。
逆に言えば、異なる理由で変更されるものは分ける。

```
✅ 「注文のルールが変わったら order/ だけ直せばいい」
❌ 「注文のルールが変わったので services/ と models/ と utils/ を直す」
```

**実務で最も効くのはこの原則です。**まずCCPだけ意識してください。

#### ③ CRP — 全再利用の原則（Common Reuse Principle）

> **一緒に使われないクラスを、同じパッケージに入れてはならない**

**ISP（インターフェース分離の原則）のパッケージ版**です。
パッケージAの一部だけ使いたいのに、A全体に依存させられる状況を避ける。

#### 3原則は互いに引っ張り合う（テンション図）

```
            REP（再利用しやすく）
                  ／＼
                 ／   ＼
   まとめすぎる ／      ＼ 分けすぎる
               ／         ＼
         CCP ────────────── CRP
     （変更しやすく）    （余計な依存を避ける）
```

- REPとCCPを重視 → パッケージが**大きく**なる
- CRPを重視 → パッケージが**小さく**なる

**3つ全部は同時に満たせません。** プロジェクトの段階で重心を動かします。

| 段階 | 重視すべき原則 |
|---|---|
| 開発初期・自社サービス | **CCP**（開発しやすさ優先） |
| 成熟後・ライブラリ公開 | **REP / CRP**（再利用しやすさ優先） |

初心者はまず **CCP（一緒に変わるものをまとめる）** だけを守れば十分です。

### 7-4. パッケージの結合度：3つの原則

「パッケージ同士がどう依存すべきか」の基準です。ここが第8章への直接の橋渡しになります。

#### ① ADP — 非循環依存関係の原則（Acyclic Dependencies Principle）

> **パッケージの依存関係に、循環があってはならない**

```
❌ 循環している
   order ──▶ user
     ▲         │
     └─────────┘

✅ 循環がない（DAG：有向非巡回グラフ）
   order ──▶ user ──▶ shared
     │                   ▲
     └───────────────────┘
```

**循環があると何が起きるか：**

- どちらか片方だけをテストできない（必ずセットで必要）
- ビルド順序が決まらない
- 片方を直すと、もう片方経由で自分に返ってくる
- どちらか片方だけをリリース／切り出せない

**循環の壊し方は2つ：**

1. **DIPを使う**（第5章）— 依存の向きを片方だけ逆転させる
   ```
   order ──▶ [UserFinderインターフェース] ◀── user
   ```
2. **共通部分を新しいパッケージに抜き出す**
   ```
   order ──▶ shared ◀── user
   ```

**実務での鉄則：循環importが出たら、その場で直す。**放置すると必ず増えます。
（`madge`, `dependency-cruiser`, `import-linter` などで自動検出できます）

#### ② SDP — 安定依存の原則（Stable Dependencies Principle）

> **より安定した方向に依存せよ**

ここでの「安定」＝**変更しにくい**という意味です。

```
安定度 = 「どれだけ多くのものから依存されているか」

  多くから依存される → 変えると影響が大きい → 変えにくい → 安定
  何からも依存されない → 自由に変えられる     → 不安定
```

```
    [UI]  ← 不安定（誰も依存していない。自由に変えられる）
      │
      ▼
  [UseCase]
      │
      ▼
   [Domain] ← 安定（多くが依存している。おいそれと変えられない）
```

**依存の矢印は、不安定なものから安定なものへ向ける。**
逆向き（安定なものが不安定なものに依存する）だと、**変えにくいはずのものが、しょっちゅう変更に巻き込まれる**ことになります。

これは第6章の「依存の矢印は変わりにくいものへ向ける」と同じことです。

#### ③ SAP — 安定度・抽象度等価の原則（Stable Abstractions Principle）

> **安定したパッケージは、抽象的であるべき**

安定＝変えにくい。でも変更にはいつか対応しなければならない。
**では変えにくいのに拡張できるようにするには? → 抽象（インターフェース）にする。**（第5章 OCP）

```
安定 かつ 具体 = 最悪（変えたいのに変えられない、拡張もできない）
安定 かつ 抽象 = 理想（実装を追加すれば拡張できる）
不安定 かつ 具体 = OK（自由に書き換えればいい）
```

だから**中心（ドメイン層）にはインターフェースと業務ルールが置かれ、外側（インフラ層）に具体的な実装が置かれる**のです。

### 7-5. 実践：まず守るべき4つのルール

理論は多いですが、日々守るべきことは4つだけです。

1. **一緒に変更されるものを、同じディレクトリに置く**（CCP）
2. **循環依存を作らない**（ADP）
3. **依存の矢印を、変わりにくい方へ向ける**（SDP）
4. **パッケージの公開範囲を最小にする**（`index.ts` などの窓口を作る）

#### アンチパターン集

| アンチパターン | なぜダメか | 対処 |
|---|---|---|
| `utils/`, `common/`, `helpers/` に何でも入れる | 偶発的凝集。全パッケージから依存される泥沼 | 用途ごとに名前のあるパッケージへ |
| `models/` に全エンティティを集約 | 機能変更が複数ディレクトリに散る | 機能ごとに配置 |
| 深すぎる階層（5階層以上） | importパスが読めない、移動が大変 | 2〜3階層に収める |
| どのパッケージからでも何でもimportできる | 事実上パッケージ分割していない | 窓口(index)経由に統一、Lintで強制 |
| `shared/` が全体の半分を占める | 分割の判断を放棄している | 本当に共通か再検討 |

#### 依存ルールは自動チェックできる

人間の意志では守れません。ツールで縛ってください。

- **ESLint** `import/no-restricted-paths` / `no-cycle`
- **dependency-cruiser**（JS/TS）— 層をまたぐ依存を禁止できる
- **ArchUnit**（Java）、**import-linter**（Python）

```javascript
// 例：domain層がinfrastructure層をimportすることを禁止する
{
  from: { path: '^src/.*/domain' },
  to:   { path: '^src/.*/infrastructure' },
  severity: 'error'
}
```

### 7-6. ここまでの原則が、次章のアーキテクチャになる

第8章のアーキテクチャは、**本章のパッケージ原則を、システム全体に適用した「型」**にすぎません。

| 本章で学んだこと | 第8章での現れ方 |
|---|---|
| CCP（一緒に変わるものをまとめる） | 層・機能への分割そのもの |
| ADP（循環禁止） | 「依存は一方向」というルール |
| SDP（安定な方へ依存） | 「外側から内側へ」の依存の向き |
| SAP（安定なものは抽象に） | 中心にインターフェース、外側に実装 |
| 公開範囲の最小化 | ポート＆アダプタの「ポート」 |

つまり、次章で出てくる**同心円の図は、SDPとSAPを絵にしたもの**です。
「なぜ内側に依存するのか?」の答えは、**「内側の方が安定しているから」**です。

### 7-7. コード例で確認する（Before / After）

#### 例1：パッケージの窓口を作る

```typescript
// ❌ Before：内部ファイルを直接importされている

import { taxRate }      from '../order/internal/constants';   // 内部実装に侵入
import { PriceTable }   from '../order/internal/PriceTable';
// → order/ の中身を1つ動かすと、無関係な10ファイルが壊れる

// ✅ After：index.ts を唯一の窓口にする
// order/index.ts

// 内部（PriceTable, taxRate）はexportしない

// 利用側
import { OrderService } from '@/order';
```

#### 例2：循環依存を DIP で断ち切る

```typescript
// ❌ Before：user と order が相互参照している
// user/User.ts
import { Order } from '../order/Order';
export class User { orders: Order[]; }

// order/Order.ts
import { User } from '../user/User';
export class Order { user: User; }

// ✅ After：片方はIDだけを持つ（依存を一方向にする）
// order/Order.ts
export class Order { userId: UserId; }          // userを知らない

// user/UserOrders.ts（必要な側が組み立てる）
import { Order } from '@/order';
export class UserOrders {
  constructor(private orderRepo: OrderRepository) {}
  forUser(userId: UserId): Promise<Order[]> { /* ... */ }
}
```

#### 例3：`shared` を肥大化させない

❌ Before                          ✅ After
src/                               src/

│   ├── utils.ts                   │   └── result.ts     ← 本当に全体共通のものだけ
│   ├── constants.ts               ├── order/
│   ├── orderHelper.ts   ★         │   └── OrderPricing.ts  ← 注文固有の知識は注文へ
│   ├── userHelper.ts    ★         ├── user/
│   └── mailTemplate.ts  ★         │   └── UserPolicy.ts
├── order/                         └── notification/

  「共通」は置き場所に困ったものの避難所になりやすい。
  1つ置くたびに「本当に3つ以上の機能から使うか?」を確認する。
```

## 第8章 アーキテクチャ

ここまでの原則を、**システム全体のスケールに適用したもの**がアーキテクチャです。
新しいことは何も出てきません。第3〜7章の拡大版です。

### 8-1. なぜアーキテクチャが必要か

小さなアプリでは、全部1ファイルでも動きます。
しかし規模が大きくなると：

- どこに何を書けばいいか分からない
- 画面を変えたらDBが壊れる
- テストを書こうにもDBやAPIが必要で書けない

**アーキテクチャ = 「どこに何を置くか」のルール**です。

### 8-2. レイヤードアーキテクチャ（基本形）

最も基本的で、まず理解すべき形。**関心事を層に分ける。**

```
┌─────────────────────────────┐
│  プレゼンテーション層          │  UI、Controller、画面表示
├─────────────────────────────┤  ↓依存
│  アプリケーション層            │  ユースケース、処理の流れの調整
├─────────────────────────────┤  ↓依存
│  ドメイン層                   │  ビジネスルール、業務知識
├─────────────────────────────┤  ↓依存
│  インフラストラクチャ層        │  DB、外部API、ファイル
└─────────────────────────────┘
```

#### 各層の責務

| 層 | 責務 | 置くもの |
|---|---|---|
| プレゼンテーション | 入出力の変換 | Controller、View、DTO |
| アプリケーション | ユースケースの手順 | 「注文する」という一連の流れ |
| ドメイン | 業務ルール | 「在庫がなければ注文不可」等 |
| インフラ | 技術的詳細 | SQL、HTTPクライアント |

#### ルール

- **上の層は下の層を呼べる。逆は禁止。**
- 層を飛ばさない（Controllerが直接SQLを書かない）

#### 問題点

ドメイン層（最重要）がインフラ層（最も変わりやすい）に依存している。

```
❌ 素朴なレイヤード
  ┌────────────┐
  │ ドメイン層   │ 最も重要・最も安定させたい
  └──────┬─────┘
         │ 依存
  ┌──────▼─────┐
  │ インフラ層   │ 最も変わりやすい（DB・API・ライブラリ）
  └────────────┘
     → DBを変えるとビジネスロジックが壊れる

✅ DIPで矢印を逆転させる（第5章）
  ┌────────────────────────────────┐
  │ ドメイン層                       │
  │   ┌──────────────────────────┐ │
  │   │ OrderRepository（IF）     │ │ ← インターフェースはドメイン層が所有
  │   └────────────▲─────────────┘ │
  └────────────────│───────────────┘
                   │ implements（依存の矢印が上向きに）
        ┌──────────┴──────────┐
        │ インフラ層             │
        │ MySQLOrderRepository │
        └──────────────────────┘
     → DBを差し替えてもドメイン層は1行も変わらない
```
→ **DBを変えるとビジネスロジックが壊れる。** これを解決したのが次の形です。

### 8-3. ヘキサゴナルアーキテクチャ（ポート＆アダプタ）

> **アイデア：アプリケーションの中心を、外界から隔離する**

```
              [Web UI]  [CLI]  [テストコード]
                  │       │        │
                  ▼       ▼        ▼
             ┌──── 駆動アダプタ ────┐
             │  ┌───────────────┐  │
             │  │  入力ポート     │  │  ← インターフェース
             │  ├───────────────┤  │
             │  │               │  │
             │  │  アプリケーション │  │  ← ビジネスロジック
             │  │  （六角形の中） │  │     外の世界を一切知らない
             │  │               │  │
             │  ├───────────────┤  │
             │  │  出力ポート     │  │  ← インターフェース
             │  └───────────────┘  │
             └──── 被駆動アダプタ ───┘
                  │       │        │
                  ▼       ▼        ▼
             [MySQL]  [外部API]  [モック]
```

#### 用語

- **ポート(Port)**：アプリケーションが定義するインターフェース（＝契約）
- **アダプタ(Adapter)**：ポートの実装。外の技術に合わせる部品

#### なぜ「六角形」か

「層」という上下関係ではなく、**「中と外」という関係**を表現するため。
辺の数に意味はなく、「入口・出口が複数ある」ことを示しています。

#### 何が嬉しいか

```javascript
// アプリケーション側が定義するポート（インターフェース）
interface UserRepositoryPort {
  findById(id): User;
}

// アダプタは差し替え可能
class MySQLUserAdapter implements UserRepositoryPort { /* 本番 */ }
class InMemoryUserAdapter implements UserRepositoryPort { /* テスト */ }
```

→ **DBなしでビジネスロジックのテストが書ける。**
→ **MySQLからDynamoDBに変えても、六角形の中は1行も変わらない。**

これは第5章のDIPをシステム全体に適用しただけです。

### 8-4. クリーンアーキテクチャ

ヘキサゴナル等の考え方を統合・整理したもの。**同心円で表現されます。**

```
        ┌──────────────────────────────────────┐
        │  Frameworks & Drivers                │  Web, DB, UI, 外部API
        │  ┌────────────────────────────────┐  │
        │  │  Interface Adapters            │  │  Controller, Presenter,
        │  │  ┌──────────────────────────┐  │  │  Gateway
        │  │  │  Use Cases               │  │  │  アプリケーション固有の
        │  │  │  ┌────────────────────┐  │  │  │  ビジネスルール
        │  │  │  │  Entities          │  │  │  │
        │  │  │  │                    │  │  │  │  企業全体で通用する
        │  │  │  └────────────────────┘  │  │  │  ビジネスルール
        │  │  └──────────────────────────┘  │  │
        │  └────────────────────────────────┘  │
        └──────────────────────────────────────┘

           依存の方向：外側 ───────▶ 内側
           （内側は外側を一切知らない）
```

#### 最重要ルール：依存性のルール

> **ソースコードの依存性は、内側にのみ向かうこと。**
> 内側の円は、外側の円について何も知ってはならない。

- Entities は、DBもWebも知らない
- Use Cases は、Web frameworkを知らない
- **内側にはフレームワーク由来のimport文が一切ない**

#### 各層の中身

| 層 | 内容 | 例 |
|---|---|---|
| Entities | 最も普遍的な業務ルール | `Order.canCancel()` — アプリが変わっても不変 |
| Use Cases | アプリ固有の処理手順 | 「注文をキャンセルする」フロー |
| Interface Adapters | データ形式の変換 | Controller、Repository実装、Presenter |
| Frameworks & Drivers | 技術的詳細 | Express、TypeORM、React |

#### 制御の流れと依存の向きが逆になる問題

実行時はUse Caseから外側（DB）を呼びますが、依存は内向きでなければなりません。
これを解決するのが**DIP**です。

```
【実行時の流れ】 UseCase ──呼び出し──▶ DB実装

【ソースの依存】 UseCase ──▶ [Repositoryインターフェース]
                                    ▲
                                    │implements
                              DB実装（外側）

インターフェースを内側に置くことで、依存を内向きに保つ
```

**これがクリーンアーキテクチャの心臓部です。**第5章のDIPそのものです。

### 8-5. 3つの関係を整理する

| | レイヤード | ヘキサゴナル | クリーン |
|---|---|---|---|
| 発想 | 関心事を層に分ける | 中心を外界から隔離 | 上記を統合・体系化 |
| 表現 | 積み重ね | 六角形（中と外） | 同心円 |
| 依存の向き | 上→下 | 外→中 | 外→内 |
| 核心 | 責務分離 | ポート＆アダプタ | 依存性のルール |

**結論：3つとも言っていることはほぼ同じです。**

> **重要なビジネスロジックを、変わりやすい技術的詳細から守る**

表現方法と語彙が違うだけ。この一文を理解していれば、どの流派でも通用します。

### 8-6. 実践上の注意

⚠️ **小規模なアプリに全部を適用しないでください。**

- ファイル数が3倍になり、変更のたびに5ファイル触ることになる
- 初心者が最初にやると「なぜこんなに面倒なのか」で終わる

**現実的な導入順序：**

1. まず**関数分割**と**責務の分離**を徹底する（第3章）
2. 次に**ビジネスロジックとI/Oを分ける**（これだけで8割の恩恵）
3. テストが書きにくいと感じたら**DI**を導入する
4. ファイルが増えてきたら**機能ごとのパッケージ分割**と**循環依存の排除**（第7章）
5. 規模が大きくなってから**レイヤ分割**を導入
6. 複数の入出力経路が必要になったら**ポート＆アダプタ**

## 第9章 状態と不変性

第3章で「計算とI/Oを分ける」を学びました。本章はその根っこにある**「状態」**の話です。

> **バグの大半は「値が変わること」から生まれます。**
> 変わらないものは壊れません。だから設計の要点は、**変わる部分をできるだけ小さく囲い込む**ことです。

### 9-1. なぜ状態が難しいのか

```
   純粋な計算                      状態を持つ処理
   ┌──────────────────┐           ┌──────────────────┐
   │ f(2, 3) → 5      │           │ counter.next()   │
   │ f(2, 3) → 5      │           │  → 1             │
   │ f(2, 3) → 5      │           │ counter.next()   │
   └──────────────────┘           │  → 2  ★結果が違う │
   いつ・何回呼んでも同じ           └──────────────────┘
   → 読むときに履歴を考えなくていい   → 「今どうなっているか」を
   → テストが引数と戻り値だけで済む      頭の中で追う必要がある
```

**状態があると、コードを読むときに「時間」という次元が増えます。**
「この行に来たとき、この変数は何になっているか?」を追うのが、読解コストの正体です。

```
   認知コスト ＝ 変数の数 × 変わりうるタイミングの数

   ┌────────────────────────────────────────────┐
   │ 変数10個 × どこでも書き換え可能              │ → 組合せが爆発
   │ 変数10個 × うち8個は不変（const）           │ → 実質2個だけ追えばいい
   └────────────────────────────────────────────┘
```

### 9-2. 不変（イミュータブル）を基本にする

```javascript
// ❌ 引数を書き換える（呼び出し元も壊れる）
function addTax(order) {
  order.total = order.total * 1.1;   // 元のオブジェクトを破壊
  return order;
}

// ✅ 新しい値を返す
function addTax(order) {
  return { ...order, total: order.total * 1.1 };
}
```

```
   破壊的変更                       非破壊的変更
   ┌───────┐                       ┌───────┐    ┌───────┐
   │ order │ ──書き換え──▶ 変質      │ order │ ──▶│ order'│
   └───────┘                       └───────┘    └───────┘
   誰が変えたか追えない               元は無傷。差分が明確
   他の参照元が巻き添えになる          いつでも前の状態に戻れる
```

**言語ごとの基本装備**

| 言語 | 不変にする手段 |
|---|---|
| JavaScript / TypeScript | `const`、スプレッド構文、`readonly`、Object.freeze |
| Java | `final`、record、不変コレクション |
| Kotlin | `val`、`data class` + `copy()` |
| Python | タプル、`frozen=True` の dataclass |
| Go | 値渡し、ポインタを渡さない |

> **原則：まず `const` / `val` / `final` で宣言し、どうしても必要なときだけ可変にする。**

### 9-3. 可変性を閉じ込める

現実のアプリに状態は必ず必要です。**なくすのではなく、集める**のが正解です。

```
❌ 状態が散らばっている              ✅ 状態を一箇所に集める
 ┌────┐ ┌────┐ ┌────┐              ┌───────────────────┐
 │ A  │ │ B  │ │ C  │              │  状態を持つ層       │
 │state│ │state│ │state│              │  （Store / Entity）│
 └─┬──┘ └─┬──┘ └─┬──┘              └─────────┬─────────┘
   └──────┴──────┘                            │ 値を渡すだけ
   どこで変わったか分からない          ┌────┬────┴────┬────┐
   同期がずれる                      │ A  │    B    │ C  │ ← 全部純粋
                                     └────┴─────────┴────┘
```

これは第3章の「計算とI/Oの分離」、第8章の「ドメイン層に状態を集める」と同じ発想です。

```
   関数型コア / 命令型シェル（Functional Core, Imperative Shell）

   ┌─────────────────────────────────────┐
   │ 命令型シェル（薄い）                   │ 状態・I/O・時刻・乱数
   │  ┌───────────────────────────────┐  │
   │  │ 関数型コア（厚い）               │  │ 純粋な計算・業務ルール
   │  │  入力 → 計算 → 出力            │  │ テストが超簡単
   │  └───────────────────────────────┘  │
   └─────────────────────────────────────┘
```

### 9-4. 特に危険な「共有された可変状態」

```
   ┌─────────────────────────────────────────────┐
   │ 危険度ランキング                              │
   ├─────────────────────────────────────────────┤
   │ ★★★ グローバル変数・シングルトンの可変状態     │
   │      → どこからでも変えられる。追跡不能        │
   │ ★★  引数として渡されたオブジェクトの書き換え    │
   │      → 呼び出し元が予期しない副作用            │
   │ ★★  モジュールスコープのキャッシュ             │
   │      → テストが実行順に依存する原因No.1        │
   │ ★    クラスのフィールド                       │
   │      → スコープが限定されるのでまだ扱える       │
   └─────────────────────────────────────────────┘
```

```javascript
// ❌ モジュールレベルの可変状態（テストが順序依存になる）
let cache = {};
export function getUser(id) {
  if (!cache[id]) cache[id] = fetchUser(id);
  return cache[id];
}

// ✅ 状態を持つ主体を明示し、注入できるようにする
export class UserLoader {
  #cache = new Map();
  constructor(fetcher) { this.fetcher = fetcher; }
  get(id) { /* ... */ }
}
```

### 9-5. 「不正な状態を作れなくする」

第12章の型の話とも重なる、最も強力な考え方です。

```
   3段階の防ぎ方（下ほど強い）

   ① 実行時にチェックする      … if文で弾く（漏れる）
   ② テストで確認する          … 書き忘れる
   ③ そもそも表現できなくする   … 構造上あり得なくする ★最強
```

```typescript
// ❌ 不正な状態が表現できてしまう
class Order {
  status: string;
  shippedAt?: Date;
  cancelledAt?: Date;
  // status='cancelled' なのに shippedAt がある、が作れてしまう
}

// ✅ 状態遷移を型と操作で縛る
type Order =
  | { status: 'pending' }
  | { status: 'shipped';   shippedAt: Date }
  | { status: 'cancelled'; cancelledAt: Date };
```

**状態遷移図を書いてから実装するのも有効です。**

```
   [pending] ──confirm──▶ [confirmed] ──ship──▶ [shipped]
       │                       │
     cancel                  cancel
       ▼                       ▼
   [cancelled] ◀───────────────┘

   shipped から cancelled への矢印は存在しない
   → コード上も「呼べない」ようにする
```

### 9-6. コード例で確認する（Before / After）

#### 例1：引数の配列を破壊している

```javascript
// ❌ Before：sortは元の配列を書き換える
function topThree(scores) {
  return scores.sort((a, b) => b - a).slice(0, 3);
}
const scores = [3, 1, 5];
topThree(scores);
console.log(scores);   // [5, 3, 1] ← 呼び出し元の配列が変わっている！

// ✅ After：コピーしてから操作する

  return [...scores].sort((a, b) => b - a).slice(0, 3);
}
```

#### 例2：ネストしたオブジェクトの部分更新

```javascript
// ❌ Before

  user.status.isActive = true;         // 深いところを直接書き換え
  user.status.updatedAt = new Date();
  return user;
}

// ✅ After
function activate(user, now) {
  return {
    ...user,
    status: { ...user.status, isActive: true, updatedAt: now },

```

#### 例3：状態を持つクラスの不変条件を守る

```javascript
// ❌ Before：外部から自由に壊せる

  items = [];                       // publicで露出
}
cart.items.push(null);              // 不正な値が入る
cart.items = 'こわれた';             // 型ごと壊れる

// ✅ After：変更手段を限定し、内部を見せない

  add(item) {
    if (item.quantity <= 0) throw new InvalidItemError();
    this.#items = [...this.#items, item];
  }

  get items() { return [...this.#items]; }   // コピーを返す（外から壊せない）
  get total() { return this.#items.reduce((s, i) => s + i.subtotal, 0); }
}
```

#### 例4：状態遷移を型で縛る

```typescript
// ❌ Before：あり得ない組み合わせが作れる
class Job {
  status: 'queued' | 'running' | 'done' | 'failed';
  startedAt?: Date;
  result?: string;
  error?: string;
  // status='queued' なのに result がある、が作れてしまう

// ✅ After：状態ごとに持つデータを固定する

  | { status: 'queued';  queuedAt: Date }
  | { status: 'running'; startedAt: Date }
  | { status: 'done';    startedAt: Date; finishedAt: Date; result: string }
  | { status: 'failed';  startedAt: Date; failedAt: Date;   error: string };

// 使う側は網羅チェックが効く
function describe(job: Job): string {
  switch (job.status) {
    case 'queued':  return '待機中';
    case 'running': return '実行中';
    case 'done':    return `完了: ${job.result}`;   // resultの存在が型で保証される
    case 'failed':  return `失敗: ${job.error}`;
  }
}
```

#### 例5：モジュールレベルのキャッシュがテストを壊す

```javascript

  if (!settingsCache) settingsCache = await db.loadSettings();

  constructor(private db) {}

    this.#cache ??= await this.db.loadSettings();

  }

## 第10章 エラーハンドリングと例外設計

初心者が最も雑に書き、かつ**障害の深刻度を決定づける**のがエラー処理です。
正常系だけのコードは半分しか書けていません。

### 10-1. まず分類する：3種類の「失敗」

**すべてを同じように扱うから混乱します。**

```
 ┌──────────────────────────────────────────────────────────┐
 │ ① 想定内の失敗（業務エラー）                                │
 │    在庫切れ、残高不足、バリデーションNG、認証失敗            │
 │    → 「起きて当然」。戻り値で表現し、呼び出し元が必ず処理する │
 ├──────────────────────────────────────────────────────────┤
 │ ② 想定内の異常（環境エラー）                                │
 │    ネットワーク断、DBタイムアウト、外部APIの5xx              │
 │    → 例外。リトライ・フォールバック・縮退運転の対象           │
 ├──────────────────────────────────────────────────────────┤
 │ ③ 想定外（バグ）                                           │
 │    null参照、配列外アクセス、あり得ない分岐                  │
 │    → 握りつぶさない。速やかに落として気づく（Fail Fast）     │
 └──────────────────────────────────────────────────────────┘
```

```
   よくある間違い

   ①を例外で投げる  → 正常な業務フローが例外まみれになり、見落とす
   ③を握りつぶす    → バグが隠れ、原因不明の不整合データが残る ★最悪
```

### 10-2. 例外 vs 戻り値

```javascript
// ①想定内の業務エラー → 戻り値で表現する（呼び出し元が無視できない）
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

function withdraw(account, amount): Result<Account, 'INSUFFICIENT_FUNDS'> {
  if (account.balance < amount) {
    return { ok: false, error: 'INSUFFICIENT_FUNDS' };
  }
  return { ok: true, value: { ...account, balance: account.balance - amount } };
}
```

```
   例外を使うべきとき                戻り値を使うべきとき
   ─────────────────────────────────────────────────────
   ・その場で対処できない            ・呼び出し元が必ず判断すべき
   ・呼び出し元の何段も上で処理する    ・「失敗」が仕様の一部
   ・プログラムの前提が壊れた         ・型で網羅性を強制したい

   判断基準：「これは例外的な事態か? それとも予期された結果か?」
```

### 10-3. アンチパターン：握りつぶし

```javascript
// ❌ 最悪。原因が永久に分からなくなる
try {
  await save(order);
} catch (e) {
  // 何もしない
}

// ❌ ログだけ出して握りつぶす（呼び出し元は成功したと思う）
catch (e) { console.log(e); }

// ❌ 情報を捨てる（元の原因が消える）
catch (e) { throw new Error('保存に失敗'); }

// ✅ 原因を保持して、意味のある例外に変換する
catch (e) {
  throw new OrderSaveError(`注文${order.id}の保存に失敗`, { cause: e });
}
```

```
   握りつぶしが生む地獄

   catch{} ──▶ エラーが消える ──▶ 不整合データが静かに増える
                                        │
                                        ▼
                            数ヶ月後に「なぜか数字が合わない」
                            ログもスタックトレースも残っていない
```

> **原則：catchしたら、必ず「処理する」か「情報を足して投げ直す」かのどちらか。**
> 何もしない catch は、意図的なら**理由をコメントで残す**（第2章）。

### 10-4. どの層で捕まえるか（第8章との接続）

**エラー処理は「層」で役割分担します。**

```
 ┌────────────────────────────────────────────────────────┐
 │ プレゼンテーション層                                     │
 │  ・例外を「ユーザー向けメッセージ」と「HTTPステータス」に変換 │
 │  ・最終防衛線（グローバルハンドラ）で必ず捕まえる ★        │
 ├────────────────────────────────────────────────────────┤
 │ アプリケーション層                                       │
 │  ・業務エラーを判断し、フローを分岐                       │
 │  ・トランザクションのロールバック                         │
 ├────────────────────────────────────────────────────────┤
 │ ドメイン層                                              │
 │  ・業務ルール違反を「型・戻り値」で表現                    │
 │  ・技術的な例外は知らない（DBのエラーを知らない）           │
 ├────────────────────────────────────────────────────────┤
 │ インフラ層                                              │
 │  ・技術例外（SQLException等）を、上位の言葉に翻訳して投げる  │
 │    SQLException → OrderRepositoryError                  │
 └────────────────────────────────────────────────────────┘

   原則：例外は「層をまたぐときに翻訳する」
        DBの都合をUIまで漏らさない（＝依存の向きを守る）
```

### 10-5. エラーメッセージの設計

```
   ❌ 「エラーが発生しました」
      → 利用者も開発者も何も分からない

   ✅ 2種類を分けて設計する
   ┌──────────────────────────────────────────────┐
   │ ユーザー向け                                   │
   │  ・何が起きたか（平易な言葉で）                  │
   │  ・次に何をすればいいか ★これが最重要            │
   │  ・内部情報を出さない（SQLやパスは漏洩リスク）    │
   │  例：「メールアドレスの形式が正しくありません」    │
   ├──────────────────────────────────────────────┤
   │ 開発者向け（ログ）                              │
   │  ・いつ・どこで・何が・どの入力で                │
   │  ・スタックトレース、相関ID                     │
   │  例：OrderSaveError order_id=123 cause=...     │
   └──────────────────────────────────────────────┘
```

### 10-6. リトライとフォールバック

```
   リトライしていい失敗          リトライしてはいけない失敗
   ────────────────────────────────────────────────
   ・タイムアウト                ・バリデーションエラー（何度やっても同じ）
   ・503 / 429                  ・認証失敗
   ・一時的なネットワーク断        ・冪等でない処理（二重課金の危険）★

   ⚠️ リトライ前に必ず確認：その処理は冪等か?
      「同じリクエストを2回送っても結果が変わらない」ことを保証してから
```

```
   指数バックオフ（一斉再送でサーバを潰さないため）

   1回目 ─1秒─▶ 2回目 ─2秒─▶ 3回目 ─4秒─▶ 諦める
                  ＋ジッター（ランダムな揺らぎ）を入れる
```

**サーキットブレーカー**：連続失敗したら一定時間呼び出しを止め、無駄な待ちと連鎖障害を防ぐ考え方も覚えておくとよいです。

### 10-7. 早期に失敗させる（Fail Fast）

```
❌ 不正な値のまま進める              ✅ 入口で止める
 入力 → 処理 → 処理 → 処理 → 保存    入力 →[検証]→ 処理 → 処理 → 保存
              ↑                            ↑
        ここで初めて壊れる            壊れた場所＝原因の場所
        原因の特定に何時間もかかる      デバッグが一瞬で終わる
```

**境界（入力を受け取る場所）で検証し、内側では「正しい値であること」を前提にできる状態を作ります。**
これは第9章の「不正な状態を作れなくする」と同じ考え方です。

### 10-8. コード例で確認する（Before / After）

#### 例1：業務エラーを例外で投げない

function reserve(item: Item, qty: number): ReserveResult {

    return { ok: false, reason: 'OUT_OF_STOCK', available: item.stock };
  }
  return { ok: true, reserved: qty };
}
// → 呼び出し側は ok を確認しないとコンパイルが通らない
```

## 第11章 テストによる品質保証

第8章までは「どう書くか」の話でした。
本章と次章は、**「書いたものをどう保証し続けるか」**の話です。

> **設計とテストは表裏一体です。テストしにくいコードは、ほぼ例外なく設計が悪い。**
> だからテストは「品質を測る道具」であると同時に、**「設計の良し悪しを教えてくれるセンサー」**でもあります。

### 11-1. テストは何のために書くのか

初心者は「バグを見つけるため」と考えがちですが、実際の価値は次の順です。

```
  ① 変更する勇気をくれる  ★最大の価値★
     「直したら他が壊れるかも」→「テストが通れば大丈夫」
              │
              ▼
  ② 設計のフィードバック
     テストが書きにくい ＝ 結合度が高い・責務が多すぎるというサイン
              │
              ▼
  ③ 実行可能なドキュメント
     「この関数はこう使う」「この条件ではこうなる」が仕様として残る
              │
              ▼
  ④ バグの検出
     （もちろん重要だが、上の3つの副産物に近い）
```

**テストがないコードは、事実上リファクタリングできません。**
第1章の「変更容易性」は、テストがあって初めて成立します。

```
      設計 ◀────────────────▶ テスト
       │   テストしやすさが      │
       │   良い設計の証明        │
       ▼                       ▼
   変更しやすい ◀───────────▶ 安心して変更できる
```

### 11-2. テストの種類とテストピラミッド

#### テストの3階層

```
                    ▲ 遅い・壊れやすい・書くのが高価
                   ╱ ╲
                  ╱E2E╲          少数
                 ╱─────╲         ブラウザ操作、実システム通し
                ╱       ╲        「ユーザーが登録して注文できる」
               ╱ 統合テスト ╲       中程度
              ╱             ╲     DB・外部APIとの結合を確認
             ╱───────────────╲    「Repositoryが正しく保存する」
            ╱                 ╲
           ╱    ユニットテスト    ╲  多数
          ╱                     ╲ 単一の関数・クラスを高速に検証
         ╱───────────────────────╲「税率10%で110円になる」
                    ▼ 速い・安定・書くのが安価
```

| 種類 | 対象 | 実行速度 | 何を保証するか |
|---|---|---|---|
| ユニット | 関数・クラス単体 | ミリ秒 | ロジックの正しさ |
| 統合 | 複数部品の連携、DB、API | 秒 | 繋ぎ込みの正しさ |
| E2E | システム全体 | 分 | ユーザー価値が成立するか |

#### なぜ「ピラミッド」型なのか

```
❌ アイスクリームコーン（アンチパターン）    ✅ ピラミッド
    ┌─────────────────────┐                      ▲
    │      E2E 多数        │                     ╱ ╲  E2E 少
    ├─────────────────┤                        ╱───╲
    │   統合           │                      ╱ 統合 ╲
    ├─────────┤                             ╱───────╲
    │ ユニット少 │                          ╱ ユニット多 ╲
    └────┘                                ╱─────────────╲

  ・CIに40分かかる                        ・CIが数分で終わる
  ・たまに落ちる（Flaky）                  ・落ちたら本当にバグ
  ・落ちても原因箇所が分からない            ・落ちた場所＝原因の場所
  ・誰も直さなくなる → 形骸化              ・信頼できるので開発が速い
```

**判断基準：同じことを保証できるなら、常に下の層で書く。**
E2Eは「主要な導線が繋がっていること」の確認に絞ります（数本〜数十本）。

#### 補足：テスティングトロフィー

近年のWeb開発では、統合テストを厚めにする「トロフィー型」も支持されています。

```
      ╭───────╮   E2E（少）
      │       │
    ╭─┴───────┴─╮ 統合（最も厚い）★
    │           │  実装詳細に依存しにくく、リファクタで壊れにくい
    ╰─┬───────┬─╯
      │ ユニット │  複雑なロジック部分に絞る
      ╰───┬───╯
      ─────────   静的解析（型・Lint）＝土台 → 第12章
```

**どちらが正しいという話ではありません。**
「複雑なドメインロジックがある」ならピラミッド、「大半が画面とAPIの繋ぎ込み」ならトロフィー、と対象で選びます。

### 11-3. アーキテクチャとテストの対応（第8章との接続）

第8章で層を分けた最大の実利がここに現れます。

```
 ┌────────────────────────────────────────────────────────┐
 │ Frameworks & Drivers（DB, Web, 外部API）                 │
 │   → 統合テスト / E2E                                     │
 │   ┌──────────────────────────────────────────────────┐ │
 │   │ Interface Adapters（Controller, Repository実装）    │ │
 │   │   → 統合テスト（本物のDBやテスト用DBを使う）          │ │
 │   │   ┌────────────────────────────────────────────┐ │ │
 │   │   │ Use Cases                                   │ │ │
 │   │   │   → ユニットテスト（Repositoryはモック/Fake） │ │ │
 │   │   │   ┌──────────────────────────────────────┐ │ │ │
 │   │   │   │ Entities（業務ルール）                 │ │ │ │
 │   │   │   │   → ユニットテスト                     │ │ │ │
 │   │   │   │   依存なし・超高速・最も書く価値が高い   │ │ │ │
 │   │   │   └──────────────────────────────────────┘ │ │ │
 │   │   └────────────────────────────────────────────┘ │ │
 │   └──────────────────────────────────────────────────┘ │
 └────────────────────────────────────────────────────────┘

  内側に行くほど：テストが速く・安定し・書きやすい
  → だから「ビジネスロジックを内側に寄せる」設計に価値がある
```

**逆に言えば：** ロジックがController（外側）に書かれていると、テストのたびにHTTPリクエストが必要になります。これが「テストが書きにくい＝設計が悪い」の正体です。

### 11-4. 良いテストの条件

#### F.I.R.S.T. 原則

| 頭文字 | 意味 | 内容 |
|---|---|---|
| **F**ast | 速い | 遅いテストは実行されなくなる |
| **I**ndependent | 独立 | 他のテストの実行順・結果に依存しない |
| **R**epeatable | 再現可能 | 何度実行しても、どの環境でも同じ結果 |
| **S**elf-validating | 自己検証 | 成功/失敗が自動判定される（目視確認しない） |
| **T**imely | 適時 | 実装とほぼ同時に書く（後回しは書かれない） |

**特に危険なのが Independent 違反です。**

```
❌ テスト同士が繋がっている
  test1: ユーザーを作成（DBに残る）
  test2: そのユーザーを前提に検証  ← test1が落ちると連鎖して落ちる
                                   ← 単独実行できない
                                   ← 実行順を変えると壊れる

✅ 各テストが自己完結
  test1: [準備] ユーザー作成 → 検証 → [後片付け]
  test2: [準備] ユーザー作成 → 検証 → [後片付け]
```

#### 構造：AAA（Given-When-Then）

テストは常に3ブロックで書きます。**空行で区切るだけで劇的に読みやすくなります。**

```javascript
test('3年以上の会員は20%割引になる', () => {
  // Arrange（準備 / Given）— 前提条件を作る
  const user = new User({ isActive: true, membershipYears: 3 });

  // Act（実行 / When）— テスト対象を1回だけ呼ぶ
  const discount = getDiscount(user);

  // Assert（検証 / Then）— 期待結果を確認する
  expect(discount).toBe(0.2);
});
```

```
   Arrange ─────▶ Act ─────▶ Assert
   （準備）      （実行）     （検証）
    複数行OK    1行が理想    1つの概念を検証
```

#### テスト名は「仕様書」として書く

```javascript
❌ test('test1', ...)
❌ test('getDiscount', ...)          // 何を確認しているか不明

✅ test('3年以上の会員は20%割引になる', ...)
✅ test('退会済みユーザーには割引を適用しない', ...)
✅ test('userがnullの場合は0を返す', ...)
```

**テスト名を並べたものが、そのままその関数の仕様一覧になるのが理想**です。

```
 getDiscount の仕様（＝テスト名の一覧）
  ├─ userがnullの場合は0を返す
  ├─ 退会済みユーザーには割引を適用しない
  ├─ 会員年数3年未満は10%割引
  └─ 会員年数3年以上は20%割引
```

### 11-5. 何をテストすべきか

すべての入力を試すことは不可能なので、**代表値を選ぶ技法**を使います。

#### ① 同値分割 — 同じ結果になるグループの代表を1つ選ぶ

```
 会員年数による割引
 ├──────────┬──────────────────▶
 0年       3年
 [ 10%割引 ][    20%割引    ]
     ↑            ↑
   代表:1       代表:5      ← 各グループから1つ選べば十分
```

#### ② 境界値分析 — バグは境界に集中する

```
        2年   3年   4年
  ───────┼─────┼─────┼──────▶
        10%  20%  20%
         ↑    ↑
     ここが最頻出のバグ（>= と > の間違い）

  → テストすべき値：境界の「直前・ちょうど・直後」
```

**経験則：バグの大半は境界（0、1、上限、空、null）で起きます。**

#### ③ 異常系を必ず入れる

```
 テストすべき観点
 ├─ 正常系（ハッピーパス）      … 1〜2本
 ├─ 境界値                    … 境界ごと
 ├─ 異常系（null, 空, 負数, 型違い） … 忘れられがち★
 └─ エラー時の振る舞い（例外を投げる/エラーを返す）
```

### 11-6. テストダブル（偽物の部品）

外部依存（DB、API、時刻、乱数）を切り離すための代用品です。

```
  【本番】                        【テスト】
  UseCase                         UseCase
     │                               │
     ▼                               ▼
  MySQLRepository               FakeRepository
     │                          （メモリ上の配列）
     ▼                               
   MySQL                          高速・安定・準備不要
```

| 種類 | 役割 | 使いどころ |
|---|---|---|
| **Dummy** | 渡すだけで使わない | 引数を埋めるため |
| **Stub** | 決まった値を返す | 「このAPIは常に成功する」を再現 |
| **Fake** | 簡易的だが動く実装 | インメモリDBなど。**最も推奨** |
| **Spy** | 呼ばれたことを記録する | 「メールが1回送られた」を確認 |
| **Mock** | 呼ばれ方を検証する | 上に同じ（期待を事前に設定） |

#### モックの使いすぎに注意

```
❌ 何もかもモックにする
  実装を変えただけでテストが壊れる（＝実装詳細に依存している）
  テストが通っても、本当に動くか分からない

✅ 原則
  ・自分が書いたコード同士 → なるべく本物を使う
  ・外部システム（DB, 決済API, メール送信） → Fake / Stub に置き換える
  ・「時刻」「乱数」「UUID」 → 必ず注入して固定できるようにする
```

```javascript
// ❌ テスト不能（実行時刻で結果が変わる）
function isExpired(token) {
  return token.expiresAt < new Date();
}

// ✅ 時刻を注入する
function isExpired(token, now) {
  return token.expiresAt < now;
}
```

### 11-7. テストしにくさは「設計の警告」

**テストが書きにくいと感じたら、テストの書き方ではなく設計を疑ってください。**

| テストの症状 | 疑うべき設計上の問題 | 対処 |
|---|---|---|
| 準備（Arrange）が20行超 | 依存が多すぎる | 責務を分割（SRP） |
| private メソッドをテストしたい | クラスが大きすぎる | 別クラスとして切り出す |
| モックが5個必要 | 結合度が高い | 依存を減らす、DIP適用 |
| DBがないと1行も動かない | ロジックがインフラに埋まっている | 純粋な計算を抽出（第3章） |
| 実行順で結果が変わる | グローバル状態を共有している | 状態を引数/インスタンスに |
| ちょっと直すと大量に壊れる | 実装詳細をテストしている | 公開された振る舞いをテストする |

```
   テストが書きにくい
          │
          ▼
   ┌──────────────────┐
   │ 設計を直すサイン   │  ← テストを頑張って書く前に、ここを疑う
   └──────────────────┘
          │
          ▼
   分割する / 依存を注入する / 計算とI/Oを分ける
          │
          ▼
   テストが素直に書けるようになる ＝ 設計が良くなった証拠
```

### 11-8. カバレッジの基礎知識

#### カバレッジとは何を測っているのか

```
 カバレッジ = テスト実行時に「通過した」コードの割合

  ⚠️ 測っているのは【実行されたか】であって、【検証されたか】ではない
```

```javascript
// カバレッジ100%だが、何ひとつ保証していないテスト
test('動く', () => {
  calculateTax(100);   // 呼んだだけ。結果を検証していない
});
```

**この一点を理解していないと、カバレッジは害になります。**
「カバレッジ90%です」は「90%のコードが正しい」ではなく、**「10%のコードは一度も動かしていない」**という意味しか持ちません。

```
  低い（例:30%）→ 「触れていない箇所がある」という【確かな事実】
  高い（例:95%）→ 「テストが十分」という【証明にはならない】

  ＝ カバレッジは「悪いことの検出」には使えるが、
     「良いことの証明」には使えない非対称な指標
```

#### カバレッジの種類（網羅の厳しさの階段）

```javascript
function judge(a, b) {
  if (a > 0 && b > 0) {
    return 'both';
  }
  return 'other';
}
```

```
 厳しさ
   ▲
   │ ┌──────────────────────────────────────────────────────┐
   │ │ パス網羅（C∞）  すべての経路の組合せ                    │ 現実には不可能
   │ ├──────────────────────────────────────────────────────┤
   │ │ MC/DC          各条件が単独で結果を変えることを確認      │ 航空・医療で要求
   │ ├──────────────────────────────────────────────────────┤
   │ │ 複合条件網羅(C2) a,bの真偽の全組合せ（4通り）            │ コスト高
   │ ├──────────────────────────────────────────────────────┤
   │ │ 分岐網羅（C1）   ifのtrue/falseを両方通す（2通り）★実務標準│
   │ ├──────────────────────────────────────────────────────┤
   │ │ 命令網羅（C0）   全行を1回通す（1通りで100%になる）      │ 甘すぎる
   │ └──────────────────────────────────────────────────────┘
   ▼ 緩い

  上の例では：
   C0 → judge(1,1) の1本で【100%】になってしまう
   C1 → judge(1,1) と judge(0,0) の2本が必要
   C2 → (T,T)(T,F)(F,T)(F,F) の4本が必要
```

> **実務の標準は C1（分岐網羅）です。**
> 「カバレッジ80%」と言うとき、それがC0なのかC1なのかで意味がまったく違います。
> **C0の数字だけを見ているチームは、実態よりかなり甘い数字を見ています。**

#### 主要ツールでの呼び名

| 表示名 | 対応 | 見るべきか |
|---|---|---|
| Statements / Lines | C0 | 参考程度 |
| **Branches** | **C1** | **ここを見る** |
| Functions | 関数網羅 | 未着手箇所の発見に有用 |

---

### 11-9. カバレッジ戦略 — 高ければいいわけではない

ここが本節の本題です。**カバレッジ100%は、ほとんどのプロダクトで不合理な目標です。**

#### 理由① 収穫逓減とコストの逆転

```
 テストの価値
    ▲
    │        ┌─────────────────── 頭打ち
    │      ／
    │    ／  ← ここまでで価値の大半を得ている
    │  ／
    │／
    └────┬──────┬──────┬──────┬────▶ カバレッジ
        40%    70%    85%   100%

 コスト
    ▲                            ／  ← 最後の10〜15%に
    │                        ／       全体の半分以上の労力
    │                    ／
    │ ＿＿＿＿＿＿＿＿／
    └───────────────────────────▶ カバレッジ

  → 70〜85%あたりに「費用対効果の折り返し点」がある
    （数字は目安。プロダクト特性で動く）
```

最後の数%に含まれるのは、たいてい**「起こしようのないエラー分岐」「フレームワークの型合わせ」「防御的なdefault句」**です。
ここを埋めるために、実装をねじ曲げたり、テストのためだけの分岐を足すのは本末転倒です。

#### 理由② 指標が目標になると、指標として壊れる（グッドハートの法則）

```
 「カバレッジ80%必達」をノルマにすると何が起きるか

   ✗ assertのないテストが量産される
   ✗ getter/setterやDTOのテストで数字を稼ぐ
   ✗ 難しくて本当にテストすべき箇所は後回しにされる
   ✗ テストが「通すためのもの」になり、誰も中身を読まなくなる

   結果：カバレッジは上がったが、バグは減らない
```

> **カバレッジは「目標」ではなく「健康診断の数値」です。**
> 体重計の数字を目標にして水を抜いても健康にならないのと同じです。

#### 理由③ 数字より「どこがカバーされているか」が重要

```
  同じ「カバレッジ 70%」でも、中身は正反対になりうる

  ❌ 悪い70%                       ✅ 良い70%
  ┌────────────────────┐          ┌────────────────────┐
  │ ドメインロジック  30% │          │ ドメインロジック  95% │
  │ ユースケース     40% │          │ ユースケース     85% │
  │ DTO/getter    100% │          │ DTO/getter      0% │
  │ 設定・定数     100% │          │ 設定・定数       0% │
  └────────────────────┘          └────────────────────┘
    重要な所ほど穴だらけ              重要な所は厚く、些末な所は捨てている
```

**層別に目標を分けるのが正解です。**

| 層 | 目標の目安 | 理由 |
|---|---|---|
| ドメイン（業務ルール） | 90〜100% | バグが金銭・信用に直結。依存がなく書きやすい |
| ユースケース | 70〜90% | 主要シナリオと異常系を押さえる |
| アダプタ（Repository実装等） | 50〜70% | 統合テストで担保。単体で追いすぎない |
| UI・画面 | 低くてよい | E2Eで主要導線のみ |
| DTO・設定・自動生成コード | 計測対象から除外 | テストする価値がない |

#### プロダクトの性質でカバレッジ方針は変わる

**「適正なカバレッジ」は技術ではなくビジネスの問題です。**
判断軸は「**バグが起きたとき、何を失うか**」の一点です。

```
        失敗のコスト 大
              ▲
   医療機器 ●  │  ● 決済 / 金融取引
   航空制御 ●  │  ● 認証・認可基盤
              │  ● 課金計算
   ───────────┼───────────────────▶ 変更頻度 大
              │  ● 業務Webアプリ
   社内バッチ ● │  ● 管理画面
              │  ● 検証用プロトタイプ
        失敗のコスト 小        ● 使い捨てスクリプト
```

| プロダクトの性質 | 方針 | 目安 |
|---|---|---|
| **医療・航空・鉄道**（人命） | MC/DCなど規格が要求する網羅を厳格に満たす | 規格準拠（100%が必須なことも） |
| **決済・金融・認証**（金銭・信用） | ドメイン層は極めて厚く。異常系を重点的に | ドメイン95%+ |
| **一般的な業務Webアプリ** | 層別に配分。ロジック厚く、繋ぎ込みは統合テストで | 全体70〜80% |
| **社内ツール・管理画面** | 主要導線のみ。壊れても直せばよい | 40〜60% |
| **MVP / PoC / 仮説検証** | **意図的に薄くする**。捨てる前提のコードにテストは負債 | 主要ロジックのみ |
| **OSSライブラリ・SDK** | 利用者が多く後方互換の責任がある → 非常に厚く | 90%+ |
| **使い捨てスクリプト** | 書かない判断も正しい | ー |

#### 特に強調したい2点

**① MVP・検証フェーズで100%を目指すのは有害**

```
  仮説検証中のコード
   → 来月には作り直す、あるいは丸ごと消える可能性が高い
   → テストは「そのコードを固定する」ので、捨てにくくなる
   → スピードも落ち、捨てる決断も鈍る

  ただし「決済」「個人情報」に触る部分だけは例外なく守る
```

**② 逆に、後から上げるのは非常に難しい**

```
  カバレッジ 20% のレガシーコードを 80% にする
   → テスト不能な設計になっていることが多い
   → まず設計を直す必要がある（第3〜8章の作業）
   → 「テストを書く」ではなく「テストできる形にする」プロジェクトになる

  ＝ 低く始めるのは自由だが、上げるのは高くつく。
     少なくとも「ドメイン層だけは最初から守る」のが現実的な折衷案。
```

#### リスクベースで優先順位をつける

全体を一律に上げるのではなく、**2軸で優先度を決めます。**

```
              変更頻度 高
                  ▲
   ┌──────────────┼──────────────┐
   │ ② 中優先      │ ① 最優先 ★    │
   │ よく変わるが   │ よく変わり、   │
   │ 壊れても軽微   │ 壊れると重大   │
   │              │ → 最も厚く    │
影 ├──────────────┼──────────────┤ 影
響 │ ④ 低優先      │ ③ 高優先      │ 響
小 │ 触らないし    │ めったに変えないが│ 大
   │ 軽微          │ 壊れると致命的  │
   │ → 書かない    │ → 一度厚く書く │
   └──────────────┼──────────────┘
              変更頻度 低
```

- **①（高頻度×高影響）**＝ 課金計算、権限判定など。**ここに全力を投じる**
- **③（低頻度×高影響）**＝ マイグレーション、締め処理。回数は少ないので一度しっかり書く
- **④（低頻度×低影響）**＝ 書かない勇気を持つ

**変更頻度は `git log` から機械的に出せます。**「よく直っているファイル」＝バグが出やすい場所です。

```bash
# 変更回数の多いファイル上位20件（バグの温床候補）
git log --format=format: --name-only | grep -v '^$' | sort | uniq -c | sort -rn | head -20
```

#### 差分カバレッジという実践解

既存プロジェクトで最も効くのがこれです。

```
❌ 全体カバレッジで縛る
   「全体80%まで上げてから機能開発」→ 何ヶ月も止まる。現実的でない

✅ 差分カバレッジ（Diff Coverage）で縛る
   「このPRで追加・変更した行は80%以上」
   → 既存の負債はそのまま、新しい負債だけは作らせない
   → 触った箇所から自然に改善していく（第12章のボーイスカウトルール）
```

```
 全体カバレッジの推移

  80%│                                    ＿＿／
     │                            ＿＿／
  60%│                    ＿＿／
     │            ＿＿／
  40%│   ＿＿／
     │／
     └────────────────────────────────────▶ 時間
      差分カバレッジを守るだけで、全体は自然に上がっていく
```

**運用ルール**
- CIでは「絶対値」ではなく**「前回より下げない」**（Ratchet方式）を条件にする
- 除外設定（生成コード、DTO等）は設定ファイルに明記し、レビュー対象にする

#### カバレッジの「質」を測る — ミューテーションテスト

「そのテストは本当に壊れたら気づけるのか?」を検証する手法です。

```
  ① ツールがソースを意図的に書き換える（ミュータント）
       a > b   →   a >= b
       +       →   -
       return x  →  return null

  ② テストを実行する

  ③ テストが失敗した  → ✅ Killed（そのテストは有効）
     テストが通った    → ❌ Survived（そのテストは何も見ていない）
```

```
  カバレッジ  95%   … コードは通っている
  ミューテーションスコア 40% … しかし壊しても6割は気づけない
                              ＝ assertが不足している証拠
```

**ツール例**：Stryker（JS/TS）、PIT（Java）、mutmut（Python）

重いので全体には回しません。**ドメイン層など「絶対に間違えられない箇所」に限定して**使うのが現実的です。

#### まとめ：カバレッジとの正しい付き合い方

```
  ┌────────────────────────────────────────────────┐
  │ ✅ すること                                      │
  ├────────────────────────────────────────────────┤
  │ ・C1（分岐）を見る                                │
  │ ・層別・リスク別に目標を分ける                      │
  │ ・差分カバレッジで「悪化させない」                   │
  │ ・低い箇所を「発見の手がかり」として使う              │
  │ ・除外設定を明示し、合意する                        │
  ├────────────────────────────────────────────────┤
  │ ❌ しないこと                                     │
  ├────────────────────────────────────────────────┤
  │ ・全体一律の数値ノルマを課す                        │
  │ ・100%を目標にする                                │
  │ ・数字のためだけのテストを書く                      │
  │ ・カバレッジが高いことを「品質が高い」と読み替える     │
  └────────────────────────────────────────────────┘
```

> ### 問うべきは「何%か」ではなく、
> ### **「このプロダクトで壊れたら困るものが、テストで守られているか」**

### 11-10. TDD（テスト駆動開発）の基本

必須ではありませんが、**「テストしやすい設計」が自然に手に入る**手法です。

```
        ┌──────────────┐
   ┌───▶│  🔴 Red      │ 失敗するテストを先に書く
   │    │  （仕様を決める）│
   │    └──────┬───────┘
   │           ▼
   │    ┌──────────────┐
   │    │  🟢 Green    │ とにかく通す（汚くてよい）
   │    └──────┬───────┘
   │           ▼
   │    ┌──────────────┐
   └────┤  🔵 Refactor │ テストを盾に、安心して整理する
        └──────────────┘
        1サイクル：数分〜十数分
```

**TDDの本質は「テストを書くこと」ではなく、**
**「使う側の視点でインターフェースを先に決めること」**です。
先にテストを書くと、使いにくいAPIは自然に排除されます。

### 11-11. テストのアンチパターン

| アンチパターン | 何が起きるか |
|---|---|
| 実装詳細をテストする | リファクタのたびに壊れる。テストが足枷になる |
| 1テストに10個のassert | 落ちた原因が分からない |
| テスト内にif/loopがある | テスト自体にバグが入る |
| 巨大な共通セットアップ | そのテストの前提が読めない |
| Flakyテストを放置 | 「また誤検知でしょ」と誰も見なくなる（最悪） |
| コミット前にコメントアウト | 存在しないのと同じ |

**Flakyテスト（たまに落ちるテスト）は最優先で潰してください。**
1本でもあると、チーム全体がテスト結果を信用しなくなります。

```javascript

class InMemoryUserRepository implements UserRepository {
  #users = new Map();

}

const repo = new InMemoryUserRepository();   // 使い回せる。準備1行
```

## 第12章 ツールによる品質の自動化

テストは強力ですが、**書くコストがかかり、人間が書き忘れます。**
一方、機械が確実に・無料で・一瞬で検出できる問題も大量にあります。

> **原則：機械に任せられるものは、1つ残らず機械に任せる。**
> 人間のレビューは、機械にできないこと（命名・責務分割・設計判断）だけに集中させる。

### 12-1. 品質保証は「多層防御」で考える

単一の手段で品質は守れません。**フィードバックが速い順に並べた多層構造**にします。

```
 検出が早い＝修正コストが安い
     ▲
     │  ┌──────────────────────────────────────┐
     │  │ ① フォーマッター  保存時 / 0.1秒        │ スタイルの統一
     │  ├──────────────────────────────────────┤
     │  │ ② 型チェック     入力中 / エディタ上     │ 型の不整合
     │  ├──────────────────────────────────────┤
     │  │ ③ リンター       保存時 / 数秒          │ バグの温床・規約違反
     │  ├──────────────────────────────────────┤
     │  │ ④ ユニットテスト  コミット前 / 数秒〜     │ ロジックの正しさ
     │  ├──────────────────────────────────────┤
     │  │ ⑤ 統合・E2E      CI / 数分              │ 繋ぎ込み・シナリオ
     │  ├──────────────────────────────────────┤
     │  │ ⑥ コードレビュー  PR / 数時間〜           │ 設計・命名・意図
     │  ├──────────────────────────────────────┤
     │  │ ⑦ 監視・アラート  本番 / 事後             │ 想定外
     │  └──────────────────────────────────────┘
     ▼
 検出が遅い＝修正コストが高い（本番障害は最悪）
```

#### バグ修正コストは指数関数的に増える

```
 修正コスト
    ▲
    │                                        ██ 本番
    │                                  ██
    │                          ██  レビュー
    │                  ██  CI
    │          ██ コミット時
    │  ██ エディタ上
    └──────────────────────────────────────▶ 検出タイミング

  → 「できるだけ左側で捕まえる」ことに投資する価値がある
```

### 12-2. フォーマッター — 議論をゼロにする

**役割：コードの見た目を機械的に統一する。**（インデント、改行、クォート、末尾カンマ）

| 言語 | 代表的ツール |
|---|---|
| JavaScript / TypeScript | Prettier, Biome |
| Python | Black, Ruff format |
| Go | gofmt（標準搭載） |
| Rust | rustfmt |
| Java / Kotlin | google-java-format, ktlint |

**最大の価値は「見た目が綺麗になること」ではありません。**

```
❌ フォーマッター導入前のレビュー
  「インデントが揃ってません」
  「ここはシングルクォートで」        ← 本質的でない指摘に時間を溶かす
  「改行を入れてください」

✅ 導入後のレビュー
  「この関数は2つの責務を持っていませんか?」  ← 人間にしかできない議論
```

**さらに副次効果として、差分（diff）が綺麗になります。**
書式の揺れがなくなるので、Gitの差分＝本当の変更だけになります。

**運用ルール**
- 設定で揉めない。**デフォルト設定をそのまま使う**のが最善
- 保存時に自動実行（エディタ設定をリポジトリで共有する）
- 導入時は「全ファイル一括整形」を**単独のコミット**で行う（差分が混ざらないように）

### 12-3. リンター — バグの温床を静的に見つける

**役割：文法的には正しいが、危険・非推奨なコードを指摘する。**

| 言語 | 代表的ツール |
|---|---|
| JavaScript / TypeScript | ESLint, Biome |
| Python | Ruff, Pylint, flake8 |
| Go | golangci-lint, go vet |
| Ruby | RuboCop |
| Java | SpotBugs, Checkstyle, ErrorProne |

#### リンターが検出するもの

```
 ┌─────────────────────────────────────────────┐
 │ ① 明らかなバグ                                │
 │    未使用変数、到達不能コード、== と === の混同 │
 │    awaitの付け忘れ、Promiseの投げっぱなし       │
 ├─────────────────────────────────────────────┤
 │ ② 危険な書き方                                │
 │    any型の使用、eval、非推奨API                │
 ├─────────────────────────────────────────────┤
 │ ③ 複雑度の警告  ★設計に直結★                  │
 │    循環的複雑度、関数の行数、ネストの深さ、引数の数 │
 ├─────────────────────────────────────────────┤
 │ ④ アーキテクチャ違反  ★第7章で扱った内容★       │
 │    循環import、層をまたぐ禁止import             │
 └─────────────────────────────────────────────┘
```

#### ③④は「設計原則の自動執行」である

ここが本資料の重要な接続点です。**第3章・第7章で学んだ原則は、ツールで強制できます。**

```javascript
// ESLint：第3章の「関数は短く、ネストは浅く」を機械的に守らせる
{
  "complexity": ["warn", 10],          // 循環的複雑度の上限
  "max-depth": ["warn", 3],            // ネストの深さ
  "max-lines-per-function": ["warn", 50],
  "max-params": ["warn", 4],
  "import/no-cycle": "error"           // 第7章 ADP（循環依存の禁止）
}
```

```javascript
// dependency-cruiser：第8章の「依存の向き」を強制する
{
  name: 'domain-must-not-depend-on-infra',
  severity: 'error',
  from: { path: '^src/.*/domain' },
  to:   { path: '^src/.*/infrastructure' }
}
```

> **設計ルールは、口頭やドキュメントでは守られません。CIで落ちるようにして初めて守られます。**

### 12-4. 型チェック — 実行せずに矛盾を見つける

| 言語 | 手段 |
|---|---|
| JavaScript | TypeScript |
| Python | mypy, Pyright（型ヒント） |
| Ruby | Sorbet, RBS |

```
 型がないと必要なテスト            型があると不要になるテスト
 ├─ 引数にnullを渡したら?      →  型で禁止（テスト不要）
 ├─ 数値の代わりに文字列を渡したら? → 型で禁止（テスト不要）
 └─ 存在しないプロパティ参照     →  型で検出（テスト不要）

  ＝ 型はテストの一部を肩代わりする「最も安価なテスト」
```

**型の設計上の価値**

```typescript
// ❌ 型が弱い：不正な状態を表現できてしまう
type Order = { status: string; cancelledAt?: Date };

// ✅ 型で不正な状態を作れなくする
type Order =
  | { status: 'pending' }
  | { status: 'shipped'; shippedAt: Date }
  | { status: 'cancelled'; cancelledAt: Date };
```

> **「不正な状態を、そもそも表現できなくする」** — これは型で実現する設計原則です。
> テストは「不正が起きないこと」を確認しますが、型は「不正を存在させない」ことができます。

### 12-5. その他の静的解析

| 種類 | 内容 | ツール例 |
|---|---|---|
| セキュリティ | 脆弱性パターンの検出 | Semgrep, CodeQL, Snyk Code |
| 依存パッケージ | 既知の脆弱性・ライセンス | Dependabot, `npm audit`, Renovate |
| シークレット検出 | APIキー等の誤コミット | gitleaks, git-secrets |
| 重複コード | コピペの検出（DRY違反） | jscpd, PMD-CPD |
| 総合品質 | 複雑度・重複・カバレッジの可視化 | SonarQube |
| 依存構造 | 循環・レイヤ違反 | dependency-cruiser, ArchUnit, import-linter |

**特に「シークレットの誤コミット」と「依存パッケージの脆弱性」は、
設計の巧拙に関係なく事故が起きるので、最初期から入れてください。**

### 12-6. いつ実行するか — フィードバックループの設計

同じツールでも、**実行タイミングによって価値が変わります。**

```
 ①エディタ         ②保存時        ③コミット時        ④CI（PR）
 （入力中）        （自動修正）     （pre-commit）     （最終防衛線）
    │                │               │                  │
    ▼                ▼               ▼                  ▼
 型エラー表示     フォーマット      軽量Lint          全Lint
 Lint警告表示     import整理       型チェック         全テスト
                                  変更分のテスト      ビルド
                                  シークレット検出     E2E
    │                │               │                  │
  0.1秒           0.5秒            5〜15秒            3〜10分
    └────────────────┴───────────────┴──────────────────┘
              早い層で捕まえるほど、開発体験が良い

 ⚠️ pre-commitに重い処理を入れない
    → 開発者が `--no-verify` で回避するようになり、意味を失う
```

#### 責務の分担

```
  ┌────────────────┬──────────────────────────────┐
  │ pre-commit     │ 速いもの・自動修正できるもの     │
  │                │ フォーマット、変更分のLint       │
  ├────────────────┼──────────────────────────────┤
  │ CI             │ 網羅的なもの・時間がかかるもの    │
  │                │ 全テスト、ビルド、E2E、依存監査   │
  └────────────────┴──────────────────────────────┘

  CIは「絶対に妥協しない門番」にする。
  マージにはCI通過を必須にする（ブランチ保護ルール）。
```

### 12-7. CIパイプラインの基本形

```
  git push
     │
     ▼
 ┌─────────────┐
 │ 1. Lint     │ ── 失敗 ──▶ ✗ 即終了（速いものから流す）
 │    Format   │
 └──────┬──────┘
        ▼
 ┌─────────────┐
 │ 2. 型チェック │ ── 失敗 ──▶ ✗
 └──────┬──────┘
        ▼
 ┌─────────────┐
 │ 3. ユニット   │ ── 失敗 ──▶ ✗
 │    テスト    │
 └──────┬──────┘
        ▼
 ┌─────────────┐
 │ 4. ビルド    │ ── 失敗 ──▶ ✗
 └──────┬──────┘
        ▼
 ┌─────────────┐
 │ 5. 統合/E2E  │ ── 失敗 ──▶ ✗
 └──────┬──────┘
        ▼
     ✓ マージ可能

  ポイント：速くて落ちやすいものを前に置く（フェイルファスト）
```

### 12-8. 既存プロジェクトへの導入手順

「いきなり全部入れたら、警告が3000件出て心が折れた」はよくある失敗です。

```
 Step 1  フォーマッター導入
         全ファイル一括整形を「単独コミット」で実施
         （ここは議論せず、デフォルト設定で決め打つ）
              │
 Step 2  リンター導入（警告レベルで）
         既存の違反は一旦 warn。新規違反だけ error にする
              │
 Step 3  CIに組み込む
         「これ以上悪化させない」ラインを引く（Ratchet戦略）
              │
 Step 4  重要箇所からテストを追加
         全体を目指さない。「よく壊れる場所」「これから直す場所」から
              │
 Step 5  ルールを段階的に error へ昇格
         直した分だけ厳しくしていく
```

> **鉄則：既存コードを全部直そうとしない。「新しく書く部分だけは綺麗にする」から始める。**
> これを**ボーイスカウトルール**（来たときより少しだけ綺麗にして帰る）と言います。

### 12-9. ツールでは守れないもの

自動化には明確な限界があります。

```
 ┌──────────────────────────────┬──────────────────────────────┐
 │  機械が守れる（自動化する）      │  人間しか守れない（レビューする）│
 ├──────────────────────────────┼──────────────────────────────┤
 │ ・書式、インデント              │ ・命名が適切か（第3章）         │
 │ ・未使用変数、型の不整合         │ ・責務の分け方が妥当か（第5章）  │
 │ ・関数の行数、ネストの深さ        │ ・その抽象化は必要か（YAGNI）   │
 │ ・循環依存、レイヤ違反           │ ・ドメインの理解が正しいか       │
 │ ・テストが通るか                │ ・テストが本質を検証しているか    │
 │ ・カバレッジの数値              │ ・仕様の妥当性そのもの           │
 └──────────────────────────────┴──────────────────────────────┘

  機械が左側を全部片付けるからこそ、
  レビューで右側（＝本資料の第1〜8章の内容）に集中できる。
```

**これが本章の結論です。**
ツールは設計の代わりにはなりませんが、**設計を議論するための時間を作ってくれます。**

**章末チェック**
- [ ] 品質保証が多層防御であることを説明できる
- [ ] 早期検出ほどコストが安い理由が言える
- [ ] フォーマッターの本当の価値がレビュー効率だと理解した
- [ ] Lintで設計原則（複雑度・循環依存）を強制できると知っている
- [ ] pre-commitとCIの役割分担ができる
- [ ] 既存プロジェクトへの導入手順が言える

## 第13章 Git・コミット・コードレビュー

第12章で「機械にできないことは人間がレビューする」と書きました。本章はその**人間側の仕組み**の話です。

> **コードレビューは「間違い探し」ではありません。**
> 設計の議論をする場であり、知識を共有する場であり、コードを「チームのもの」にする場です。

### 13-1. コミットは「変更の意味の単位」

```
❌ 1コミット＝1日の作業              ✅ 1コミット＝1つの意味
 ┌──────────────────────────┐      ┌──────────────────────┐
 │ "いろいろ修正"             │      │ "注文APIに在庫チェックを追加"│
 │  ・機能追加                │      ├──────────────────────┤
 │  ・バグ修正                │ ──▶  │ "注文一覧のN+1問題を修正"   │
 │  ・変数名の一括変更         │      ├──────────────────────┤
 │  ・フォーマット整形         │      │ "全ファイルをPrettierで整形" │
 └──────────────────────────┘      └──────────────────────┘
   ・レビューできない                  ・1つずつレビューできる
   ・revertできない                   ・問題のあるものだけ revert できる
   ・bisectで原因を追えない            ・git bisect が機能する
```

> **鉄則：フォーマット整形・リネームは、機能変更と絶対に混ぜない。**
> 混ぜると差分の99%がノイズになり、本当の変更が見えなくなります。

### 13-2. コミットメッセージ

```
   <型>: <何をしたか（現在形・50字以内）>
   （空行）
   なぜそうしたか / 背景 / トレードオフ
   （空行）
   Refs: #123
```

```
❌ 悪い例                          ✅ 良い例
   "修正"                            "fix: 注文合計の税計算で端数が1円ずれる問題を修正"
   "wip"                             
   "レビュー指摘対応"                  本文：切り捨てと四捨五入が混在していたため、
   "update UserService.ts"           仕様書に合わせて切り捨てに統一した。
                                     Refs: #452
```

**型の例（Conventional Commits）**

| 型 | 意味 |
|---|---|
| `feat` | 機能追加 |
| `fix` | バグ修正 |
| `refactor` | 挙動を変えない内部改善 |
| `test` | テストの追加・修正 |
| `docs` | ドキュメント |
| `chore` | ビルド・依存更新など |

**「何をしたか」はdiffを見れば分かります。メッセージの価値は「なぜ」にあります。**（第2章のコメント論と同じ）

### 13-3. プルリクエストは小さく

```
   レビュー品質
      ▲
      │ ██
      │ ████
      │ ██████
      │ ████████
      │ ██████████▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁
      └──────────────────────────────────▶ 変更行数
        〜200行      400行      1000行〜
        きちんと見る   流し読み    LGTM（見ていない）★

   400行を超えると、レビューは実質機能しなくなる
```

**分割のコツ**

```
   大きな機能を1PRで出さない

   ① リファクタのみ（挙動を変えない）     ← 先にマージ
   ② インターフェース・型の追加
   ③ 実装
   ④ 画面との接続

   → 各PRが独立してレビュー可能・revert可能になる
```

### 13-4. レビューの観点は「機械にできないこと」に絞る

```
 ┌───────────────────────────────────────────────────┐
 │ レビューで見るべきこと（優先度順）                    │
 ├───────────────────────────────────────────────────┤
 │ ① 仕様として正しいか（そもそも作るものが合っているか） │
 │ ② 設計：責務の分け方・依存の向き（第4〜8章）          │
 │ ③ 名前：意図が伝わるか（第2章）                     │
 │ ④ エラー処理・異常系の考慮漏れ（第10章）             │
 │ ⑤ テストが本質を検証しているか（第11章）             │
 │ ⑥ セキュリティ上の懸念（第15章）                    │
 ├───────────────────────────────────────────────────┤
 │ 見なくていいこと（機械に任せる：第12章）              │
 │  書式・インデント・未使用変数・import順               │
 └───────────────────────────────────────────────────┘
```

### 13-5. 指摘の仕方 — 人ではなくコードに向ける

```
❌ 「なんでこう書いたんですか」        ✅ 「ここは〇〇にすると△△の点で良くなりそうです」
❌ 「これは間違いです」               ✅ 「〜という前提だとバグになりませんか?」
❌ 好みの押し付け                     ✅ 理由（原則・トレードオフ）とセットで伝える
```

**指摘に「重み」を明示すると、驚くほど摩擦が減ります。**

```
   [MUST]    直してほしい（マージ条件）
   [SHOULD]  直した方がよい（議論の余地あり）
   [IMO]     好みの範囲。従わなくてよい
   [NITS]    些細な指摘
   [ASK]     単なる質問。学習のため
   [GOOD]    良い実装。積極的に書く ★
```

**受ける側の姿勢**

```
   ・コードへの指摘は、自分への攻撃ではない
   ・「なぜそう書いたか」を説明する（それ自体が設計の言語化になる）
   ・納得できないときは議論してよい。従うことが目的ではない
   ・議論が長引いたら、同期で5分話す（テキストは誤解を生む）
```

### 13-6. ブランチ戦略は「小さく始める」

```
   GitHub Flow（推奨・シンプル）
   main ──●──────●──────●──────▶ 常にデプロイ可能
           ╲    ╱ ╲    ╱
            ●──●   ●──●   短命なfeatureブランチ

   Git Flow（複雑。リリース版を並行管理する製品向け）
   → 多くのWebサービスには過剰。まずGitHub Flowで十分
```

**共通ルール**
- `main` へは必ずPR経由（直接pushを禁止する設定にする）
- CIが通らないとマージできないようにする（第12章）
- ブランチは短命に。長生きするほどコンフリクトが増える

**章末チェック**
- [ ] コミットを意味単位で分ける理由が言える
- [ ] フォーマット整形を機能変更と混ぜてはいけない理由が説明できる
- [ ] PRが大きいとレビューが機能しなくなる理由が言える
- [ ] レビューで見るべき観点／見なくていい観点を区別できる

## 第14章 ログと可観測性

テストは「リリース前」に守る仕組みでした。**ログは「リリース後」に守る仕組み**です。

> **障害対応の速さは、ログの設計で決まります。**
> 「再現できません」と言うしかない状況を作らないための章です。

### 14-1. ログは誰のために書くのか

```
   3時間後の自分／深夜に叩き起こされた同僚

   良いログ                          悪いログ
   ┌──────────────────────────┐    ┌──────────────────────────┐
   │ いつ・誰が・何をして         │    │ "error"                  │
   │ 何が起きたかが1行で分かる     │    │ "処理開始"                │
   │ 相関IDで一連の流れを追える    │    │ "OK"                     │
   └──────────────────────────┘    └──────────────────────────┘
   → 5分で原因特定                   → 再現待ち。原因不明で終わる
```

### 14-2. ログレベルの使い分け

| レベル | 意味 | 対応の要否 |
|---|---|---|
| `ERROR` | 処理が失敗し、対応が必要 | **人が対応する** |
| `WARN` | 異常ではないが注視すべき（リトライ成功、非推奨API使用） | 監視する |
| `INFO` | 業務上の重要イベント（注文確定、ログイン） | 平常時の記録 |
| `DEBUG` | 開発時の詳細 | 本番では通常オフ |

```
   ⚠️ 最悪のアンチパターン：ERRORの乱発

   ERRORが1日1万件出る
      → 誰も見なくなる
      → 本物の障害がその中に埋もれる
      → 「アラート疲れ」

   原則：ERRORは「人が対応すべきもの」だけ。
        対応不要ならWARN以下に落とす。
```

### 14-3. 構造化ログ

```
❌ 文字列を組み立てる（検索・集計できない）
   log.info(`ユーザー${userId}が注文${orderId}を確定しました`);

✅ 構造化する（機械が処理できる）
   log.info('order.confirmed', {
     userId, orderId, amount, traceId
   });
```

```
   構造化の恩恵

   "エラー率をユーザー別に集計したい"
   "特定の注文の処理を最初から最後まで追いたい"
   → 構造化されていれば、クエリ一発で出る
   → 文字列だと正規表現との格闘になる
```

### 14-4. 相関ID（トレースID）

**分散した処理を1本の線につなぐ、最も費用対効果の高い仕組みです。**

```
   リクエスト受信
     traceId=abc123 を発行
        │
        ├──▶ 認証サービス      log(traceId=abc123)
        ├──▶ 在庫サービス      log(traceId=abc123)
        ├──▶ 決済サービス      log(traceId=abc123) ★ここで失敗
        └──▶ DB              log(traceId=abc123)

   → traceId=abc123 で検索すれば、一連の流れが時系列で並ぶ
```

### 14-5. 絶対にログに出してはいけないもの

```
 ┌──────────────────────────────────────────────┐
 │ ★ パスワード、トークン、APIキー、秘密鍵          │
 │ ★ クレジットカード番号、セキュリティコード        │
 │ ★ 個人情報（氏名・住所・電話・メール）★法令に注意 │
 │ ★ リクエストボディの丸ごとダンプ                 │
 └──────────────────────────────────────────────┘

   対策：IDや下4桁など「識別できるが復元できない」形にする
        userId=1234 ○   /   email=xxx@example.com ✗
        card=****1234 ○  /   card=4111111111111111 ✗

   ⚠️ ログは長期保存され、多くの人がアクセスできる。
      「一度出したら消せない」前提で設計する。
```

### 14-6. 可観測性の3本柱

```
   ┌──────────┬────────────────────────┬──────────────────┐
   │ ログ      │ 「何が起きたか」の記録     │ 個別事象の調査     │
   ├──────────┼────────────────────────┼──────────────────┤
   │ メトリクス │ 数値の時系列（率・量・時間）│ 異常の検知・傾向   │
   │           │ エラー率、レイテンシ、CPU  │                  │
   ├──────────┼────────────────────────┼──────────────────┤
   │ トレース   │ 処理の流れと各区間の時間   │ ボトルネック特定   │
   └──────────┴────────────────────────┴──────────────────┘

   メトリクスで「異常に気づき」、トレースで「場所を絞り」、
   ログで「原因を特定する」という役割分担。
```

**まず入れるべき最低限**

1. 相関IDの発行と伝播
2. 構造化ログ（JSON）
3. エラー率とレイテンシの監視・アラート
4. 未捕捉例外の通知（Sentry等）

**章末チェック**
- [ ] ERRORを乱発してはいけない理由が言える
- [ ] 構造化ログの利点が説明できる
- [ ] 相関IDが何を解決するか言える
- [ ] ログに出してはいけない情報を挙げられる

## 第15章 セキュアコーディングの基礎

セキュリティは専門分野ですが、**事故の大半は基本的な不注意から起きます。**
本章は「初心者が最低限やらかさないため」の範囲に絞ります。

> **原則：入力は信用しない。出力は文脈に応じてエスケープする。秘密は
> コードに書かない。**

### 15-1. すべての入力を信用しない

```
   信用してはいけないもの（＝外部からの入力すべて）

   ┌───────────────────────────────────────────┐
   │ フォーム入力 / URLパラメータ / クエリ文字列    │
   │ HTTPヘッダー / Cookie                       │
   │ アップロードファイル（名前・中身・拡張子）      │
   │ 外部APIのレスポンス ★忘れがち                │
   │ 環境変数・設定ファイル                       │
   └───────────────────────────────────────────┘

   ⚠️ 「フロントエンドで検証しているから大丈夫」は誤り。
      フロントの検証はUXのため。攻撃者はAPIを直接叩く。
      → サーバー側で必ず再検証する
```

```
   検証は「許可するものを列挙」する（ホワイトリスト方式）

   ❌ ブラックリスト：危険な文字を除去する → 抜け道が必ずある
   ✅ ホワイトリスト：許可する形式のみ通す  → 想定外は全部弾ける
```

### 15-2. 代表的な脆弱性と対策

```
 ┌──────────────────┬──────────────────────────────────────┐
 │ SQLインジェクション │ 文字列連結でSQLを作らない                │
 │                  │ → プレースホルダ／ORMを必ず使う           │
 ├──────────────────┼──────────────────────────────────────┤
 │ XSS              │ HTMLに値を埋める際にエスケープ             │
 │                  │ → フレームワークの自動エスケープを切らない  │
 │                  │ → innerHTML / dangerouslySetInnerHTML禁止│
 ├──────────────────┼──────────────────────────────────────┤
 │ CSRF             │ トークン検証、SameSite Cookie             │
 ├──────────────────┼──────────────────────────────────────┤
 │ 認可の欠落 ★最多  │ 「ログイン済み」と「その人が触っていい」は別 │
 │                  │ → 必ずリソース所有者を毎回検証する         │
 ├──────────────────┼──────────────────────────────────────┤
 │ 秘密情報の漏洩    │ ソースにキーを書かない、ログに出さない       │
 ├──────────────────┼──────────────────────────────────────┤
 │ 脆弱な依存関係    │ ライブラリを更新する（自動監視を入れる）     │
 └──────────────────┴──────────────────────────────────────┘
```

```javascript
// ❌ SQLインジェクション
db.query(`SELECT * FROM users WHERE email = '${email}'`);

// ✅ プレースホルダ
db.query('SELECT * FROM users WHERE email = ?', [email]);
```

### 15-3. 認可漏れは最も多く、最も見つけにくい

```
   ❌ よくある事故
   GET /api/orders/12345
     → ログイン済みかどうかだけ確認して返す
     → IDを 12346 に変えると他人の注文が見える（IDOR）

   ✅ 必ず「その人のものか」を検証する
   const order = await repo.find(id);
   if (order.userId !== currentUser.id) throw new ForbiddenError();
```

**設計での防ぎ方**

```
   認可チェックを「書き忘れられる場所」に置かない

   ❌ 各Controllerで個別にif文 → 1箇所忘れたら穴が開く
   ✅ 共通のミドルウェア／リポジトリ層で常に絞り込む
      repo.findByUser(currentUser.id, orderId)
      ＝ 構造上、他人のデータを取得できない（第9章の考え方）
```

### 15-4. 秘密情報の扱い

```
 ┌────────────────────────────────────────────────┐
 │ ・APIキー・パスワードをコードに書かない            │
 │ ・.env をコミットしない（.gitignoreを最初に書く）  │
 │ ・秘密は環境変数／シークレットマネージャで注入       │
 │ ・誤コミットしたら「消す」だけでは不十分            │
 │   → Git履歴に残る。必ずキーをローテートする ★     │
 │ ・gitleaks等で自動検出（第12章）                 │
 └────────────────────────────────────────────────┘
```

### 15-5. パスワードと認証

```
   ・自前でハッシュ処理を実装しない
     → bcrypt / argon2 など実績あるライブラリを使う
   ・平文保存・可逆暗号化は論外
   ・自前で認証基盤を作らない（可能なら OIDC / IdP に任せる）
   ・エラーメッセージで情報を漏らさない
     ❌「そのメールアドレスは登録されていません」→ 存在有無が分かる
     ✅「メールアドレスまたはパスワードが正しくありません」
```

### 15-6. 「安全側に倒す」設計

```
   デフォルトを安全にする（Secure by Default）

   ❌ 明示的に禁止しない限り許可      → 設定漏れ＝穴
   ✅ 明示的に許可しない限り禁止      → 設定漏れ＝不便（安全）

   最小権限の原則
   ・DBユーザーに不要なDROP権限を与えない
   ・APIキーのスコープを絞る
   ・「とりあえず管理者権限」をやらない
```

### 15-7. コード例で確認する（Before / After）

#### 例1：SQLインジェクション

```javascript
// ❌ Before
const rows = await db.query(
  `SELECT * FROM users WHERE name LIKE '%${keyword}%' ORDER BY ${sortColumn}`
);
// keyword に "' OR '1'='1" を入れられると全件漏洩する

// ✅ After：値はプレースホルダ、識別子はホワイトリスト
const ALLOWED_SORT = { name: 'name', created: 'created_at' };
const column = ALLOWED_SORT[sortKey] ?? 'created_at';   // 許可リスト方式

const rows = await db.query(
  `SELECT * FROM users WHERE name LIKE ? ORDER BY ${column}`,
  [`%${keyword}%`]
);
```

#### 例2：XSS

```javascript
// ❌ Before
element.innerHTML = `<div>ようこそ ${userName} さん</div>`;
// userName に <img src=x onerror=...> を入れられると任意コードが動く

// ✅ After：テキストとして挿入する
const div = document.createElement('div');
div.textContent = `ようこそ ${userName} さん`;
element.replaceChildren(div);

// Reactなら {} での埋め込みは自動エスケープされる。
// dangerouslySetInnerHTML は原則使わない（使うならサニタイズ必須）
```

#### 例3：認可漏れ（IDOR）

```javascript
// ❌ Before：ログイン確認しかしていない

  const order = await orderRepo.findByIdForUser(req.params.id, req.user.id);
  if (!order) return res.status(404).end();   // 存在有無も漏らさない

#### 例5：認証エラーで情報を漏らさない

```

```javascript

## 第16章 ドキュメントとADR

第2章で「コメントには**なぜ**を書く」と学びました。
しかし**コードのどこにも書けない「なぜ」**があります。それを残すのが本章です。

### 16-1. ドキュメントの階層

```
 ┌──────────────────────────────────────────────────────┐
 │ 寿命：長い                                             │
 │  ADR（意思決定記録）  「なぜこの技術/構成を選んだか」     │
 │  アーキテクチャ概要     全体像・境界・依存の向き           │
 ├──────────────────────────────────────────────────────┤
 │  README             動かし方・開発の始め方 ★最優先       │
 │  API仕様            外部との契約（自動生成が理想）        │
 ├──────────────────────────────────────────────────────┤
 │  コード内コメント      なぜこの実装か（第2章）             │
 │  テストコード         仕様の実例（第11章）                │
 │ 寿命：短い（コードと一緒に変わる）                        │
 └──────────────────────────────────────────────────────┘

   下に行くほどコードに近く、腐りにくい。
   上に行くほど「コードからは絶対に分からない情報」を持つ。
```

> **原則：コードから読み取れることはドキュメントに書かない。**
> 二重管理になり、必ず片方が嘘になります。

### 16-2. ADR（Architecture Decision Record）

**「なぜこうなっているのか」を後から掘り起こせるようにする、軽量な記録です。**

```
   ADRがないと起きること

   3年後の新メンバー：「なんでこんな変な作りなんだ? 直そう」
        │
        ▼
   実は当時、〇〇という制約があってそうせざるを得なかった
        │
        ▼
   直した結果、同じ問題を踏み直す（車輪の再発明ならぬ、地雷の再発見）
```

**テンプレート（1件1ファイル、A4半分程度）**

```markdown
# ADR-0007: 注文検索にElasticsearchを採用する

## ステータス
承認済み（2026-03-10） / 置換：ADR-0012 により一部変更

## 背景
注文検索が月間1000万件を超え、RDBのLIKE検索で
レスポンスが5秒を超えるようになった。

## 決定
Elasticsearchを導入し、注文検索のみを移行する。

## 理由 / 検討した代替案
- RDBのフルテキストインデックス：日本語の形態素解析が弱く断念
- 自前のキャッシュ：更新頻度が高く整合性の担保が困難
- Elasticsearch：運用コストは増えるが、要件を満たす唯一の選択肢

## 結果 / トレードオフ
- 検索は100ms以下に改善
- 運用対象が1つ増える。インデックス再構築の手順書が必要
- 結果整合になるため、更新直後の検索は最大3秒遅れる
```

```
   ADRの3つのルール
   ① 短く（長いと書かれない）
   ② 変更しない（決定当時の記録。覆すときは新しいADRを書いて「置換」する）
   ③ リポジトリ内に置く（docs/adr/ に置き、PRでレビューする）
```

### 16-3. README に書くべきこと

```
   ✅ 最低限これだけ（新メンバーが今日動かせるか?）
   ┌──────────────────────────────────────┐
   │ ① これは何か（1〜3行）                  │
   │ ② 動かし方（コピペで動くコマンド）★      │
   │ ③ 開発の始め方（環境構築・テスト実行）    │
   │ ④ ディレクトリ構成の意図（第7章）        │
   │ ⑤ 主要な設計判断へのリンク（ADR）        │
   │ ⑥ 困ったときの連絡先                    │
   └──────────────────────────────────────┘

   ⚠️ READMEの鮮度は「新メンバーが詰まった回数」で測れる。
      詰まったら、その場でREADMEを直すのを習慣にする。
```

### 16-4. 腐らせないための仕組み

```
   ドキュメントは必ず腐る。前提にして設計する。

   ① コードから自動生成する（API仕様、型定義、依存グラフ）
   ② テストをドキュメントにする（第11章：テスト名＝仕様）
   ③ 変更と同じPRで更新する（PRテンプレートにチェック項目を入れる）
   ④ 置き場所を1つにする（散在＝どれが正か分からない＝全部信用されない）
   ⑤ 「消す」勇気を持つ。嘘のドキュメントは無いより有害 ★
```

**章末チェック**
- [ ] コードから読めることを書かない理由が言える
- [ ] ADRが何を防ぐか説明できる
- [ ] ADRを書き換えずに「置換」する理由が言える
- [ ] READMEに最低限必要な項目を挙げられる

## 第17章 リファクタリング — 既存コードを安全に直す

ここまでの原則は「これから書くコード」には使えます。
しかし現実の仕事の大半は、**すでにある汚いコードを直すこと**です。本章はその手順です。

> **リファクタリングの定義：外から見た振る舞いを変えずに、内部構造を改善すること。**
> **「振る舞いを変えない」が絶対条件です。**機能追加やバグ修正と同時にやってはいけません。

### 17-1. 大原則：テストなしにリファクタリングしてはいけない

```
   テストがない状態での「改善」

   ┌──────────────┐   直す   ┌──────────────┐
   │ 汚いが動くコード │ ──────▶ │ 綺麗だが壊れたコード│ ★最悪
   └──────────────┘         └──────────────┘
        誰も壊れたことに気づかない

   正しい順序
   ① まずテストを書く（今の振る舞いを固定する）
   ② テストが通ることを確認
   ③ 小さく直す → テスト → 直す → テスト …
   ④ 振る舞いが変わっていないことを保証したまま構造だけ改善
```

**「テストが書けないほど絡まっている」場合は、
まず**テストを書ける形にするための最小限の変更**（依存の注入など）から始めます。

```
   レガシーコード攻略の順番

   ① 変更したい箇所を見つける
   ② その周囲に「継ぎ目（Seam）」を作る
      … 依存を引数/コンストラクタに追い出す（第6章 DI）
   ③ 特性テスト（現状の振る舞いをそのまま固定するテスト）を書く
      ※「正しい振る舞い」ではなく「今の振る舞い」を記録する
   ④ ここでようやくリファクタリング
   ⑤ その後に機能変更
```

### 17-2. コードの臭い（Code Smells）カタログ

**「臭い」＝ 必ずしも悪ではないが、問題が隠れている可能性が高いサイン。**

```
 ┌──────────────────────┬──────────────────┬────────────────────┐
 │ 臭い                  │ 何を疑うか         │ 対処（参照章）        │
 ├──────────────────────┼──────────────────┼────────────────────┤
 │ 長すぎる関数           │ 責務過多           │ 関数抽出（第3章）     │
 │ 巨大なクラス（神クラス） │ 凝集度の低さ        │ クラス分割（第4・5章） │
 │ 長い引数リスト         │ 責務過多／まとまり   │ オブジェクト化        │
 │ 重複コード             │ DRY違反            │ 共通化（※3回目から）  │
 │ 深いネスト             │ 制御フローの複雑さ   │ 早期リターン（第3章）  │
 │ 巨大なif/switch連鎖    │ OCP違反            │ ポリモーフィズム（第5章）│
 │ 不適切な名前           │ 設計の曖昧さ        │ 改名（第2章）         │
 │ 特徴の横恋慕           │ 責務の置き場所が違う  │ メソッド移動          │
 │ （他クラスの値ばかり参照）│                   │                    │
 │ データの群れ           │ 概念が抽出できていない│ 値オブジェクト化       │
 │ （いつも一緒に渡る引数） │                   │                    │
 │ 変更の発散             │ CCP違反            │ パッケージ再編（第7章） │
 │ （1変更で複数箇所修正）  │                   │                    │
 │ 散弾銃手術             │ 責務が散らばっている  │ 集約する             │
 │ コメントだらけ         │ コードが説明不足     │ 名前と分割で解消（第2章）│
 └──────────────────────┴──────────────────┴────────────────────┘
```

### 17-3. 基本の手順（最も使う5つ）

```
   ① 関数の抽出（Extract Function）… 最頻出
      まとまった処理に名前をつけて切り出す

   ② 変数の抽出（Extract Variable）
      複雑な式に名前をつける
      if (order.total > 1000 && user.years > 3)
        → const isEligibleForDiscount = ...

   ③ 名前の変更（Rename）
      IDEの機能で安全に一括変更できる。最も費用対効果が高い

   ④ 条件記述の分解 / ガード節の導入
      ネストを浅くする（第3章）

   ⑤ 関数の移動 / クラスの抽出
      責務を正しい場所へ運ぶ
```

> **1手順ごとにテストを実行する。**
> まとめて10箇所直してからテストを流すと、どれが原因か分からなくなります。

### 17-4. いつやるか / やらないか

```
   ✅ やるべきタイミング
   ┌──────────────────────────────────────────────┐
   │ ・機能追加の直前（追加しやすい形に整えてから足す） │
   │   「準備リファクタリング」＝最も効率がよい ★      │
   │ ・バグ修正の後（同じバグが出ない構造にする）       │
   │ ・コードを読んで理解に苦労したとき（理解した今が旬） │
   │ ・ボーイスカウトルール（触ったついでに少しだけ）    │
   └──────────────────────────────────────────────┘

   ❌ やるべきでないとき
   ┌──────────────────────────────────────────────┐
   │ ・締切直前                                     │
   │ ・機能変更と同じPR（レビュー不能になる：第13章）   │
   │ ・近く廃止・作り直しが決まっているコード           │
   │ ・「動いているが誰も触らない」枯れたコード          │
   │ ・目的が「綺麗にしたいから」だけのとき ★          │
   └──────────────────────────────────────────────┘
```

```
   準備リファクタリングの考え方（Kent Beckの言葉の趣旨）

   ❌ 汚いまま機能を足す      → さらに汚くなる。次はもっと辛い
   ✅ 足しやすい形に整えてから足す
      「西に行きたいなら、まず北を向いて道を整える」

   時間
    │ ██████████ 汚いまま足す（毎回コストが増える）
    │ ████ ██    整えてから足す（初回は高いが以降が安い）
    └──────────────────▶ 回数
```

### 17-5. 大規模な作り直しをどう進めるか

```
   ❌ ビッグバン書き換え（同時に全部作り直す）
      → 数ヶ月機能追加が止まる／途中で頓挫する／
        旧仕様の漏れが必ず出る  ＝ 成功率が非常に低い

   ✅ ストラングラーパターン（絞め殺しの木）
   ┌────────────────────────────────────────────┐
   │  旧システム ████████████████████            │
   │  新システム                                  │
   │      ↓ 機能ごとに少しずつ新へ流す             │
   │  旧システム ████████████                     │
   │  新システム         ████████                 │
   │      ↓                                      │
   │  旧システム ████                             │
   │  新システム     ████████████████            │
   │      ↓ 旧が空になったら削除                   │
   └────────────────────────────────────────────┘
      常にリリース可能な状態を保ちながら移行する
```

**章末チェック**
- [ ] リファクタリングの定義（振る舞いを変えない）が言える
- [ ] テストなしで直してはいけない理由が説明できる
- [ ] 代表的なコードの臭いを5つ挙げられる
- [ ] 準備リファクタリングの考え方が説明できる
- [ ] やるべきでないタイミングを判断できる

## 第18章 パフォーマンスの考え方

第19章で扱う優先順位のうち、最後に来るのが「速さ」です。
**ただし「最後」であって「不要」ではありません。**正しい順序で扱うための章です。

### 18-1. 鉄則：測ってから直す

```
   ❌ 推測で最適化する                ✅ 計測して直す
   ┌────────────────────┐          ┌────────────────────┐
   │ 「ここが遅そう」      │          │ プロファイラで測定   │
   │  → 読みにくく書き換え │  ──────▶ │  → 実際の犯人を特定  │
   │  → 実は1%の処理だった │          │  → そこだけ直す     │
   └────────────────────┘          └────────────────────┘
     可読性を失って成果ゼロ            最小の変更で最大の効果
```

> **「早すぎる最適化は諸悪の根源」**
> ただし、この言葉は**「設計上の選択を無視していい」という意味ではありません。**
> アルゴリズムの選択やN+1の回避は、最適化ではなく**設計**です。

### 18-2. 計算量の基礎（これだけは知っておく）

```
   処理時間
      ▲                                    O(n²)
      │                                   ／
      │                                 ／
      │                              ／
      │                          ／          O(n log n)
      │                    ／ ＿＿＿＿＿＿＿＿
      │              ／＿＿／
      │        ＿／＿＿                      O(n)
      │  ＿＿／＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿  O(log n) / O(1)
      └──────────────────────────────────────▶ データ量 n

   n=100 なら差は小さい。n=100万 で桁違いになる。
   → 「今のデータ量」ではなく「将来のデータ量」で考える
```

| 記法 | 例 | 目安 |
|---|---|---|
| O(1) | ハッシュの参照 | データ量に依存しない |
| O(log n) | 二分探索、B-treeインデックス | ほぼ無視できる |
| O(n) | 配列を1周する | 素直 |
| O(n log n) | 一般的なソート | 実用の上限 |
| O(n²) | 二重ループ | **要注意** |

```javascript
// ❌ O(n²)：配列の中で配列を検索
orders.filter(o => userIds.includes(o.userId));

// ✅ O(n)：Setにしてから検索
const idSet = new Set(userIds);
orders.filter(o => idSet.has(o.userId));
```

### 18-3. 実務で遅い原因のほとんどはI/O

```
   処理時間のオーダー感（体感で覚える）

   CPU演算            1 ns   ┃
   メモリアクセス      100 ns  ┃
   SSD読み込み        150 μs  ┃█
   同一DCのDB問い合わせ  1 ms   ┃███
   外部API呼び出し     100 ms  ┃████████████████████████

   → CPUのループを10倍速くしても、DBを1回減らす方が効く
```

**最頻出の犯人：N+1問題**

```
❌ N+1（注文100件で101回のクエリ）
   const orders = await repo.findAll();          // 1回
   for (const o of orders) {
     o.user = await userRepo.find(o.userId);     // N回 ★
   }

✅ まとめて取得（2回）
   const orders = await repo.findAll();
   const users = await userRepo.findByIds(orders.map(o => o.userId));
```

**チェックすべき定番**

```
   ① N+1クエリ                  → まとめて取得 / JOIN
   ② インデックス不足             → 実行計画（EXPLAIN）を見る
   ③ 不要なデータの取得           → SELECT * をやめる、ページング
   ④ 直列で実行している独立処理     → 並列化（Promise.all）
   ⑤ 毎回計算している不変の値       → キャッシュ
```

### 18-4. どこまでやるか — 目標を先に決める

```
   ❌ 「速ければ速いほどいい」   → 終わりがない。過剰最適化
   ✅ 数値目標を先に置く

   ┌──────────────────────────────────────────────┐
   │ 「一覧APIは p95 で 300ms 以内」                 │
   │ 「同時100リクエストでエラー率0.1%以下」          │
   └──────────────────────────────────────────────┘
        │
        ▼
   満たしていれば、それ以上は可読性を優先する
```

**平均ではなくパーセンタイル（p95 / p99）を見ます。**
平均が速くても、100人に1人が10秒待っているなら問題です。

### 18-5. 可読性とのトレードオフ

```
   最適化して可読性を落とすなら、必ずセットで残す

   ① なぜ最適化したか（コメント：第2章）
   ② 最適化前後の計測結果（数字がないと後で戻せない）
   ③ 元の素直な実装（コメントやテストとして）

   例：

   // ループを1回に統合している（計測：3.1s → 0.4s）
```

## 第19章 実践のロードマップ

### 19-1. 判断に迷ったときの優先順位

原則同士が衝突したら、この順で考えてください。

```
1. 動作する（正しさ）
2. 読める（可読性）
3. 変更しやすい（設計）
4. 速い（パフォーマンス）
```

```
        ┌─────────────────────┐
        │  4. 速い             │ ← 計測してから。最後
        ├─────────────────────┤
        │  3. 変更しやすい      │
        ├─────────────────────┤
        │  2. 読める           │
        ├─────────────────────┤
        │  1. 動作する（正しい） │ ← 土台。ここが崩れたら全て無意味
        └─────────────────────┘

   下が満たされていないのに、上を目指さない。
   「読めないが速いコード」は、たいてい後で遅くなる。
```

**「早すぎる最適化は諸悪の根源」** — 計測せずに速度のために可読性を捨てないこと。

### 19-2. 過剰設計の警告サイン

| サイン | 問題 |
|---|---|
| 実装クラスが1つしかないインターフェース | 抽象化が早すぎる可能性 |
| ファイルを5個開かないと処理が追えない | 分割しすぎ |
| 「将来必要になるかも」で作った機能 | YAGNI違反 |
| 抽象クラスの継承が3階層以上 | 継承の乱用 |
| モックだらけのテスト | 実装詳細に密着。リファクタで壊れる |
| カバレッジのためだけのテスト | 保証していないのに安心してしまう（最も危険） |

**原則：抽象化は「2回目の重複」を見てから。**（Rule of Three）

### 19-3. 学習ステップ（推奨順序）

      「もっと小さく分割するならどう分けたか」を書いてください。
```

# まとめ — 全体を1枚で振り返る

```
【第2章】名前で意図を伝える
              ↓ 名前で足りない部分は構造で
【第3章】関数は1つのことをする
              ↓ 同じ発想を拡大
【第4章】モジュールは高凝集・低結合に
              ↓ 具体的な手順に
【第5・6章】SOLID（特にSRPとDIP）／依存の向き
              ↓ ディレクトリのスケールに適用
【第7章】パッケージ設計（CCP・ADP・SDP・SAP）
              ↓ システム全体に適用
【第8章】アーキテクチャ（重要なものを詳細から守る）
              ↓ ここまでを「保証し続ける」ために
【第9・10章】状態と失敗を設計する（変わるもの・壊れるものを閉じ込める）
              ↓ ここまでを「保証し続ける」ために
【第11〜16章】テスト・自動化・レビュー・ログ・セキュリティ・記録
              ↓ そして既存コードに適用する
【第17〜20章】リファクタリングと実践
```

すべての章に共通する、たった1つの問いはこれです。

> ### 「変更が来たとき、どこを直せばいいかすぐ分かり、直しても他が壊れないか?」

#### スケール別・原則の対応表

```
 スケール      技法                        共通する問い
 ─────────────────────────────────────────────────────────
 名前        命名の6条件 / コメント         「読む人が誤解しないか?」
   ▲
   │
 関数        単一責任 / 早期リターン        「1つのことをしているか?」
   ▲
   │
 モジュール    高凝集・低結合                「一緒に変わるものが一緒にあるか?」
   ▲
   │
 クラス間     SOLID（SRP / DIP）           「変更理由は1つか? 抽象に依存しているか?」
   ▲
   │
 パッケージ    CCP / ADP / SDP              「循環はないか? 安定な方へ依存しているか?」
   ▲
   │
 システム     レイヤード / ヘキサゴナル /     「重要なものが、詳細から守られているか?」
             クリーン
 ─────────────────────────────────────────────────────────
 全体を貫く    テスト / Lint / 型 / CI        「壊れたとき、すぐ気づけるか?」
 ─────────────────────────────────────────────────────────
 チーム       コミット / PR / レビュー / ADR   「他人が理解し、引き継げるか?」
 ─────────────────────────────────────────────────────────
 本番        ログ / 監視 / セキュリティ        「起きたことを、後から追えるか?」
```

#### 設計とテストの関係を一言で

```
   良い設計 ──────▶ テストが書きやすい
      ▲                    │
      │                    ▼
      └──────────── テストがあるから安心して直せる
                    （＝設計を良くし続けられる）

   この循環に入れたチームは、時間とともにコードが良くなる。
   入れないチームは、時間とともにコードが悪くなる。
```

この問いに「はい」と答えられるコードが、良いコードです。
