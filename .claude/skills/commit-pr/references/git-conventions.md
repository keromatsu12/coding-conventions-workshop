# コミット・PR・ブランチの規約（第13章・12-8）

## コミットは「変更の意味の単位」（13-1）

```
❌ 1コミット＝1日の作業           ✅ 1コミット＝1つの意味
"いろいろ修正"                    "注文APIに在庫チェックを追加"
 ・機能追加                       "注文一覧のN+1問題を修正"
 ・バグ修正                 ──▶   "全ファイルをPrettierで整形"
 ・変数名の一括変更
 ・フォーマット整形
 → レビューできない                → 1つずつレビューできる
 → revert できない                → 問題のあるものだけ revert できる
 → bisect で原因を追えない          → git bisect が機能する
```

> **鉄則：フォーマット整形・リネームは、機能変更と絶対に混ぜない。**

## コミットメッセージ（13-2）

```
<型>: <何をしたか（現在形・50字以内）>

<なぜそうしたか / 背景 / トレードオフ>

Refs: #123
```

| 型 | 意味 | このリポジトリでの例 |
| --- | --- | --- |
| `feat` | 機能追加 | `feat: 注文APIに在庫チェックを追加` |
| `fix` | バグ修正（振る舞いが変わる） | `fix: ユーザー検索のSQLインジェクションを修正` |
| `refactor` | 挙動を変えない内部改善 | `refactor: 注文金額の計算を純粋関数に切り出す` |
| `test` | テストの追加・修正 | `test: 会員割引の境界値テストを追加` |
| `docs` | ドキュメント | `docs: ADR-001 リポジトリ層の導入を記録` |
| `chore` | ビルド・依存更新・設定 | `chore: Prettier を導入` |

❌ 悪い例 → ✅ 良い例:

```
❌ 修正 / wip / レビュー指摘対応 / update UserService.ts

✅ fix: 注文合計の税計算で端数が1円ずれる問題を修正

   切り捨てと四捨五入が混在していたため、
   仕様書に合わせて切り捨てに統一した。

   Refs: #452
```

**「何をしたか」は diff で分かる。メッセージの価値は「なぜ」にある。**（コメント論と同じ、第2章）

`refactor:` の本文には、振る舞いを変えていないことの確認方法を書くとレビューが速い（例: `npm start の出力が変わらないことを確認`）。

## PRは小さく（13-3）

```
〜200行   きちんと見られる
400行     流し読みになる
1000行〜  LGTM（見ていない）
```

大きな機能の分割順:

```
① リファクタのみ（挙動を変えない）   ← 先にマージ
② インターフェース・型の追加
③ 実装
④ 画面（ハンドラ）との接続
```

各PRが独立してレビュー可能・revert 可能になる。

## レビューで見てもらうこと（13-4）

PR本文の「レビューしてほしい点」には、機械にできないことだけを書く: 仕様の解釈、責務の分け方、依存の向き、名前、異常系、テストの妥当性、セキュリティ。書式・import順は書かない（ツールの仕事）。

## ブランチ（13-6）

- GitHub Flow: `main` は常にデプロイ可能、短命の作業ブランチから PR。
- `main` へは必ず PR 経由。CI が通らないとマージできないようにする。
- ブランチは短命に。長生きするほどコンフリクトが増える。

## ツール導入をコミットするとき（12-8）

既存プロジェクトにフォーマッター/リンターを入れる順番。各ステップを**別コミット**にする:

```
1. フォーマッター導入             chore: Prettier を導入
2. 全ファイル一括整形（単独！）    chore: Prettier で全ファイルを整形
3. リンター導入（既存違反は warn）  chore: ESLint を導入（既存違反は warn）
4. CI に組み込む                 ci: lint と typecheck を CI で実行
5. ルールを段階的に error へ      chore: no-empty を error に昇格
```

2 の一括整形コミットは中身の変更を一切含めない。`git blame` から除外したい場合は `.git-blame-ignore-revs` にそのコミットを登録する。

## 秘密情報（15-4）

- `.env`・キー・パスワードをコミットしない。`.gitignore` を先に書く。
- 誤ってコミット・push したら、履歴から消すだけでは不十分。**必ずキーをローテートする。**
