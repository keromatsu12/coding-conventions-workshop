# コミットとPR

## 1. 差分を把握する

```bash
bash .claude/skills/commit-pr/scripts/diff-report.sh          # ステージ済み
bash .claude/skills/commit-pr/scripts/diff-report.sh main     # PR全体（main...HEAD）
```

行数・空白だけの変更の混在・テストの有無・教材ファイルへの変更を報告する。`[WARN]` が出たら次の分割を検討する。

## 2. 意味の単位に分ける（13-1）

**1コミット = 1つの意味。** 次は必ず別コミットにする:

| 混ぜてはいけない組み合わせ                   | 理由                         |
| -------------------------------------------- | ---------------------------- |
| フォーマット整形・一括リネーム ／ 中身の変更 | 差分の99%がノイズになる      |
| リファクタリング ／ 機能追加・バグ修正       | 振る舞いの変化が追えなくなる |
| 依存追加・設定変更 ／ それを使うコード       | revert 単位が合わない        |

分けるときは `git add -p` 相当の操作ではなく（対話不可）、ファイル単位の `git add <path>` か、一時的に変更を戻して段階的にステージする。分け方がユーザーの意図に関わる場合は先に案を出して確認する。

順番は **リファクタ → 型・インターフェース → 実装 → 接続**（13-3）。

## 3. メッセージを書く（13-2）

```
<型>: <何をしたか（現在形・50字以内）>

<なぜそうしたか / 背景 / トレードオフ>

Refs: #123
```

- 型: `feat` `fix` `refactor` `test` `docs` `chore`
- **価値は「なぜ」にある。** 「何を」は diff で分かる。本文に原則・章番号を書いてもよい（例: `計算とI/Oを分離（20-3）`）。
- ❌ `修正` `wip` `レビュー指摘対応` `update X.ts`
- リポジトリ既存の流儀（`git log --oneline -20`）に合わせる。このリポジトリは `<型>: 日本語の要約`。
- 環境・ユーザーがコミット末尾の署名（Co-Authored-By など）を指定している場合はそれに従う。

`refactor:` を付けるなら、振る舞いが変わっていないことを確認済みであること（`safe-refactor` の `verify` やテスト）。

## 4. PRにまとめる（13-3）

- **目安は200行、400行を超えたら分割する。** 超える場合は分割案（①リファクタのみ ②型の追加 ③実装 ④接続）を示す。
- PRはユーザーが明示的に頼んだときだけ作る。テンプレートがあればその構成に従う。
- `main` に直接 push しない。短命のブランチを切る（13-6）。

PR本文の型:

```markdown
## 何を・なぜ
<変更の目的。背景となる課題>

## 変更内容
- <意味の単位ごとに。コミットと対応させる>

## 振る舞いへの影響
- なし（refactor のみ。golden master verify OK）／ あり: <何がどう変わるか>

## 確認方法
- `npm run typecheck`
- <実行したテスト・手順と結果>

## レビューしてほしい点
- <設計判断で迷った箇所。機械で見られる書式などは書かない>
```

## 5. コミット前の最終確認

- [ ] `npm run typecheck` が通る
- [ ] 1コミットに1つの意味だけが入っている
- [ ] メッセージに「なぜ」がある
- [ ] 秘密情報（キー・パスワード・トークン）を新たに含めていない（15-4）
- [ ] 教材の保護ファイル（`src/fake-libs/` など）を変えていない
