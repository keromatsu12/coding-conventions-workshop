# リファクタリングの技法と判断基準（第17章）

## 基本の5手順（17-3）

| 手順 | 内容 | 例 |
| --- | --- | --- |
| ① 関数の抽出 | まとまった処理に名前をつけて切り出す。最頻出 | 「ここから税計算」コメントの下を `calculateTax()` に |
| ② 変数の抽出 | 複雑な式に名前をつける | `const isEligibleForDiscount = order.total > 1000 && user.years > 3` |
| ③ 名前の変更 | 費用対効果が最も高い | `d` → `order` |
| ④ 条件の分解／ガード節 | ネストを浅くする | `if (!order) return 0;` |
| ⑤ 関数の移動／クラスの抽出 | 責務を正しい場所へ運ぶ | 他クラスの値ばかり見るメソッドをそのクラスへ |

**1手順ごとに検証する。** まとめて10箇所直してからテストすると、どれが原因か分からない。

## 振る舞いを変えないための注意

リファクタリングのつもりで振る舞いを変えてしまう典型:

- 計算順序・端数処理（`Math.floor` の位置）を変える
- `==` と `===`、`!= null` と truthy 判定を入れ替える（`0` や `''` の扱いが変わる）
- 例外を投げる/投げないを変える（握りつぶしを直すのはバグ修正であってリファクタではない）
- ログ・出力の文言や順序を変える
- 非同期処理の順序（`await` の有無、並列化）を変える
- 引数の破壊的変更をやめたことで、呼び出し元がその変更に依存していた

## 継ぎ目（Seam）と特性テスト（17-1）

テストが書けないほど絡まっているときの順番:

```
① 変更したい箇所を見つける
② 継ぎ目を作る … 依存を引数/コンストラクタに追い出す（最小限の変更）
③ 特性テストを書く … 「正しい振る舞い」ではなく「今の振る舞い」を固定
④ ここでようやくリファクタリング
⑤ その後に機能変更
```

継ぎ目の作り方（既定値を残すと呼び出し元を変えずに済む）:

```ts
// Before: 中で依存を作っている
export async function placeOrder(input) {
  const db = createConnection(config);
  // ...
}

// After: 外から渡せるようにする（既定値で既存の呼び出しは無変更）
export async function placeOrder(input, db: Db = createConnection(config)) {
  // ...
}
```

特性テストの例（今の振る舞いをそのまま記録する）:

```ts
test('合計に端数があるとき切り捨てられる（現状の振る舞い）', () => {
  assert.equal(calculateTotal(sampleOrder), 12320);
});

test('検索キーワードの引用符がそのままSQLに入る（現状の振る舞い・バグ）', async () => {
  const users = await searchUsers(fakeDb, "' OR '1'='1");
  assert.equal(users.length, 3);   // 直したらこのテストを「正しい仕様」に書き換える
});
```

時刻・乱数・ID生成も継ぎ目にする（`now: () => Date = () => new Date()` など）。そうしないとテストが Repeatable にならない。

## いつやるか / やらないか（17-4）

✅ やるべきとき
- **機能追加の直前**（準備リファクタリング＝最も効率がよい）
- バグ修正の後（同じバグが出ない構造にする）
- 読んで理解に苦労したとき（理解した今が旬）
- 触ったついでに少しだけ（ボーイスカウトルール）

❌ やるべきでないとき
- 締切直前
- 機能変更と同じPR
- 近く廃止・作り直しが決まっているコード
- 動いているが誰も触らない枯れたコード
- 目的が「綺麗にしたいから」だけ

## 大規模な作り直し（17-5）

ビッグバン書き換えはしない。**ストラングラーパターン**で機能ごとに新しい実装へ流し、常にリリース可能な状態を保つ。旧実装が空になったら削除する。

## やりすぎの警告（19-2）

| サイン | 問題 |
| --- | --- |
| 実装が1つしかないインターフェース | 抽象化が早すぎる（ただしDB・外部APIの境界は除く） |
| ファイルを5個開かないと処理が追えない | 分割しすぎ |
| 「将来必要になるかも」の機能 | YAGNI |
| 継承が3階層以上 | 継承の乱用 |
| モックだらけのテスト | 実装詳細に密着 |

**抽象化は「2回目の重複」を見てから（Rule of Three）。**
