# 安全なリファクタリング

> **リファクタリング = 外から見た振る舞いを変えずに、内部構造を改善すること。**
> テストなしにやってはいけない。機能追加・バグ修正と同時にやってはいけない。（17-1）

何をどう直すかの原則は `coding-conventions` スキル（特に `references/refactoring.md`）を参照する。
このスキルは**進め方と安全確認**を担う。

## 0. やるかどうかを決める（17-4）

着手前に確認し、当てはまるならユーザーに伝えて止まる:

- 機能変更と同じ作業単位になっていないか → 分ける（リファクタが先）
- 近く廃止予定・誰も触らないコードではないか
- 目的が「綺麗にしたいから」だけではないか → 次に入る変更（機能追加・バグ修正）を聞く

いちばん効くのは**準備リファクタリング**（機能を足す直前に、足しやすい形に整える）。

## 1. 振る舞いを固定する（17-1 ③ / 20-4）

構造を変える前に、必ずどちらかを用意する。

### A. ゴールデンマスター（このリポジトリの legacy-app 向け・最短）

`npm start` の出力全体を特性テストとして使う（README「進捗の測り方」）。

```bash
node .claude/skills/safe-refactor/scripts/golden-master.mjs record   # 作業前に1回
node .claude/skills/safe-refactor/scripts/golden-master.mjs verify   # 1手順ごとに
```

- レポートIDと処理時間（`NNms`）は自動で正規化される。
- ベースラインは `.golden-master/`（gitignore 済み）に保存される。
- **`verify` が NG なら直前の1手順を戻す。** 原因を探しながら先に進まない。

### B. 特性テスト（関数単位）

ゴールデンマスターでは粗すぎる、または対象が `npm start` で通らないとき:

- `node:test` + `node:assert/strict` で書く（このリポジトリにテストフレームワークは無い）。
- **「正しい振る舞い」ではなく「今の振る舞い」を assert する。** 明らかなバグも一旦そのまま固定し、テスト名に `（現状の振る舞い・バグ）` と書いておく。
- テストが書けないほど絡まっていたら、先に**継ぎ目（Seam）**を作る: DB・メール・時刻・乱数を引数/コンストラクタで受け取れるようにする最小変更だけを行う（第6章）。
- テストファイルを `tsconfig` の対象に置き、`tsc && node --test dist/<path>.test.js` で実行する。

## 2. ステップを1つずつ進める（第20章）

```
20-1 名前を直す        → まだ構造は変えない
20-2 ネストを浅くする   → ガード節
20-3 計算とI/Oを分離   → 最大の転換点（純粋関数に切り出す）
20-4 テストを書く      → ★ 1-B の特性テストを、切り出した純粋関数の単体テストに育てる
20-5 エラー処理を正す
20-6 責務を分割する
20-7 依存を逆転させる
20-8 配置を整える
```

各ステップの中では 17-3 の基本手順（関数の抽出・変数の抽出・改名・ガード節・移動）を**1つ適用するごとに検証**する:

```
小さく1つ直す → npm run typecheck → verify（またはテスト） → 次へ
```

- 1ステップ = 1コミット（`refactor: ...`）を基本にする。コミット手順は `commit-pr` スキル。
- **全ステップを一度にやらない。** 依頼範囲が曖昧なら 20-4 まで進めて報告し、続けるか確認する。
- ステップごとに、何を変えたかと検証結果（verify OK / テスト件数）を短く報告する。

## 3. 振る舞いを変えたくなったら

途中で見つけたバグ（SQLインジェクション、XSS、接続の閉じ忘れなど）は、**その場で直さない**。

1. メモしてリファクタリングを先に区切る（コミット）
2. ユーザーに「これは振る舞いの変更になる」と伝えて了承を得る
3. 別コミット（`fix: ...`）で直し、意図した差分だけが出ることを `verify` で確認する
4. 差分が意図どおりなら `record` でベースラインを更新する

`DB接続を張った回数` のように**欠陥そのものが出力に出ている行**もある。そこが変わるのは「修正」であって「リファクタリング」ではない。

## 4. 終わりの報告

- 実施したステップと、残りのステップ
- 検証結果（最後の `verify` / テストの実行結果をそのまま）
- 見つけたが直していない振る舞いの問題（3. のメモ）

## このリポジトリでの注意

- `src/fake-libs/`・`src/chapters/_support.ts`・`src/chapters/ch11-subject.ts` は変更しない。
- `src/chapters/ch*.bad.ts` は Before の教材。改善版は依頼されたときだけ、元ファイルを残して `ch*.good.ts` などの別ファイルに書くのが無難（迷ったらユーザーに確認）。
