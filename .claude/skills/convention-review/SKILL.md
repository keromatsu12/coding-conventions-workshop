# 規約レビュー

規約の中身は `coding-conventions` スキルにある。このスキルは**それを使ってレビューする手順**。
迷ったら `coding-conventions` の該当 references を読む（全文の原文は読まない）。

## 1. 対象を決める

| 依頼                       | 対象                                        |
| -------------------------- | ------------------------------------------- |
| 「この変更を見て」・PR     | `git diff main...HEAD`（またはステージ済み） |
| ファイル・ディレクトリ指定 | そのファイル全体                            |
| 指定なし                   | 未コミットの差分 → なければ直近コミット     |

差分レビューでは、差分の外は「変更が既存の何を壊すか」を確認するためだけに読む。差分外の既存の問題は指摘しない（ボーイスカウトの範囲を超える）。

## 2. 機械に任せることを除外する（12-9 / 13-4）

書式・インデント・未使用変数・import順・関数の行数・ネストの深さ・循環依存は**指摘しない**（フォーマッター/リンターの仕事）。ツールが入っていなければ、そのこと自体を1件だけ指摘する（第12章）。

`npm run typecheck` が通るかは最初に確認しておく。

## 3. 最低限のレビュー観点（優先度順）

上から順に見て、上位で重大な問題が見つかったら下位の細かい指摘は減らす（指摘が多すぎるレビューは読まれない）。

| #  | 観点               | 問い                                                                                                                       | 章          |
| -- | ------------------ | -------------------------------------------------------------------------------------------------------------------------- | ----------- |
| 1  | **仕様**           | 作るべきものを作っているか。境界値と異常系は考えてあるか                                                                   | 13-4 ①      |
| 2  | **セキュリティ**   | 外部入力をサーバー側で検証しているか。SQLを文字列連結していないか、出力をエスケープしているか。他人のデータを触れないか（認可）。秘密情報をコードやログに書いていないか | 15          |
| 3  | **エラー**         | エラーを握りつぶしていないか。元の原因（cause）を捨てていないか                                                             | 10          |
| 4  | **責務**           | 関数やクラスが「1つのこと」をしているか。計算とI/Oが混ざっていないか                                                         | 3・4・5     |
| 5  | **依存**           | 依存の向きは「変わりにくいもの」に向いているか。依存を自分で作らず、外から受け取っているか                                   | 6           |
| 6  | **名前**           | 初見の人が誤解しないか。`data` や `util` のような汎用語を使っていないか、単位や状態が名前に入っているか                       | 2           |
| 7  | **状態**           | 引数で受け取ったオブジェクトを書き換えていないか。共有された可変状態を増やしていないか                                       | 9           |
| 8  | **テスト**         | この変更を保証するテストはあるか。そのテストは本質を検証しているか                                                           | 11          |
| 9  | **必要性**         | その抽象化は今本当に必要か（YAGNI、過剰設計）                                                                               | 12-9・19-2  |
| 10 | **変更の単位**     | 1コミットに1つの意味か。リファクタリングと機能変更が同じPRに混ざっていないか。PRが400行を超えていないか                      | 13          |

**時間がないときは 1〜3（仕様・セキュリティ・エラー）だけを見る。** ここの見落としは事故になり、4以降の見落としは変更コストが上がるだけ（19-1 の優先順位「動作する → 読める → 変更しやすい」）。

パフォーマンスは、N+1 など明らかな I/O の問題があるときだけ指摘する。計測なしのCPU最適化は求めない（第18章）。

構造的な臭いは 17-2 のカタログ（`coding-conventions/references/refactoring.md`）で名前を付けて指摘する（「長すぎる関数」「特徴の横恋慕」など）。

## 4. 指摘の書き方（13-5）

- **人ではなくコードに向ける。** 「なぜこう書いたのか」ではなく「ここを〇〇にすると△△が良くなりそう」。
- 断定より前提を示す: 「`items` が空のとき 0 除算になりませんか?」
- **理由（原則・章番号）とセットで書く。** 好みは `[IMO]` に落とす。
- 直し方は方向だけ示し、必要なら短いコード例を添える。全面書き直しのコードは貼らない。
- 良いところがあれば必ず `[GOOD]` で書く。

重みの基準:

| ラベル     | 使う場面                                                                |
| ---------- | ----------------------------------------------------------------------- |
| `[MUST]`   | バグ、セキュリティ脆弱性、データ破損、握りつぶし、テストを壊す変更     |
| `[SHOULD]` | 設計・命名・テスト不足など、放置すると変更コストが上がるもの           |
| `[IMO]`    | 原則上どちらもあり得る選択                                              |
| `[NITS]`   | 些細な表記（機械で検出できないものに限る）                              |
| `[ASK]`    | 意図が読み取れず判断できないとき                                        |
| `[GOOD]`   | 規約に沿った良い実装                                                    |

## 5. 出力形式

```markdown
## レビュー結果: <対象>

**総評**: <2〜3行。最も重要な問題と、まず直すべき1点>

| # | 重み | 場所 | 指摘 | 根拠 |
|---|------|------|------|------|
| 1 | [MUST] | `src/foo.ts:42` | 検索キーワードをSQLに文字列連結しているため、`' OR '1'='1` で全件取得できてしまいます。プレースホルダにすると防げます。 | 15-2 |
| 2 | [SHOULD] | ... | ... | 3-1 |
| 3 | [GOOD] | ... | ... | 9-2 |

### 直す順番の提案
1. [MUST] を先に（別コミット・`fix:`）
2. 構造の改善は振る舞いを固定してから → `safe-refactor` スキル
```

- 場所は `path:line` で示す（クリックできる形）。
- 件数が多いときは [MUST]/[SHOULD] を全件、[IMO]/[NITS] は代表例のみ。
- 演習の「欠陥一覧」を作るときは、第20章 20-0 に倣い**章ごとに数え上げる**表にしてもよい。

## 6. このリポジトリでの注意

- `src/` は**意図的に悪いコード**。レビュー対象として読むのは自由だが、依頼なしに修正しない。
- `src/fake-libs/`・`src/chapters/_support.ts`・`src/chapters/ch11-subject.ts` は「外部ライブラリ扱い」。指摘対象から外す。
- `ch*.bad.ts` のコメントにある `（2-6 例3）` などの節番号は、根拠列にそのまま使える。
- GitHub の PR にコメントとして投稿するのは、ユーザーが明示的に頼んだときだけ。
