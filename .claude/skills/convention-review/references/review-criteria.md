# レビュー観点の詳細（❌/✅ 例つき）

SKILL.md の「最低限のレビュー観点」10項目それぞれについて、何を見て、何を指摘するかの具体例。
原文は `docs/coding-conventions.md`（節番号で引ける。行番号は `coding-conventions/references/source-map.md`）。

---

## 1. 仕様（13-4 ①）

- 作るべきものを作っているか（PR説明・Issue と突き合わせる）
- **境界値**: 0件、1件、上限ちょうど、上限+1、`null`/`undefined`、空文字
- **異常系**: 入力不正、外部サービスの失敗、二重送信

```ts
// ❌ 「3年以上」の仕様なのに > になっている（境界値の取り違え）
if (user.membershipYears > 3) { ... }
// ✅
if (user.membershipYears >= LOYAL_MEMBER_YEARS) { ... }
```

指摘例: `[MUST] 会員年数がちょうど3年のとき割引されませんが、仕様は「3年以上」でしょうか?（11-5 境界値）`

## 2. セキュリティ（第15章）

| 見るもの | ❌ | ✅ |
| --- | --- | --- |
| SQLインジェクション（15-2） | `` db.query(`... WHERE email = '${email}'`) `` | `db.query('... WHERE email = ?', [email])` |
| XSS（15-2） | `` `<div>ようこそ ${name}</div>` ``、`innerHTML` | エスケープしてから埋める。自動エスケープを切らない |
| 認可の欠落（15-3）★最多 | ログイン済みかだけ確認して `repo.find(orderId)` | `repo.findByUser(currentUser.id, orderId)`（構造上他人のデータが取れない） |
| 入力検証（15-1） | フロントだけで検証、ブラックリスト | サーバー側で再検証、ホワイトリスト |
| 秘密情報（15-4） | APIキー・パスワードをコードに直書き | 環境変数／シークレットマネージャ |
| ログ（14-5） | パスワード・トークン・カード番号・個人情報を出力 | マスクする／出さない |
| レスポンス（15-6） | DBの行をそのまま返す（`password` 列まで出る） | 返す項目をホワイトリストで選ぶ |
| 認証エラー（15-5） | 「そのメールアドレスは登録されていません」 | 「メールアドレスまたはパスワードが正しくありません」 |

秘密の誤コミットを見つけたら、**消すだけでは不十分。キーのローテートを求める**（15-4）。

## 3. エラー（第10章）

```ts
// ❌ 何もしない catch（最悪）
catch (e) {}
// ❌ ログだけ出して握りつぶす（呼び出し元は成功したと思う）
catch (e) { console.log(e); }
// ❌ 原因を捨てる
catch (e) { throw new Error('保存に失敗'); }
// ✅ 原因を保持して意味のある例外に変換
catch (e) { throw new OrderSaveError(`注文${order.id}の保存に失敗`, { cause: e }); }
```

- 失敗の3分類（10-1）を取り違えていないか: 業務エラー（在庫切れ等）は戻り値、環境エラー（DB断等）は例外、バグは Fail Fast。
- 例外は層をまたぐときに翻訳しているか（10-4）: `SQLException` をUIまで漏らさない。
- ユーザー向けメッセージに内部情報（SQL、スタックトレース）が出ていないか（10-5）。
- 意図的に無視するなら、理由のコメントがあるか。

## 4. 責務（第3・4・5章）

- 説明に「そして」が入る／名前に `And` → 分割対象（3-1）
- 同じ関数に「何を」と「どうやって」が混在（SLAP, 3-2）
- **計算とI/Oが混ざっている**（DBアクセスの途中で金額計算）→ 純粋関数に切り出せばテストできる（3-4）
- boolean引数で振る舞いを切り替えている → 関数を2つに（3-3）
- 種類が増えるたびに `if`/`switch` を足す構造 → OCP 違反（5-2）
- 1クラスが複数の「変更理由」を持つ（神クラス）→ SRP 違反（5-1）

```ts
// ❌ 割引ルールが増えるたびに if を足す
if (years >= 3) amount *= 0.8;
if (isCampaign) amount *= 0.9;
// ✅ ルールを部品にして追加だけで拡張
const finalAmount = rules.reduce((amount, rule) => rule.apply(amount, context), subtotal);
```

## 5. 依存（第6・7・8章）

- 依存の矢印が「変わりにくいもの」（業務ルール）へ向いているか。業務ロジックが DB・HTTP・メールの具体実装を直接 import していないか（6-2）
- 依存を関数の中で `new` / `createConnection` していないか → コンストラクタ注入（6-3）
- `internal/` や他機能の内部ファイルを直接 import していないか（7-5）
- `utils/` `common/` `shared/` に機能固有のものを置いていないか（7-2）

```ts
// ❌ 中で作る（差し替えられない・テストできない）
class OrderService { private db = new MySQLClient(config); }
// ✅ 外から受け取る
class OrderService { constructor(private readonly repository: OrderRepository) {} }
```

## 6. 名前（第2章）

| ❌ | 理由 | ✅ |
| --- | --- | --- |
| `d`, `t`, `tmp`, `data`, `info`, `result` | 何も伝えない | `order`, `totalAmount` |
| `timeout`, `size` | 単位が無い | `timeoutMs`, `sizeMb` |
| `password`（ハッシュ済みか不明） | 状態が無い | `plaintextPassword`, `passwordHash` |
| `flag`, `disableSsl = false` | 意味不明・二重否定 | `isActive`, `shouldVerifySsl` |
| `fetchUser` / `getOrder` / `retrieveItem` の混在 | 同じ概念に違う語 | 動詞を統一 |
| `OrderManager`, `UserHelper` | 責務を説明できていない（設計の問題） | 責務名で分ける |

悪い名前をコメントで補っていたら、コメントではなく名前を直すよう指摘する（2-4）。

## 7. 状態（第9章）

```ts
// ❌ 引数を書き換える（呼び出し元の値まで変わる）
function applyDiscount(order) { order.total *= 0.8; return order; }
// ✅ 新しい値を返す
function applyDiscount(order) { return { ...order, total: order.total * 0.8 }; }
```

- 再代入を繰り返す `let` → `const` と小さな関数で置き換えられないか（9-2）
- モジュールレベルの可変変数・グローバル状態を増やしていないか（9-4）
- 不正な状態（`status = 'paid'` なのに `paidAt = null`）を作れる型になっていないか（9-5）

## 8. テスト（第11章）

- この変更を保証するテストがあるか。**無ければ何が壊れても気づけない**
- テスト名が仕様になっているか: `test('3年以上の会員は20%割引になる')`（❌ `test('getDiscount')`）
- AAA（Arrange / Act / Assert）に分かれているか
- テスト同士が状態を共有していないか（F.I.R.S.T. の Independent）
- 本質を検証しているか（`assert.ok(result)` だけ、例外が出ないことだけ、は検証していないのと同じ）

アンチパターン（11-11）:

| アンチパターン | 何が起きるか |
| --- | --- |
| 実装詳細をテストする | リファクタのたびに壊れる |
| 1テストに大量の assert | 落ちた原因が分からない |
| テスト内に if / loop | テスト自体にバグが入る |
| 巨大な共通セットアップ | 前提が読めない |
| Flaky テストの放置 | 誰もテスト結果を信用しなくなる |
| コメントアウトされたテスト | 存在しないのと同じ |
| カバレッジのためだけのテスト | 保証していないのに安心してしまう（最も危険） |

テストが書きにくそうなら、テストではなく**設計**を指摘する（11-7）。

## 9. 必要性（12-9・19-2）

| 過剰設計のサイン | 問題 |
| --- | --- |
| 実装が1つしかないインターフェース | 抽象化が早すぎる可能性 |
| ファイルを5個開かないと処理が追えない | 分割しすぎ |
| 「将来必要になるかも」で作った機能 | YAGNI 違反 |
| 継承が3階層以上 | 継承の乱用 |
| モックだらけのテスト | 実装詳細に密着している |

**抽象化は「2回目の重複」を見てから（Rule of Three）。** 過剰設計は不足設計と同じくらい悪い。
ただしテスト用に差し替えが必要な境界（DB・外部API）のインターフェースは、実装が1つでも正当。

## 10. 変更の単位（第13章）

- フォーマット整形・一括リネームが機能変更と混ざっていないか（13-1）
- リファクタリングと機能変更・バグ修正が同じPRにないか（17-4）
- 400行を超えていないか（13-3）→ 分割案を示す
- コミットメッセージに「なぜ」があるか（13-2）

## 指摘の言い回し（13-5）

| ❌ | ✅ |
| --- | --- |
| 「なんでこう書いたんですか」 | 「ここを〇〇にすると△△の点で良くなりそうです」 |
| 「これは間違いです」 | 「〜という前提だとバグになりませんか?」 |
| 好みの押し付け | 理由（原則・章番号・トレードオフ）とセットで |
