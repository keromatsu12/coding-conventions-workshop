# 保守できるコードの原則

すべての章に共通する、たった1つの問い:

> **「変更が来たとき、どこを直せばいいかすぐ分かり、直しても他が壊れないか?」**

設計の目的は「変更しやすさ」ただ一つ。美しさでも技術の披露でもない。

## 判断に迷ったときの優先順位（第19章）

```
1. 動作する（正しさ）    ← 土台。ここが崩れたら全て無意味
2. 読める（可読性）
3. 変更しやすい（設計）
4. 速い（パフォーマンス） ← 計測してから。最後
```

下が満たされていないのに上を目指さない。**早すぎる最適化は諸悪の根源。**

原則同士が衝突したら、この順で決める。過剰設計は不足設計と同じくらい悪い（→ 過剰設計の警告サインは `references/refactoring.md`）。

## このスキルの使い方

1. **コードを書く前** — 下の「常に守る核」を適用する。
2. **判断に迷ったら** — 該当する参照ファイルだけを読む（下の表）。
3. **書き終えたら** — 「日々のチェックリスト」で自問する。
4. **原文の細部が要るとき** — `docs/coding-conventions.md` の該当行だけを読む（`references/source-map.md` に章・節ごとの行番号がある）。279KB あるので全文は読まない。

## 常に守る核（これだけで質の8割が決まる）

### 名前（第2章）

- 汎用語を使わない: `tmp` `data` `info` `flag` `result` `manager` `util` `helper` は原則禁止。
- **単位と状態を名前に埋める**: `delaySecs` `sizeMb` `maxItems` `plaintextPassword` `unescapedHtml`。
- boolean は肯定形＋接頭辞: `isActive` `hasPermission` `canEdit` `shouldRetry`。`disableSsl = false` のような二重否定を作らない。
- 同じ概念には同じ語を使う（`fetchUser` / `getOrder` / `retrieveProduct` の混在は禁止）。
- スコープが広いほど長く正確に、3行しか生きない変数は短くてよい。
- `Manager` / `Util` / `Helper` が出たら**命名ではなく設計の問題**。責務が説明できていない。

### コメント（第2章）

- 「何を」ではなく **「なぜ」** を書く。
- コメントを書きたくなったら順に自問: ①名前を変えれば不要か → ②関数に切り出せば不要か → ③どちらでもないなら「なぜ」を書く。
- 悪い名前の言い訳としてコメントを足さない。名前を直す。
- 記法を揃える: `TODO:` `FIXME:` `HACK:` `NOTE:` `WARN:`。

### 関数（第3章）

- **1つのことだけをする。** 説明に「そして(and)」が入る／名前に `And` が入るなら分割対象。
- **抽象レベルを揃える（SLAP）。** 同じ関数内に「何を」と「どうやって」を混ぜない。
- 分割サイン: 画面に収まらない／ネスト3段以上／引数4個以上／boolean引数がある／「ここから〜の処理」コメントがある。
- boolean引数は2つの関数に分ける（`createUser(name, email, true)` → `createAdminUser` / `createNormalUser`）。
- **早期リターン（ガード節）** で例外的ケースを先に片付け、本筋を一番浅い階層に置く。ネストは2段以内を目標。
- **計算とI/Oを分離する。** 計算は純粋関数に切り出す（テストが劇的に楽になる）。

### 状態（第9章）

- まず `const` / `readonly` で宣言し、どうしても必要なときだけ可変にする。
- **引数で受け取ったオブジェクトを書き換えない。** 新しい値を返す（`return { ...order, total: ... }`）。
- 状態は散らばらせず一箇所に集める。共有された可変状態（グローバル変数、モジュールレベルの可変オブジェクト）は最も危険。
- 「不正な状態を作れなくする」型・コンストラクタ設計を優先する。

### エラー（第10章）

失敗を3つに分類してから扱う:

| 種類                         | 例                                   | 扱い                                                   |
| ---------------------------- | ------------------------------------ | ------------------------------------------------------ |
| ① 想定内の失敗（業務エラー） | 在庫切れ、残高不足、バリデーションNG | **戻り値**で表現（Result型など）。呼び出し元が必ず処理 |
| ② 想定内の異常（環境エラー） | ネットワーク断、DBタイムアウト、5xx  | **例外**。リトライ・フォールバックの対象               |
| ③ 想定外（バグ）             | null参照、あり得ない分岐             | 握りつぶさず速やかに落とす（Fail Fast）                |

- **catch したら「処理する」か「情報を足して投げ直す」かのどちらか。** 何もしない catch は禁止（意図的なら理由をコメントで残す）。
- 元の原因を捨てない: `throw new OrderSaveError('...', { cause: e })`。
- 例外は層をまたぐときに翻訳する（`SQLException` → `OrderRepositoryError`）。DBの都合をUIまで漏らさない。
- エラーメッセージはユーザー向け（次に何をすればいいか）と開発者向け（原因特定に足る情報）を分ける。内部情報をユーザーに出さない。

### 依存（第5〜7章）

- **依存の矢印は「変わりにくいもの」へ向ける。** 業務ルール ← 詳細（DB・UI・フレームワーク）であって、逆はない。
- 依存は自分で作らず外から受け取る（コンストラクタ注入）。組み立てを知るのは `main` / DIコンテナだけ。
- **循環importが出たら、その場で直す。** DIPで向きを逆転させるか、共通部分を別パッケージに抜く。
- 一緒に変更されるものを同じディレクトリに置く（CCP）。技術で分ける（`models/` `services/`）より機能で分ける（`order/` `user/`）。
- `utils/` `common/` `helpers/` に何でも入れない。全パッケージから依存される泥沼になる。
- パッケージの公開範囲は最小に（`index.ts` の窓口経由）。

### テスト（第11章）

- 構造は **AAA**（Arrange / Act / Assert）。空行で3ブロックに区切る。Act は1行が理想。
- **テスト名は仕様書として書く**: `test('3年以上の会員は20%割引になる')`。`test('getDiscount')` は不可。
- F.I.R.S.T.（Fast / Independent / Repeatable / Self-validating / Timely）。特に **Independent** — テスト間で状態を共有しない。
- 境界値と異常系を必ず含める。カバレッジ100%を目的化しない（カバレッジのためだけのテストが最も危険）。
- **テストが書きにくいと感じたら、テストではなく設計を疑う。**

### セキュリティ（第15章）

- **入力は信用しない。出力は文脈に応じてエスケープする。秘密はコードに書かない。**
- 検証はホワイトリスト方式（許可するものを列挙）。フロントの検証はUXのため、サーバー側で必ず再検証。
- SQLは文字列連結しない → プレースホルダ／ORM。
- HTMLへの埋め込みはエスケープ。`innerHTML` / `dangerouslySetInnerHTML` は使わない。
- **認可漏れが最多。** 「ログイン済み」と「その人が触っていい」は別。リソース所有者を毎回検証する。構造上他人のデータを取れない形（`repo.findByUser(userId, orderId)`）にする。
- ログにパスワード・トークン・カード番号・個人情報を出さない。
- 秘密を誤コミットしたら、消すだけでは不十分。**必ずキーをローテートする。**

### ログ（第14章）

- 構造化ログ（JSON）で出す。文字列連結でメッセージを組み立てない。
- レベルを使い分ける（ERROR: 対応が必要 / WARN: 異常だが継続 / INFO: 業務上の節目 / DEBUG: 開発用）。
- リクエストに相関ID（トレースID）を持たせ、全ログに含める。

### コミット・PR（第13章）

- 1コミット＝1つの意味。フォーマット変更と機能変更を混ぜない。
- リファクタリングと機能変更を同じPRに入れない（レビュー不能になる）。
- レビュー指摘は人ではなくコードに向ける。機械で防げる指摘は人力でやらずツールに任せる。

## 既存コードを直すとき（第17・20章）

**絶対条件: テストなしにリファクタリングしてはいけない。** 振る舞いを変えないのがリファクタリングの定義であり、機能追加やバグ修正と同時にやってはいけない。

```
① 変更したい箇所を見つける
② 継ぎ目（Seam）を作る … 依存を引数/コンストラクタに追い出す
③ 特性テストを書く … 「正しい振る舞い」ではなく「今の振る舞い」を固定する
④ ここでようやくリファクタリング（1手順ごとにテストを実行）
⑤ その後に機能変更
```

大きなコードを段階的に改善する順序（第20章）:

```
1. 名前を直す        → まだ構造は変えない
2. ネストを浅くする   → ガード節
3. 計算とI/Oを分離   → 最大の転換点
4. テストを書く      → ★ 構造を変える前に振る舞いを固定する
5. エラー処理を正す
6. 責務を分割する
7. 依存を逆転させる
8. 配置を整える
```

**全ステップを一度にやってはいけない。** 4（テスト）まで進めれば既に大きな成果。

## パフォーマンス（第18章）

- **測ってから直す。** 推測で最適化しない。
- 実務で遅い原因のほとんどはI/O（特に **N+1クエリ**）。CPU最適化より先に疑う。
- 目標値を先に決める（「何msなら合格か」）。決めずに始めると終われない。
- 可読性を捨てる最適化は、計測で効果が確認できた箇所だけに限定し、理由をコメントに残す。

## 日々のチェックリスト（第19章）

コードを書き終えたら自問する:

- [ ] この変数名/関数名は、初見の人が誤解しないか?
- [ ] この関数は「1つのこと」をしているか?
- [ ] ネストは2段以内に収まっているか?
- [ ] このコードをテストするのは簡単か?（難しいなら結合度が高い）
- [ ] 3ヶ月後の自分が読んで理解できるか?
- [ ] コメントで補っている部分は、コード自体を直せないか?
- [ ] このファイルは、一緒に変更されるファイルと同じディレクトリにあるか?
- [ ] 循環importを作っていないか?
- [ ] この変更を保証するテストはあるか?
- [ ] テストが書きにくいと感じたら、設計を疑ったか?
- [ ] 機械で防げる指摘を、人力でやっていないか?
- [ ] エラーを握りつぶしていないか?
- [ ] 引数で受け取ったオブジェクトを書き換えていないか?
- [ ] 外部からの入力をサーバー側で検証しているか?
- [ ] このコミットは1つの意味だけを含んでいるか?

## この規約を適用しない場所

このリポジトリの `src/` 配下のコードは**教材として意図的に悪く書かれている**。演習として明示的に依頼された場合を除き、勝手に「修正」しない。特に `src/fake-libs/`、`src/chapters/_support.ts`、`src/chapters/ch11-subject.ts` は触らない前提の素材。
