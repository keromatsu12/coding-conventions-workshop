# リファクタリングとパフォーマンス（第17〜20章）

> **リファクタリングの定義: 外から見た振る舞いを変えずに、内部構造を改善すること。**
> 「振る舞いを変えない」が絶対条件。機能追加やバグ修正と同時にやってはいけない。

## 大原則: テストなしにリファクタリングしてはいけない

```
テストがない状態での「改善」
  汚いが動くコード ──直す──▶ 綺麗だが壊れたコード ★最悪
  （誰も壊れたことに気づかない）

正しい順序
  ① まずテストを書く（今の振る舞いを固定する）
  ② テストが通ることを確認
  ③ 小さく直す → テスト → 直す → テスト …
```

### レガシーコード攻略の順番

```
① 変更したい箇所を見つける
② その周囲に「継ぎ目（Seam）」を作る … 依存を引数/コンストラクタに追い出す（DI）
③ 特性テストを書く … 「正しい振る舞い」ではなく「今の振る舞い」を記録する
④ ここでようやくリファクタリング
⑤ その後に機能変更
```

## コードの臭い（Code Smells）カタログ

「臭い」＝必ずしも悪ではないが、問題が隠れている可能性が高いサイン。

| 臭い | 何を疑うか | 対処 |
|---|---|---|
| 長すぎる関数 | 責務過多 | 関数抽出（第3章） |
| 巨大なクラス（神クラス） | 凝集度の低さ | クラス分割（第4・5章） |
| 長い引数リスト | 責務過多／まとまり | オブジェクト化 |
| 重複コード | DRY違反 | 共通化（※3回目から） |
| 深いネスト | 制御フローの複雑さ | 早期リターン（第3章） |
| 巨大なif/switch連鎖 | OCP違反 | ポリモーフィズム（第5章） |
| 不適切な名前 | 設計の曖昧さ | 改名（第2章） |
| 特徴の横恋慕（他クラスの値ばかり参照） | 責務の置き場所が違う | メソッド移動 |
| データの群れ（いつも一緒に渡る引数） | 概念が抽出できていない | 値オブジェクト化 |
| 変更の発散（1変更で複数箇所修正） | CCP違反 | パッケージ再編（第7章） |
| 散弾銃手術 | 責務が散らばっている | 集約する |
| コメントだらけ | コードが説明不足 | 名前と分割で解消（第2章） |

## 最もよく使う5つの手順

```
① 関数の抽出（Extract Function）… 最頻出。まとまった処理に名前をつけて切り出す
② 変数の抽出（Extract Variable）… 複雑な式に名前をつける
   if (order.total > 1000 && user.years > 3) → const isEligibleForDiscount = ...
③ 名前の変更（Rename）… IDEで安全に一括変更できる。最も費用対効果が高い
④ 条件記述の分解 / ガード節の導入 … ネストを浅くする
⑤ 関数の移動 / クラスの抽出 … 責務を正しい場所へ運ぶ
```

> **1手順ごとにテストを実行する。** まとめて10箇所直してからテストを流すと、どれが原因か分からなくなる。

## いつやるか / やらないか

```
✅ やるべきタイミング
・機能追加の直前（追加しやすい形に整えてから足す）＝「準備リファクタリング」最も効率がよい ★
・バグ修正の後（同じバグが出ない構造にする）
・コードを読んで理解に苦労したとき（理解した今が旬）
・ボーイスカウトルール（触ったついでに少しだけ）

❌ やるべきでないとき
・締切直前
・機能変更と同じPR（レビュー不能になる）
・近く廃止・作り直しが決まっているコード
・「動いているが誰も触らない」枯れたコード
・目的が「綺麗にしたいから」だけのとき ★
```

## 大規模な作り直し

```
❌ ビッグバン書き換え（同時に全部作り直す）
   → 数ヶ月機能追加が止まる／途中で頓挫する／旧仕様の漏れが必ず出る

✅ ストラングラーパターン（絞め殺しの木）
   機能ごとに少しずつ新システムへ流し、旧が空になったら削除する
   常にリリース可能な状態を保ちながら移行する
```

## 段階的改善の順序（第20章）

1つの汚いコードを直すときは、この順で進める。

```
1. 名前を直す         → まだ構造は変えない（第2章）
2. ネストを浅くする    → ガード節（第3章）
3. 計算とI/Oを分離     → ここが最大の転換点（第3・9章）
4. テストを書く       → ★ 構造を変える前に、振る舞いを固定する（第11・17章）
5. エラー処理を正す    → （第10・15章）
6. 責務を分割する      → （第4・5章）
7. 依存を逆転させる    → （第6・8章）
8. 配置を整える        → （第7章）
```

> **この全ステップを一度にやってはいけない。4（テスト）まで進めれば、既に大きな成果。**

# パフォーマンス（第18章）

## 鉄則: 測ってから直す

推測で最適化しない。**早すぎる最適化は諸悪の根源。**
プロファイラで実測し、ボトルネックを特定してから手を入れる。

## 計算量の基礎

| 記法 | 例 | 目安 |
|---|---|---|
| O(1) | ハッシュの参照 | データ量に依存しない |
| O(log n) | 二分探索、B-treeインデックス | ほぼ無視できる |
| O(n) | 配列を1周する | 素直 |
| O(n log n) | 一般的なソート | 実用の上限 |
| O(n²) | 二重ループ | **要注意** |

「今のデータ量」ではなく「将来のデータ量」で考える。

```javascript
// ❌ O(n²)：配列の中で配列を検索
orders.filter(o => userIds.includes(o.userId));

// ✅ O(n)：Setにしてから検索
const idSet = new Set(userIds);
orders.filter(o => idSet.has(o.userId));
```

## 実務で遅い原因のほとんどはI/O

```
CPU演算              1 ns
メモリアクセス       100 ns
SSD読み込み         150 μs
同一DCのDB問い合わせ   1 ms
外部API呼び出し      100 ms

→ CPUのループを10倍速くしても、DBを1回減らす方が効く
```

**最頻出の犯人: N+1問題**

```javascript
// ❌ N+1（注文100件で101回のクエリ）
const orders = await repo.findAll();
for (const o of orders) {
  o.user = await userRepo.find(o.userId);   // N回 ★
}

// ✅ まとめて取得（2回）
const orders = await repo.findAll();
const users  = await userRepo.findByIds(orders.map(o => o.userId));
```

チェックすべき定番:

```
① N+1クエリ              → まとめて取得 / JOIN
② インデックス不足        → 実行計画（EXPLAIN）を見る
③ 不要なデータの取得      → SELECT * をやめる、ページング
④ 直列で実行している独立処理 → 並列化（Promise.all）
⑤ 毎回計算している不変の値  → キャッシュ
```

## どこまでやるか — 目標を先に決める

```
❌「速ければ速いほどいい」→ 終わりがない。過剰最適化
✅ 数値目標を先に置く
   「一覧APIは p95 で 300ms 以内」「同時100リクエストでエラー率0.1%以下」
   → 満たしていれば、それ以上は可読性を優先する
```

**平均ではなくパーセンタイル（p95 / p99）を見る。**

## 可読性とのトレードオフ

可読性を捨てる最適化は、**計測で効果が確認できた箇所だけ**に限定し、
「なぜこの書き方なのか」「どれだけ速くなったか」をコメントに残す（第2章の「なぜ」を書く）。

# 過剰設計の警告サイン（第19章）

| サイン | 問題 |
|---|---|
| 実装クラスが1つしかないインターフェース | 抽象化が早すぎる可能性 |
| ファイルを5個開かないと処理が追えない | 分割しすぎ |
| 「将来必要になるかも」で作った機能 | YAGNI違反 |
| 抽象クラスの継承が3階層以上 | 継承の乱用 |
| モックだらけのテスト | 実装詳細に密着。リファクタで壊れる |
| カバレッジのためだけのテスト | 保証していないのに安心してしまう（最も危険） |

**原則: 抽象化は「2回目の重複」を見てから**（Rule of Three）。
