# テスト・ツール・チーム・運用（第11〜14章）

## テストは何のために書くのか

「バグを見つけるため」ではなく、**安心して変更するため**。
テストがあるから設計を直し続けられ、設計が良いからテストが書ける。この循環に入れたチームはコードが良くなる。

## テストピラミッド

```
        E2E        少なく（遅い・壊れやすい）
    統合テスト      中くらい
  ユニットテスト     多く（速い・安定）★土台
```

アーキテクチャの内側ほどテストが速く・安定し・書きやすい。
ロジックがController（外側）にあると、テストのたびにHTTPリクエストが必要になる
— これが「テストが書きにくい＝設計が悪い」の正体。

## 良いテストの条件

### F.I.R.S.T.

| 頭文字 | 意味 | 内容 |
|---|---|---|
| **F**ast | 速い | 遅いテストは実行されなくなる |
| **I**ndependent | 独立 | 他のテストの実行順・結果に依存しない ★特に重要 |
| **R**epeatable | 再現可能 | 何度でも、どの環境でも同じ結果 |
| **S**elf-validating | 自己検証 | 成功/失敗が自動判定される（目視確認しない） |
| **T**imely | 適時 | 実装とほぼ同時に書く（後回しは書かれない） |

### 構造：AAA（Given-When-Then）

```javascript
test('3年以上の会員は20%割引になる', () => {
  // Arrange（準備）— 前提条件を作る
  const user = new User({ isActive: true, membershipYears: 3 });

  // Act（実行）— テスト対象を1回だけ呼ぶ
  const discount = getDiscount(user);

  // Assert（検証）— 期待結果を確認する
  expect(discount).toBe(0.2);
});
```

Arrange は複数行OK、Act は1行が理想、Assert は1つの概念を検証。空行で3ブロックに区切る。

### テスト名は「仕様書」として書く

```javascript
❌ test('test1', ...)
❌ test('getDiscount', ...)        // 何を確認しているか不明
✅ test('3年以上の会員は20%割引になる', ...)
✅ test('退会済みユーザーには割引を適用しない', ...)
```

## 何をテストすべきか

1. **同値分割** — 同じ結果になるグループから代表を1つ選ぶ
2. **境界値分析** — バグは境界に集中する。「直前・ちょうど・直後」をテストする（`>=` と `>` の間違いが最頻出）
3. **異常系を必ず入れる** — null、空、負数、型違い。忘れられがち★

```
正常系（ハッピーパス）        … 1〜2本
境界値                      … 境界ごと
異常系（null, 空, 負数）      … ★忘れられがち
エラー時の振る舞い            … 例外を投げる／エラーを返す
```

経験則: バグの大半は境界（0、1、上限、空、null）で起きる。

## テストダブル

| 種類 | 役割 | 使いどころ |
|---|---|---|
| **Dummy** | 渡すだけで使わない | 引数を埋めるため |
| **Stub** | 決まった値を返す | 「このAPIは常に成功する」を再現 |
| **Fake** | 簡易的だが動く実装 | インメモリDBなど。**最も推奨** |
| **Spy** | 呼ばれたことを記録する | 「メールが1回送られた」を確認 |
| **Mock** | 呼ばれ方を検証する | 期待を事前に設定 |

**モックの使いすぎに注意。** 何もかもモックにすると、実装を変えただけでテストが壊れ（＝実装詳細に依存）、
テストが通っても本当に動くか分からなくなる。

```
・自分が書いたコード同士        → なるべく本物を使う
・外部システム（DB, 決済, メール） → Fake / Stub に置き換える
・「時刻」「乱数」「UUID」       → 必ず注入して固定できるようにする
```

```javascript
// ❌ テスト不能（実行時刻で結果が変わる）
function isExpired(token) { return token.expiresAt < new Date(); }

// ✅ 時刻を注入する
function isExpired(token, now) { return token.expiresAt < now; }
```

## カバレッジ

- 行カバレッジ100%でも、分岐や境界を通っていなければ何も保証しない。
- **数字を目的化しない。** 「カバレッジのためだけのテスト」は、保証していないのに安心させる最も危険な状態。
- 優先して上げるべきは、業務ルール（ドメイン層）と、変更頻度が高くバグが多いファイル。

## テストのアンチパターン

| アンチパターン | 何が起きるか |
|---|---|
| 実装詳細をテストする | リファクタのたびに壊れる。テストが足枷になる |
| 1テストに10個のassert | 落ちた原因が分からない |
| テスト内にif/loopがある | テスト自体にバグが入る |
| 巨大な共通セットアップ | そのテストの前提が読めない |
| Flakyテストを放置 | 「また誤検知でしょ」と誰も見なくなる（最悪） |
| コミット前にコメントアウト | 存在しないのと同じ |

**Flakyテストは最優先で潰す。** 1本でもあると、チーム全体がテスト結果を信用しなくなる。

## テストしにくさは「設計の警告」

| テストが書きにくい理由 | 疑うべき設計 |
|---|---|
| 準備が長大 | 依存が多すぎる（結合度が高い） |
| モックだらけになる | 具体に依存している（DIP違反） |
| private を呼びたくなる | クラスの責務が大きすぎる |
| 時刻・乱数で結果が変わる | 依存を注入していない |
| DBを立てないと動かない | 計算とI/Oが分離されていない |

# ツールによる自動化（第12章）

品質保証は**多層防御**で考える。

```
エディタ（保存時） → コミット前フック → CI → コードレビュー
   速い・軽い                              遅い・人間の時間
```

早い層で捕まえるほど安い。**人間のレビューは「機械にできないこと」だけに使う。**

- **フォーマッター**（Prettier など）— 書式の議論をゼロにする。設定を1つ決めて全ファイルに適用し、それ以降は考えない。
- **リンター**（ESLint など）— バグの温床を静的に検出。ルールは少しずつ増やす。
- **型チェック**（TypeScript の `strict`）— 実行せずに矛盾を見つける。`any` は逃げ道であって解決ではない。
- **その他** — 依存の循環検出（dependency-cruiser / madge）、秘密情報の検出（gitleaks）、脆弱な依存の検出。

### 既存プロジェクトへの導入手順

```
Step 1  フォーマッター導入 — 全ファイル一括整形を「単独コミット」で（議論せずデフォルト設定で決め打つ）
Step 2  リンター導入（警告レベル）— 既存違反は warn、新規違反だけ error
Step 3  CIに組み込む — 「これ以上悪化させない」ラインを引く（Ratchet戦略）
Step 4  重要箇所からテスト追加 — 全体を目指さない。「よく壊れる場所」「これから直す場所」から
Step 5  ルールを段階的に error へ昇格
```

> **鉄則: 既存コードを全部直そうとしない。「新しく書く部分だけは綺麗にする」から始める。**
> （ボーイスカウトルール = 来たときより少しだけ綺麗にして帰る）

一度に全部エラーにすると、警告が数千件出て誰も直せず、結局無効化される。

# Git・コミット・レビュー（第13章）

- **1コミット＝1つの意味の変更。** 「動く単位」ではなく「説明できる単位」。
- フォーマット変更と機能変更を混ぜない（差分がレビュー不能になる）。
- コミットメッセージは「何をしたか」より **「なぜ」** が価値を持つ。件名は簡潔に、本文に背景を書く。
  Conventional Commits（`feat:` `fix:` `refactor:` `docs:` `test:` `chore:`）は有効な選択肢。
- **PRは小さく。** 大きなPRはレビューが形骸化する（「LGTM」だけ付く）。
- リファクタリングと機能変更を同じPRに入れない。
- レビュー観点は「機械にできないこと」に絞る: 設計・命名・仕様の理解・抜けているケース。
- 指摘は**人ではなくコードに向ける**。「なぜこうしたのか」を聞く姿勢で、提案として書く。

# ログと可観測性（第14章）

- ログは**未来の自分と運用者**のために書く。「後から何が起きたか追える」ことが目的。
- **構造化ログ（JSON）** で出す。文字列連結でメッセージを組み立てない（検索・集計できなくなる）。
- **相関ID（トレースID）** をリクエスト単位で発行し、全ログに含める。分散環境では必須。

### ログレベル

| レベル | 意味 | 対応の要否 |
|---|---|---|
| ERROR | 処理が失敗し、対応が必要 | **人が対応する** |
| WARN | 異常ではないが注視すべき（リトライ成功、非推奨API使用） | 監視する |
| INFO | 業務上の重要イベント（注文確定、ログイン） | 平常時の記録 |
| DEBUG | 開発時の詳細 | 本番では通常オフ |

**最悪のアンチパターンは ERROR の乱発。** ERRORが1日1万件出ると誰も見なくなり、本物の障害が埋もれる（アラート疲れ）。
ERRORは「人が対応すべきもの」だけ。対応不要ならWARN以下に落とす。

```javascript
// ❌ 文字列を組み立てる（検索・集計できない）
log.info(`ユーザー${userId}が注文${orderId}を確定しました`);

// ✅ 構造化する（機械が処理できる）
log.info('order.confirmed', { userId, orderId, amount, traceId });
```

### 絶対にログに出してはいけないもの

パスワード、トークン、APIキー、クレジットカード番号、個人情報（氏名・住所・メールアドレスの全体）、
セッションID。マスクするか、そもそも出さない。

### 可観測性の3本柱

**ログ**（何が起きたか）・**メトリクス**（どれくらい起きたか）・**トレース**（どこで時間を使ったか）。
3つ揃って初めて「原因が分かる」状態になる。
