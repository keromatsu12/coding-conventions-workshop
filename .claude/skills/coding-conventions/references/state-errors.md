# 状態と不変性・エラーハンドリング（第9〜10章）

> バグの大半は「値が変わること」から生まれる。変わらないものは壊れない。
> 設計の要点は、**変わる部分をできるだけ小さく囲い込む**こと。

## なぜ状態が難しいのか

```
認知コスト ＝ 変数の数 × 変わりうるタイミングの数

変数10個 × どこでも書き換え可能        → 組合せが爆発
変数10個 × うち8個は不変（const）      → 実質2個だけ追えばいい
```

状態があると、コードを読むときに「時間」という次元が増える。
「この行に来たとき、この変数は何になっているか?」を追うのが読解コストの正体。

## 不変を基本にする

```javascript
// ❌ 引数を書き換える（呼び出し元も壊れる）
function addTax(order) {
  order.total = order.total * 1.1;
  return order;
}

// ✅ 新しい値を返す
function addTax(order) {
  return { ...order, total: order.total * 1.1 };
}
```

| 言語 | 不変にする手段 |
|---|---|
| JavaScript / TypeScript | `const`、スプレッド構文、`readonly`、`Object.freeze` |
| Java | `final`、record、不変コレクション |
| Kotlin | `val`、`data class` + `copy()` |
| Python | タプル、`frozen=True` の dataclass |
| Go | 値渡し、ポインタを渡さない |

> **まず `const` / `val` / `final` で宣言し、どうしても必要なときだけ可変にする。**

## 可変性を閉じ込める

状態はなくすのではなく**集める**。

```
❌ A・B・C がそれぞれ状態を持つ  → どこで変わったか分からない、同期がずれる
✅ 状態を持つ層（Store / Entity）を1つ作り、A・B・C は値を受け取るだけの純粋な処理にする
```

## 共有された可変状態の危険度ランキング

```
★★★ グローバル変数・シングルトンの可変状態  → どこからでも変えられる。追跡不能
★★  引数として渡されたオブジェクトの書き換え  → 呼び出し元が予期しない副作用
★★  モジュールスコープのキャッシュ          → テストが実行順に依存する原因No.1
★    クラスのフィールド                    → スコープが限定されるのでまだ扱える
```

```javascript
// ❌ モジュールレベルの可変状態（テストが順序依存になる）
let cache = {};
export function getUser(id) {
  if (!cache[id]) cache[id] = fetchUser(id);
  return cache[id];
}

// ✅ 状態を持つ主体を明示し、注入できるようにする
export class UserLoader {
  #cache = new Map();
  constructor(fetcher) { this.fetcher = fetcher; }
  get(id) { /* ... */ }
}
```

## 「不正な状態を作れなくする」

```
3段階の防ぎ方（下ほど強い）
① 実行時にチェックする    … if文で弾く（漏れる）
② テストで確認する        … 書き忘れる
③ そもそも表現できなくする … 構造上あり得なくする ★最強
```

```typescript
// ❌ 不正な状態が表現できてしまう
class Order {
  status: string;
  shippedAt?: Date;
  cancelledAt?: Date;   // status='cancelled' なのに shippedAt がある、が作れる
}

// ✅ 状態遷移を型と操作で縛る
type Order =
  | { status: 'pending' }
  | { status: 'shipped';   shippedAt: Date }
  | { status: 'cancelled'; cancelledAt: Date };
```

状態遷移図を書いてから実装する。存在しない遷移は、コード上も「呼べない」ようにする。

# エラーハンドリング

正常系だけのコードは半分しか書けていない。

## 3種類の「失敗」を分類する

| 種類 | 例 | 扱い |
|---|---|---|
| ① 想定内の失敗（業務エラー） | 在庫切れ、残高不足、バリデーションNG、認証失敗 | 「起きて当然」。**戻り値**で表現し、呼び出し元が必ず処理する |
| ② 想定内の異常（環境エラー） | ネットワーク断、DBタイムアウト、外部APIの5xx | **例外**。リトライ・フォールバック・縮退運転の対象 |
| ③ 想定外（バグ） | null参照、配列外アクセス、あり得ない分岐 | 握りつぶさない。速やかに落として気づく（Fail Fast） |

よくある間違い:
- ①を例外で投げる → 正常な業務フローが例外まみれになり、見落とす
- ③を握りつぶす → バグが隠れ、原因不明の不整合データが残る ★最悪

## 例外 vs 戻り値

```typescript
// ①想定内の業務エラー → 戻り値で表現する（呼び出し元が無視できない）
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

function withdraw(account, amount): Result<Account, 'INSUFFICIENT_FUNDS'> {
  if (account.balance < amount) return { ok: false, error: 'INSUFFICIENT_FUNDS' };
  return { ok: true, value: { ...account, balance: account.balance - amount } };
}
```

```
例外を使うべきとき              戻り値を使うべきとき
・その場で対処できない          ・呼び出し元が必ず判断すべき
・呼び出し元の何段も上で処理する  ・「失敗」が仕様の一部
・プログラムの前提が壊れた       ・型で網羅性を強制したい

判断基準：「これは例外的な事態か? それとも予期された結果か?」
```

## アンチパターン：握りつぶし

```javascript
// ❌ 最悪。原因が永久に分からなくなる
try { await save(order); } catch (e) { }

// ❌ ログだけ出して握りつぶす（呼び出し元は成功したと思う）
catch (e) { console.log(e); }

// ❌ 情報を捨てる（元の原因が消える）
catch (e) { throw new Error('保存に失敗'); }

// ✅ 原因を保持して、意味のある例外に変換する
catch (e) {
  throw new OrderSaveError(`注文${order.id}の保存に失敗`, { cause: e });
}
```

> **catchしたら、必ず「処理する」か「情報を足して投げ直す」かのどちらか。**
> 何もしない catch は、意図的なら理由をコメントで残す。

## どの層で捕まえるか

```
プレゼンテーション層  例外を「ユーザー向けメッセージ」と「HTTPステータス」に変換
                    最終防衛線（グローバルハンドラ）で必ず捕まえる ★
アプリケーション層    業務エラーを判断しフローを分岐／トランザクションのロールバック
ドメイン層           業務ルール違反を型・戻り値で表現。技術的な例外を知らない
インフラ層           技術例外を上位の言葉に翻訳して投げる（SQLException → OrderRepositoryError）
```

**例外は「層をまたぐときに翻訳する」。** DBの都合をUIまで漏らさない（＝依存の向きを守る）。

## エラーメッセージの設計

「エラーが発生しました」では利用者も開発者も何も分からない。2種類を分けて設計する。

- **ユーザー向け**: 何が起きたか（平易な言葉）／**次に何をすればいいか**（最重要）／内部情報を出さない（SQLやパスは漏洩リスク）
- **開発者向け（ログ）**: 原因特定に足る情報（対象ID、パラメータ、スタックトレース、相関ID）

## リトライとフォールバック

```
リトライしていい失敗        リトライしてはいけない失敗
・タイムアウト              ・バリデーションエラー（何度やっても同じ）
・503 / 429                ・認証失敗
・一時的なネットワーク断     ・冪等でない処理（二重課金の危険）★
```

**リトライ前に必ず確認: その処理は冪等か?**

指数バックオフ＋ジッター: 1秒 → 2秒 → 4秒 → 諦める。
連続失敗したら一定時間呼び出しを止める（サーキットブレーカー）。

## 早期に失敗させる（Fail Fast）

```
❌ 入力 → 処理 → 処理 → 処理 → 保存   ← ここで初めて壊れる。原因特定に何時間も
✅ 入力 →[検証]→ 処理 → 処理 → 保存    ← 壊れた場所＝原因の場所
```

**境界（入力を受け取る場所）で検証し、内側では「正しい値であること」を前提にできる状態を作る。**
これは「不正な状態を作れなくする」と同じ考え方。
