# セキュアコーディング（第15章）

> **原則: 入力は信用しない。出力は文脈に応じてエスケープする。秘密はコードに書かない。**

事故の大半は基本的な不注意から起きる。ここは「最低限やらかさない」ための範囲。

## すべての入力を信用しない

信用してはいけないもの（＝外部からの入力すべて）:

```
フォーム入力 / URLパラメータ / クエリ文字列
HTTPヘッダー / Cookie
アップロードファイル（名前・中身・拡張子）
外部APIのレスポンス ★忘れがち
環境変数・設定ファイル
```

⚠️ **「フロントエンドで検証しているから大丈夫」は誤り。**
フロントの検証はUXのため。攻撃者はAPIを直接叩く → サーバー側で必ず再検証する。

検証は**ホワイトリスト方式**（許可する形式のみ通す）。
ブラックリスト（危険な文字を除去）には必ず抜け道がある。

## 代表的な脆弱性と対策

| 脆弱性 | 対策 |
|---|---|
| SQLインジェクション | 文字列連結でSQLを作らない → プレースホルダ／ORMを必ず使う |
| XSS | HTMLに値を埋める際にエスケープ。フレームワークの自動エスケープを切らない。`innerHTML` / `dangerouslySetInnerHTML` 禁止 |
| CSRF | トークン検証、SameSite Cookie |
| **認可の欠落（最多）** | 「ログイン済み」と「その人が触っていい」は別。リソース所有者を毎回検証する |
| 秘密情報の漏洩 | ソースにキーを書かない、ログに出さない |
| 脆弱な依存関係 | ライブラリを更新する（自動監視を入れる） |

```javascript
// ❌ SQLインジェクション
db.query(`SELECT * FROM users WHERE email = '${email}'`);

// ✅ プレースホルダ
db.query('SELECT * FROM users WHERE email = ?', [email]);
```

## 認可漏れは最も多く、最も見つけにくい

```
❌ よくある事故（IDOR）
GET /api/orders/12345
  → ログイン済みかどうかだけ確認して返す
  → IDを 12346 に変えると他人の注文が見える

✅ 必ず「その人のものか」を検証する
const order = await repo.find(id);
if (order.userId !== currentUser.id) throw new ForbiddenError();
```

### 設計で防ぐ

```
認可チェックを「書き忘れられる場所」に置かない

❌ 各Controllerで個別にif文 → 1箇所忘れたら穴が開く
✅ 共通のミドルウェア／リポジトリ層で常に絞り込む
   repo.findByUser(currentUser.id, orderId)
   ＝ 構造上、他人のデータを取得できない
```

これは第9章の「不正な状態を作れなくする」と同じ発想。

## 秘密情報の扱い

- APIキー・パスワードをコードに書かない
- `.env` をコミットしない（`.gitignore` を最初に書く）
- 秘密は環境変数／シークレットマネージャで注入する
- **誤コミットしたら「消す」だけでは不十分。Git履歴に残るので必ずキーをローテートする** ★
- gitleaks 等で自動検出する

## パスワードと認証

- 自前でハッシュ処理を実装しない → bcrypt / argon2 など実績あるライブラリを使う
- 平文保存・可逆暗号化は論外
- 自前で認証基盤を作らない（可能なら OIDC / IdP に任せる）
- エラーメッセージで情報を漏らさない

```
❌「そのメールアドレスは登録されていません」→ アカウントの存在有無が分かる
✅「メールアドレスまたはパスワードが正しくありません」
```

## 安全側に倒す（Secure by Default）

```
❌ 明示的に禁止しない限り許可  → 設定漏れ＝穴
✅ 明示的に許可しない限り禁止  → 設定漏れ＝不便（安全）
```

**最小権限の原則**
- DBユーザーに不要な DROP 権限を与えない
- APIキーのスコープを絞る
- 「とりあえず管理者権限」をやらない

## ログとの関係（第14章）

パスワード、トークン、APIキー、秘密鍵、カード番号、個人情報（氏名・住所・電話・メール）、
リクエストボディの丸ごとダンプは**絶対にログに出さない**。

「識別できるが復元できない」形にする:
`userId=1234` ○ / `email=xxx@example.com` ✗、`card=****1234` ○ / 全桁 ✗

ログは長期保存され多くの人がアクセスできる。**「一度出したら消せない」前提で設計する。**
