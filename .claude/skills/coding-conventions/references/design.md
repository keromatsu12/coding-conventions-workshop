# 設計原則（第4〜8章）

すべて「同じことを別のスケールで言っている」だけ。
関数の単一責任 → モジュールの凝集度 → SOLIDのSRP → パッケージ分割 → アーキテクチャのレイヤ分割。

## 第4章 凝集度と結合度

### 凝集度（Cohesion）＝ モジュール内部のまとまりの良さ

**高いほど良い。** 最良は「機能的凝集」（1つの明確な役割のためだけに要素が集まっている）。
最悪は「偶発的凝集」（`utils.ts` に無関係な関数が寄せ集められている状態）。

判定: 「このモジュールは何をするものか」を **and を使わず一文で** 言えるか。

### 結合度（Coupling）＝ モジュール同士の依存の強さ

**低いほど良い。**

- 悪い: 内部データ構造に直接触る、グローバル変数を共有する、相手の実装詳細を知っている
- 良い: 引数と戻り値だけでやり取りする、抽象（インターフェース）越しに話す

判定: 「相手を差し替えたとき、こちらを直す必要があるか」。

### なぜこの2つが重要か

高凝集・低結合＝**変更の影響範囲が閉じ込められている**状態。
- 高凝集 → 直す場所が1箇所に決まる
- 低結合 → 直しても他が壊れない

## 第5章 SOLID

| 原則 | 一言 | 実務での効き目 |
|---|---|---|
| **SRP** 単一責任 | 変更理由は1つに | ★最重要。まずこれだけ守る |
| **OCP** 開放閉鎖 | 拡張には開き、修正には閉じる | if/switch連鎖をポリモーフィズムへ |
| **LSP** リスコフ置換 | 派生型は基底型と置き換えられる | 継承を使うなら必須 |
| **ISP** インターフェース分離 | 使わないメソッドに依存させない | 巨大インターフェースの分割 |
| **DIP** 依存関係逆転 | 抽象に依存し、詳細に依存しない | ★テスタビリティの源 |

### SRP — 「変更理由は1つか?」

「レポートの計算方法が変わったとき」と「出力フォーマットが変わったとき」で
同じクラスを直すなら、責務が2つある。

### OCP — if/switch 連鎖はポリモーフィズムへ

新しい種類を足すたびに既存の関数を修正しているなら OCP 違反。
ただし **抽象化は「2回目の重複」を見てから**（Rule of Three）。1種類しかないうちは if で十分。

### DIP — 上位が下位に依存しない

```
❌ OrderService ──▶ MySQLOrderRepository（具体）
✅ OrderService ──▶ OrderRepository（抽象） ◀── MySQLOrderRepository（具体）
```

抽象（インターフェース）は**使う側**が所有する。これが「依存の逆転」。

## 第6章 依存関係

### 依存の向きの原則

**変わりにくいものへ向ける。**

```
変わりやすい: UI / フレームワーク / DB / 外部API
変わりにくい: 業務ルール（「送料は5000円以上で無料」）

✅ UI ──▶ 業務ルール ◀── DB
❌ 業務ルール ──▶ DB
```

ビジネスルールは、DBやフレームワークが何であっても不変。だから最も内側に置く。

### 依存性注入（DI）

```javascript
// ❌ 自分で作る（Emailに固定され、テストで本物のメールが飛ぶ）
class NotificationService {
  constructor() { this.sender = new EmailSender(); }
}

// ✅ 外から受け取る（Constructor Injection）
class NotificationService {
  constructor(sender) { this.sender = sender; }
}

const service     = new NotificationService(new EmailSender());
const testService = new NotificationService(new MockSender());
```

**「誰と誰を繋ぐか」を知っているのは `main` / DIコンテナだけ。** 各クラスは相手を知らない。

DIフレームワークは必須ではない。コンストラクタで受け取り、`main` で組み立てるだけで十分。

## 第7章 パッケージ設計

### 技術で分けるか、機能で分けるか

```
❌ 技術で分ける              ✅ 機能で分ける
src/                        src/
├── controllers/            ├── order/
├── services/               │   ├── Order.ts
├── models/                 │   ├── OrderService.ts
└── utils/                  │   └── internal/
                            └── user/

「注文のルールが変わったので services/ と models/ と utils/ を直す」
                        ↓
「注文のルールが変わったら order/ だけ直せばいい」
```

### 凝集の3原則（引っ張り合う）

- **REP** 再利用の単位＝リリースの単位
- **CCP** 一緒に変更されるものを同じパッケージに（★まずこれだけ守る）
- **CRP** 一緒に使われないものを同じパッケージに入れない（ISPのパッケージ版）

REP/CCPを重視するとパッケージは大きく、CRPを重視すると小さくなる。3つ同時には満たせない。
開発初期・自社サービスは **CCP** 優先でよい。

### 結合の3原則

- **ADP** 循環依存を作らない
- **SDP** より安定した（＝多くから依存され、変えにくい）方向に依存する
- **SAP** 安定したものほど抽象的であるべき

循環の壊し方は2つ:
1. DIPで依存の向きを片方だけ逆転させる（`order ──▶ [UserFinder] ◀── user`）
2. 共通部分を新パッケージに抜き出す（`order ──▶ shared ◀── user`）

**循環importが出たら、その場で直す。** 放置すると必ず増える。
（`madge`, `dependency-cruiser`, `import-linter` で自動検出できる）

### 日々守る4つのルール

1. 一緒に変更されるものを、同じディレクトリに置く（CCP）
2. 循環依存を作らない（ADP）
3. 依存の矢印を、変わりにくい方へ向ける（SDP）
4. パッケージの公開範囲を最小にする（`index.ts` などの窓口を作る）

### パッケージのアンチパターン

| アンチパターン | なぜダメか | 対処 |
|---|---|---|
| `utils/` `common/` `helpers/` に何でも入れる | 偶発的凝集。全パッケージから依存される泥沼 | 用途ごとに名前のあるパッケージへ |
| `models/` に全エンティティを集約 | 機能変更が複数ディレクトリに散る | 機能ごとに配置 |
| 深すぎる階層（5階層以上） | importパスが読めない、移動が大変 | 2〜3階層に収める |
| どこからでも何でもimportできる | 事実上パッケージ分割していない | 窓口(index)経由に統一、Lintで強制 |
| `shared/` が全体の半分を占める | 分割の判断を放棄している | 本当に共通か再検討 |

依存ルールは人間の意志では守れない。ツールで縛る:
ESLint `import/no-cycle` `import/no-restricted-paths`、dependency-cruiser、ArchUnit、import-linter。

```javascript
// 例: domain層がinfrastructure層をimportすることを禁止する
{ from: { path: '^src/.*/domain' }, to: { path: '^src/.*/infrastructure' }, severity: 'error' }
```

## 第8章 アーキテクチャ

3つとも言っていることは同じ: **重要なもの（業務ルール）を、詳細（DB・UI・FW）から守る。**

### レイヤード（基本形）

```
Presentation → Application → Domain → Infrastructure
```
依存は上から下への一方向のみ。ただし素朴に組むと Domain が Infrastructure に依存してしまうため、
DIP で Infrastructure → Domain に逆転させるのが実務上の定石。

### ヘキサゴナル（ポート＆アダプタ）

アプリケーションの内側が「ポート（インターフェース）」を定義し、
外側の「アダプタ」（DB実装、HTTPコントローラ）がそれを実装する。
テストではアダプタを差し替えるだけで済む。

### クリーンアーキテクチャ

```
Entities（業務ルール） ← Use Cases ← Interface Adapters ← Frameworks & Drivers
```
**依存は常に内向き。** 内側は外側を一切知らない。

### 実践上の注意

- 小さなアプリに4層は過剰。**まずレイヤード、必要になったら内側を守る方向へ**。
- 層を増やすほどファイル数と間接参照が増える。「ファイルを5個開かないと処理が追えない」は分割しすぎのサイン。
- アーキテクチャの選定理由は ADR に残す（第16章）。
